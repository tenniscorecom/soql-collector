# 使い方

Salesforce レポートの describe を管理番号ごとにとって JSON にし、 AI に SOQL を
組んでもらうための CSV（対応表・項目表）を作るツールです。

## 1. 初回準備

1. `config.ini.example` を `config.ini` にコピーする（実体の `config.ini` は
   `.gitignore` 済み）
2. `config.ini` の次のキーを必要に応じて書き換える

| セクション | キー | 意味 |
|---|---|---|
| `[FILES]` | `MASTER_XLSX_PATH` | レポート管理表（Excel）。**必須** |
| `[FILES]` | `OUTPUT_DIR` | describe の JSON と CSV の出力先。既定は `./output` |
| `[LIMITS]` | `RELATED_MAX` | 主オブジェクトから辿る関連オブジェクトの最大数。既定は `40` |
| `[SF]` | `CREDENTIAL_PREFIX` | comken の `comken cred` で登録した認証情報の先頭につける接頭辞 |

3. comken の親ディレクトリ（既定 `F:\dev`）を `PYTHONPATH` に含めるか、
   同梱の `実行.bat` を使う（ `実行.bat` は PYTHONPATH を代行してくれる）

## 2. コマンド実行例

### `fetch` （取得）

```powershell
# 1 件だけ取得
python main.py fetch 1001

# 複数まとめて
python main.py fetch 1001 1002 1003

# 管理表の「有効」が ○ のもの全部
python main.py fetch --all

# 接続せず対象だけ表示
python main.py fetch 1001 --dry-run
```

`fetch` を実行すると次の順で動きます。

1. 管理表を読んで対象エントリを決める（ `--all` で「有効」な全件）
2. ID ごとに Salesforce へつなぎ、 レポート describe・主オブジェクト
   describe・関連オブジェクト describe を取る
3. `{管理番号}.json` を `OUTPUT_DIR` に書く（ **一時ファイル経由** ）
4. 取れた ID について `対応表_{管理番号}.csv` を作り、 全体の `対応表.csv` /
   `項目表.csv` を `OUTPUT_DIR` の全 JSON から作り直す

失敗した ID は個別にスキップされ、 残りの ID は続けて取得します。
終了コードは「失敗 ID が 1 件でもあれば 1」、 全件成功なら 0、
入力エラー（管理番号が管理表に無い等）は 2 です。

### `list` （一覧）

管理表の管理番号・概要・有効（○/×）・レポート ID を表示します。 Salesforce
には接続しません。

```powershell
python main.py list
```

### `tables` （CSV を作り直す）

`OUTPUT_DIR` の全 JSON から `対応表.csv` と `項目表.csv` を再生成します。
`fetch` の最後で自動実行もされますが、 フォーマット変更後や手動で JSON を
書き換えた後にも単体で実行できます。

```powershell
python main.py tables
```

JSON が無いときは「先に fetch を実行して `OUTPUT_DIR` に JSON を作ってください」
と表示して終了コード 1 を返します。

### 引数なし（対話メニュー）

`python main.py` を引数なしで起動すると、 番号を選ぶだけの対話メニューが
出ます。

| 番号 | 動作 |
|---|---|
| `1` | 管理番号を指定して取る（続けて管理番号を聞かれる。 Enter で `--all` と同じ） |
| `2` | 有効なものをすべて取る（ `fetch --all` ） |
| `3` | 一覧を見る（ `list` ） |
| `4` | CSV を作り直す（ `tables` ） |
| `0` / 空 Enter | 終了 |

### RPA から呼ぶ例

社内 RPA 基盤から実行する場合は `実行.bat` を経由する。 終了コードは
`実行.bat` がそのまま返すので、失敗があれば 1 で上がる。

```bat
実行.bat fetch --all
```

**RPA から呼ぶときは必ず引数を付けること。** 引数なしで呼ぶと対話メニューが
起動して、入力待ちで止まってしまう。

## 3. 出力ファイルの読み方

### `{管理番号}.json` （SOQL 組立に必要な部分だけにした describe）

JSON には describe の**原本**は書きません。 SOQL を組むのに必要な **構造だけ**
を残します。 具体的には:

- レポート describe: `reportMetadata` / `reportExtendedMetadata` /
  `droppedKeys` の 3 つだけ
- オブジェクト describe: `name` / `label` / `custom` / `fields` の 4 つだけ
- 各項目: `name` / `label` / `type` / `custom` / `referenceTo` /
  `relationshipName` / `picklist` / `picklistTotal` の 8 つだけ

原本が巨大になるキー（ `reportTypeMetadata` / `childRelationships` /
`recordTypeInfos` / `picklistValues` など）は**最初から JSON に出てきません**。
レポート describe から落としたキーの名前は `droppedKeys` に**出現順で**残るので、
「 必要なものを間違って落としていないか 」 は最初の実行で確認できます。

```json
{
  "管理番号": "1001",
  "概要": "顧客一覧",
  "レポートID": "00O5g00000ABCDE",
  "URL": "https://example.my.salesforce.com/lightning/r/Report/00O5g00000ABCDE/view",
  "取得日時": "2024-01-01T12:34:56",
  "主オブジェクト": "Opportunity",
  "report": {
    "reportMetadata": {
      "id": "00O5g00000ABCDE",
      "name": "顧客一覧",
      "reportType": { "type": "Opportunity" },
      "reportFormat": "TABULAR",
      "detailColumns": ["Opp.Name"],
      "reportFilters": [...]
    },
    "reportExtendedMetadata": {
      "detailColumnInfo": {...},
      "groupingColumnInfo": {...},
      "aggregateColumnInfo": {...}
    },
    "droppedKeys": {
      "reportMetadata": ["useNormalizedFieldForCurrency"],
      "reportExtendedMetadata": [],
      "top": ["reportTypeMetadata", "attributes"]
    }
  },
  "objects": {
    "Opportunity": {
      "name": "Opportunity",
      "label": "商談",
      "custom": false,
      "fields": [
        {
          "name": "StageName",
          "label": "フェーズ",
          "type": "picklist",
          "custom": false,
          "referenceTo": [],
          "relationshipName": null,
          "picklist": ["Prospecting", "Qualification", "ClosedWon"],
          "picklistTotal": 4
        }
      ]
    },
    "Account": { "...": "同じ形の関連オブジェクト describe" }
  },
  "column_map": [
    {
      "列キー": "Opp.Account",
      "表示名": "取引先名",
      "対応フィールドAPI名": "AccountId",
      "型": "reference",
      "備考": ""
    }
  ],
  "warnings": []
}
```

`report` に残す `reportMetadata` のキー（ SOQL 組立に必要なものだけ ）:

| キー | 用途（ SOQL ） |
|---|---|
| `id` / `name` | レポート ID と名前 |
| `reportType` / `reportFormat` / `scope` | レポートの種別・形式・スコープ |
| `detailColumns` | SELECT する列 |
| `reportFilters` / `reportBooleanFilter` | WHERE 条件 |
| `standardDateFilter` / `standardFilters` | 日付条件・標準フィルタ |
| `crossFilters` | サブクエリ |
| `groupingsDown` / `groupingsAcross` | GROUP BY |
| `aggregates` | 集計 |
| `sortBy` | ORDER BY |
| `topRows` | LIMIT |
| `historicalSnapshotDates` / `buckets` | 履歴 / 独自グループ |
| `customSummaryFormula` | 独自計算式 |
| `division` | 事業部門 |
| `hasDetailRows` | 詳細行の有無 |

`reportExtendedMetadata` に残すキーは `detailColumnInfo` /
`groupingColumnInfo` / `aggregateColumnInfo` の 3 つだけです（ 列の表示情報 ）。

`droppedKeys` の意味: レポート describe で**落としたキーの名前**が、
サブキー 3 つ（ `reportMetadata` / `reportExtendedMetadata` / `top` ）に
**出現順**で入ります。 `reportMetadata` から落としたキーが `reportMetadata` に
入り、 トップレベルから落としたキーが `top` に入ります（ どちらも
**入力に存在したキーだけ** ）。 1 つも落ちていないときはそれぞれ空リスト。
最初の実行で `droppedKeys` を見て、 「 必要なキーを落としていないか 」 を
確認してください。

- `主オブジェクト` が `null` のときは、 そのレポートの主オブジェクトの
  describe は取れなかった（ `warnings` に理由が残る）
- `objects` のキーは主オブジェクト + 関連オブジェクト（ `[LIMITS] RELATED_MAX`
  を超えると一部は `warnings` に名前だけ残る）
- `column_map` の `対応フィールドAPI名` が `"(不明)"` のものは、 表示名からは
  自動対応できなかった列

### `対応表_{管理番号}.csv` / `対応表.csv` （AI に渡す列対応）

1 行がレポートの 1 列に対応します。 AI に貼るのはこの CSV が一番楽です。

| 列 | 中身 |
|---|---|
| `管理番号` | JSON の `管理番号` |
| `概要` | JSON の `概要` |
| `レポートID` | JSON の `レポートID` |
| `レポートタイプ` | `report.reportMetadata.reportType.type` |
| `主オブジェクト` | JSON の `主オブジェクト` |
| `列キー` | `column_map` の `列キー` |
| `表示名` | `column_map` の `表示名` |
| `対応フィールドAPI名` | `column_map` の `対応フィールドAPI名` |
| `型` | `column_map` の `型` |
| `参照先オブジェクト` | 対応フィールドが参照項目のとき、 `referenceTo` を `|` 区切り |
| `リレーション名` | 同 `relationshipName` |
| `備考` | `column_map` の `備考` |

### `項目表.csv` （AI に渡すオブジェクトの項目表）

1 行が 1 つの項目。 AI に「どのフィールドが使えるか」を聞きたいときに。

| 列 | 中身 |
|---|---|
| `オブジェクト` | オブジェクトの API 名 |
| `オブジェクト表示名` | describe の `label` |
| `項目API名` | `name` |
| `項目表示名` | `label` |
| `型` | `type` |
| `参照先オブジェクト` | 参照項目なら `referenceTo` を `|` 区切り |
| `リレーション名` | `relationshipName` |
| `カスタム` | カスタム項目は `○` |
| `選択肢` | 選択肢のうち `active` のもの（30 件超なら末尾に `…`） |

## 4. AI に SOQL を組んでもらう手順

1. `python main.py fetch 1001` を実行する
2. 出力先（既定 `./output`）の `対応表.csv` と `項目表.csv` を、 チャットに
   そのまま貼り付ける
3. 「管理番号 1001 のレポートを SOQL にして」と頼む
4. AI が出した SOQL で「列が足りない」「条件が分からない」と AI が
   言い出したら、 該当する管理番号の `{管理番号}.json` の該当部分だけ
   追加で貼る
5. AI が出した SOQL は、 本番で実行する前に人が確認する
   （ 組織の SOQL には 2000 行のレスポンス上限があるなど、 自動で全部が
   取れるわけではない。 条件を狭めるか分割実行を検討する ）

## 5. 対応表の限界

- レポート列の **表示名と、 項目の表示名が一致したもの**だけが自動で
  `対応フィールドAPI名` に埋まる。 それ以外は `"(不明)"` のまま残る。
  そのような JSON は `{管理番号}.json` の `column_map` を直接見て判断する
- 集計（ `SUMMARY` / `MATRIX` ）やグルーピングつきのレポートは、 対応表だけ
  では SOQL の SELECT / HAVING を完全には再現できない。 その場合も
  `{管理番号}.json` の `report` を見ながら組み立てる
- `項目表.csv` の `選択肢` は 30 件で切っている（ `…` で省略を表現）。
  30 を超えるリスト項目は `{管理番号}.json` の `objects` → 該当オブジェクト
  → `fields` → `picklist` / `picklistTotal` を直接見る（ JSON には元
  describe ではなく、 active な値だけが **`picklist`** に入っている。
  後ろに省略された件数は **`picklistTotal`** で分かる ）
