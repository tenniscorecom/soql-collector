# 使い方

Salesforce のレポート describe を管理番号ごとにとってメモリに保持し、 人が
Excel で見る ``SOQL調査.xlsx`` と、 ダウンローダー用の ``列名の対応.csv`` 、
AI に貼る ``SOQL資料/{管理番号}.md`` を作るツールです。

完成形 （2026-10-15） ：

| ファイル | 役割 | 人がすること |
|---|---|---|
| `output/SOQL調査.xlsx` | 見る（3 シート: 一覧 / 列の対応 / 関係図） | 見るだけ（毎回作り直す） |
| `output/SOQL資料/{管理番号}.md` | AI に貼る資料 | これ 1 つを AI に貼る |
| `input/列の直し.xlsx` | 直す場所 | 直すのはここだけ |
| `output/列名の対応.csv` | ダウンローダー用 | 触らない（形式は今のまま。契約） |
| `data/項目定義.csv` | キャッシュ | 触らない |

## 典型的な流れ

1. ``実行.bat`` を実行 （引数なし）
2. ``output/SOQL調査.xlsx`` の **一覧** シートを開く（1 レポート 1 行）
3. 一覧の **要対応・要確認の列数** が 1 以上の行の **管理番号** を覚える
4. **列の対応** シートで該当の管理番号の **要対応**（薄い赤） / **要確認**
   （薄い黄） の行を確認する
5. ``input/列の直し.xlsx`` を開き、 **直したSOQL列名** 列に値を入れる
   （自動で取れた列を上書きしたいときもここを使う）
6. もう一度 ``実行.bat`` を実行
7. ``output/SOQL資料/{管理番号}.md`` を AI に貼って SOQL を組み立ててもらう

途中で 「自動が取った列を上書きしたい」 ときも ``input/列の直し.xlsx``
の **直したSOQL列名** 列に値を入れれば、 次の実行で人の値が必ず優先される。
``直したSOQL列名`` と **メモ** のセルはツール側で絶対に上書きしない。

## 1. 初回準備

1. ``config.ini.example`` を ``config.ini`` にコピーする（ 実体の ``config.ini``
   は ``.gitignore`` 済み ）
2. ``config.ini`` のキーを必要に応じて書き換える。 ``[FILES]`` ``[SURVEY]``
   ``[PII]`` の **すべてのキーが必須** 。 キーが足りないと comken の
   ``ConfigError`` で止まる（既定値での補完はしない）。 値はあるけれど
   不正なときも ``ConfigError`` で止める
3. comken の親ディレクトリ（既定 ``F:\dev``） を ``PYTHONPATH`` に
   含めるか、 同梱の ``実行.bat`` を使う（ ``実行.bat`` は ``PYTHONPATH``
   を代行してくれる ）

### `[FILES]` のキー

| キー | 値の例 | 意味 |
|---|---|---|
| `MASTER_XLSX_PATH` | `./input/レポート管理表.xlsx` | レポート管理表（Excel）。 管理番号 / 概要 / Salesforce URL / 有効 |
| `OUTPUT_DIR` | `./output` | 出力先（`SOQL調査.xlsx` / `列名の対応.csv` / `SOQL資料/` / `関係図/` を置く） |
| `DESCRIBE_CSV_PATH` | `./data/項目定義.csv` | オブジェクト describe のキャッシュ。 1 行 1 項目 |
| `COLUMN_FIX_XLSX_PATH` | `./input/列の直し.xlsx` | 人が直す xlsx。 詳細は「3. `input/列の直し.xlsx` の使い方」 |
| `XLSX_NAME` | `SOQL調査.xlsx` | `OUTPUT_DIR/` 配下に書く Excel ファイル名 |
| `MARKDOWN_DIR` | `SOQL資料` | `OUTPUT_DIR/` 配下に書く AI 向け Markdown のフォルダ名 |
| `DIAGRAM_DIR` | `関係図` | `OUTPUT_DIR/` 配下に書く Mermaid 関係図のフォルダ名 |

`列名の対応.csv` のファイル名は **ダウンローダーとの約束で固定** のため、
config からは外してある。 出力先は `OUTPUT_DIR/列名の対応.csv`。

### `[SURVEY]` のキー

| キー | 値の例 | 意味 |
|---|---|---|
| `RELATED_DEPTH` | `3` | 主オブジェクトから何段まで関連オブジェクトを掘るか。 `1` なら参照先 1 段だけ |
| `RELATED_MAX` | `40` | 関連オブジェクトの合計件数の上限。 超えた分は警告に名前が残る |
| `ROW_LIMIT_CHECK` | `○` | 1 レポートごとに 2000 件チェックを実行するか。 `×` だと 「2000件超」 列が 「未実施」 |
| `SIMILAR_COLUMN_THRESHOLD` | `0.8` | 似たレポート判定で 「近い」 とみなす Jaccard 類似度の下限。 0.0 〜 1.0 |

### `[PII]` のキー

| キー | 値の例 | 意味 |
|---|---|---|
| `KEYWORDS` | （`氏名, 名前, ...`） | 個人情報とみなすキーワード。 カンマ区切り |
| `PERSON_OBJECTS` | `Contact, Lead, User, Individual, PersonAccount` | 個人系オブジェクトの API 名。 カンマ区切り |

旧 config.ini に ``[LIMITS]`` / ``[SF]`` / ``[CHECKS]`` / ``[SIMILAR]`` /
``[OBJECTS]`` などのセクションが残っていても、 このツールは読まないので無視
される（そのまま残しておいて OK） 。

## 2. 実行

### 動かす

```bat
実行.bat
```

または

```powershell
python main.py
```

**引数は受け付けない**。 付けるとエラーで終了コード `2` が返る （ サブコマンドも
無い ） 。

### どのレポートが対象になるか

管理表の「有効」列が `○` のものすべて。 個別に取りたいときは、 その行だけ `○`
にして、 ほかを `×` にする。 「○」が 1 件も無いときは「管理表に『有効』が ○
の行がありません」と表示して終了コード `2` で終わる。

実行すると次の順で動きます。

1. 管理表を読んで対象エントリを決める（「有効」列が `○` の全件）
2. ID ごとに Salesforce へつなぎ、 レポート describe・主オブジェクト
   describe・関連オブジェクト describe・（`ROW_LIMIT_CHECK` が `○` のとき）
   レポート実行を取ってメモリ上の記録（`ReportRecord`） にする。 同時に
   **SOQL の下書き** を組み立て、 `一部作れず` のときは 1 行目に
   `【未完成】…` の印を入れる
3. `OUTPUT_DIR/` 配下へ
   - **`SOQL調査.xlsx`** （3 シート: 一覧 / 列の対応 / 関係図）
   - **`列名の対応.csv`** （ダウンローダー用）
   - **`SOQL資料/{管理番号}.md`** （1 レポート 1 Markdown）
   - **`関係図/{主オブジェクト}.md`** （主オブジェクト 1 つ 1 Markdown）
4. 失敗した ID は個別にスキップされ、 残りは続けて取得します。 Markdown
   も取れた record のぶんだけ上書きされ、 古い / 取れなかった分のファイルは
   消さない
5. 終了コードは「失敗が 1 件でもあれば `1`」、 全件成功なら `0`、 引数エラー
   や設定・対象の不足は `2`。 取れた record の xlsx / CSV を ``run_tables``
   で書き出すときに例外が出ても `1` を返す（出力の生成に失敗した）

### 単品で試す （`trial/`）

管理表を使わずにレポート 1 件だけ取りたいときは `trial/fetch_one_report.py`
の単品サンプルが使える。 出力は本体の `output/` ではなく `output/single/` に
隔離され、 本体 xlsx / csv にも混ざらない。

```
python -m trial.fetch_one_report <レポートのURL> [管理番号]
```

管理番号を省略すると既定 `sample`。 argparse が使い方（usage） を出して
`SystemExit(2)` するのは他の CLI と同じ。

`trial/` は **名前空間パッケージ** で、 `__init__.py` を **持たない** 。
`comken` のように `pythonpath` で後ろから `sys.path` に入るライブラリが
あっても pytest は特に sys.path 書き換えをせずにそのまま動く。

## 3. `input/列の直し.xlsx` の使い方

`[FILES] COLUMN_FIX_XLSX_PATH` （既定 `./input/列の直し.xlsx`） に **人が
Excel で開いて手で見比べる列の対応表** を書く。 自動の列対応
（`mapping.build_column_map`） では対応が取れない列や、 自動の対応が
間違っているときに使う。 **自動で取れた列を上書きしたいときも同じ** 。

- シート 1 枚、 Excel のテーブル 1 つ。 名前は ``ColumnFix``
- 列 （この順） ： 状態 / 主オブジェクト / 表示名 / 列キー / 自動のSOQL列名 /
  候補 / **直したSOQL列名** / メモ / 使っているレポート / 更新日
- 状態： `OK` （自動が取った・人が直した） / `要対応` （自動も人も取れず） /
  `要確認` （候補が複数、 人の値の型が引けない）
- 見栄え： 見出し行は 1 行目で固定、 列幅は全角=2・半角=1 で整え、 人が書く
  「直したSOQL列名」 と 「メモ」 の見出しセルは薄い緑、 状態=要対応の行は
  薄い赤、 状態=要確認の行は薄い黄で塗られる

**ルール**:

- 実行のたびに新しい列キーは行を追加、 既存行は `状態 / 表示名 / 自動のSOQL列名 /
  候補 / 使っているレポート / 更新日` を今回の値で書き換える
- **`直したSOQL列名` と `メモ` は絶対に書き換えない・消さない** （人の入力を尊重）
- **`直したSOQL列名` に値があれば、 自動で取れた列も人の値で上書きされる**
  （値が無い列も含めて、 人の値が `column_map` の `対応フィールドAPI名` に反映）
- 並び： 要対応 → 要確認 → OK、 その中は主オブジェクト → 列キー
- 書けない（PermissionError） ときは WARNING だけ出して他の出力は作る。
  読めない・見出し違いは ``ExcelError`` で止める （ファイルは変えない）
- 型を引けない値は状態=要確認、 値はそのまま使う

**移行**: 旧 `data/列の対応.csv` （メモ=手入力 かつ SOQL列名あり） がある
ときは、 「直したSOQL列名」に引き継ぐ。 旧ファイルは消さない。 件数をログに
出す。

**運用**:

1. ``実行.bat`` を 1 回動かす（``input/列の直し.xlsx`` が無いときは新規で作られる）
2. ``input/列の直し.xlsx`` を Excel で開く
3. **状態=要対応/要確認の行** を見て、 Salesforce の API 項目名に直す
   （例: `Account.Name`）。 自動で取れた列を上書きしたいときも、 `直したSOQL列名`
   に値を入れる
4. xlsx を保存して閉じる（Excel で開いていると書き込めないので注意）
6. もう一度 ``実行.bat`` を実行

## 4. `SOQL資料/{管理番号}.md` の構成

1 レポート 1 Markdown。 AI が SOQL を組むために、 次の節をこの順で含む:

| 節 | 中身 |
|---|---|
| `# {管理番号} {概要}` | タイトル |
| メタ 5 行 | レポートID / 主オブジェクト / レポート形式 / 2000件超 （件数付き） / 個人情報 |
| 先頭案内 | 「このファイルを丸ごと AI に貼ってください。 SOQL の下書きを、 下の資料と照らして直すよう頼みます」 |
| `## SOQL の下書き` | 状態（`作成済み` / `要確認` / `一部作れず` / `作れず`） ・SOQL 本文（```sql フェンス） ・AI への補い方 ・作れなかった部分の箇条書き ・要確認の箇条書き。 `一部作れず` の SOQL は本文の 1 行目に `【未完成】…` の印が残る |
| `## 列の対応` | 表示名 → 使う SOQL 列名・どこから・候補の表 |
| `## 絞り込み` | 組立式・絞り込みの表・日付 / 標準フィルタ / クロスフィルタ / 上位 N の箇条書き |
| `## 並び順` | `sortBy` を 1 行ずつ |
| `## グループ・集計` | TABULAR は 「なし」、 SUMMARY / MATRIX は 「SOQL では GROUP BY と集計関数で表すか、 明細を取って集計する」 の 1 行 + グループ・集計の箇条書き |
| `## 関連オブジェクトの経路` | 主オブジェクトから使われている経路だけを `Contact → Account（Account）→ Owner（User）` の形で |
| 関係図リンクと字下げツリー | `../関係図/{主オブジェクト}.md` への相対リンクと、 字下げの罫線で組んだ同じ木 （``` フェンスの中に） 。 図が無いときは出ない |
| `## SOQL を組むときの注意` | 取れなかった列 / 複数候補の列 / スコープが自分のレコード / 日時はタイムゾーンに注意 / 2000件超なので Bulk で取る / クロスフィルタはサブクエリ / 集計レポート のうち当てはまるものだけ |

毎回、 今回取れたレポート分だけ上書きする。 失敗した ID や取れなかった
レポートの古いファイルは **消さない** （パスが分かれば後から見られる） 。
UTF-8、 BOM なし、 改行 LF。

## 5. `SOQL調査.xlsx` の構成

**まず 一覧 シートを見る**。 1 行が 1 件のレポート。 そこから要対応の
あるレポートの 管理番号 を覚えて、 **列の対応** シートで掘りに行く。
**関係図** シートで主オブジェクト周りの構造を確認する。

**3 枚とも Excel のテーブル** （構造化） で、 列幅は全角=2・半角=1 で
計算して整え、 見出し行は固定される。 1 行目に案内文
（ 「 直すときは input/列の直し.xlsx の『直したSOQL列名』に書いて、
もう一度実行してください。 」 ） が出る。

### 一覧

1 行が 1 件のレポート。

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `主オブジェクト` | record の `main_object` |
| `SOQLの状態` | `作成済み` / `要確認` / `一部作れず` / `作れず` |
| `要対応・要確認の列数` | 「列の対応」シートで該当 管理番号 が状態=要対応/要確認 だった件数 |
| `2000件超` | `row_check.status` （`超えている` / `超えていない` / `判定不可` / `未実施`） |
| `行数` | `row_check.rows` が非 `None` のときだけ実際の行数 |
| `個人情報` | `pii.status` （`あり` / `要確認` / `なし`） |
| `個人情報の該当列` | `pii.matching_columns` を `表示名(根拠)` の `; ` 区切りで |
| `似たレポート` | 例 「グループ2: 1001が基準・条件のみ違い・条件を引数にして1本にできそう」 |
| `警告` | 件数と最初の 1 件の要約 |
| `SOQL資料` | `SOQL資料/{管理番号}.md` への相対パス（ハイパーリンク） |

### 列の対応

1 行 = 1 レポートの 1 列。

| 列 | 中身 |
|---|---|
| `状態` | `OK` / `要対応` / `要確認` |
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `表示名` | レポートの表示名 |
| `列キー` | レポートの列キー |
| `使うSOQL列名` | `column_map` の `対応フィールドAPI名` |
| `どこから` | `自動` / `人が直した` / `人が直した（要確認: たどれない）` / `取れず` |
| `候補` | 「複数候補あり」 のときの候補 |
| `自動の値` | 人が直して自動と違うときだけ、 自動で取れていた値 |

**要対応は薄い赤、 要確認は薄い黄** でセルが塗られる。

### 関係図

主オブジェクト単位の木。 主＋関連の **取れた** オブジェクト同士の
参照を木にして、 1 行 1 ノードで示す。 同じ主オブジェクトの record が
複数あれば、 `relations` がマージされて 1 ファイルにまとまる。
Mermaid 版は `OUTPUT_DIR/関係図/{主オブジェクト}.md` にも書く。

| 列 | 中身 |
|---|---|
| `主オブジェクト` | 木の根の API 名 |
| `段` | 主 = 0、 子は段階 +1 |
| `図` | 罫線で字下げした 1 行 |
| `行き先オブジェクト` | 子ノードの API 名 |
| `SOQLでの書き方` | 主オブジェクトからのリレーション名の鎖 `+.(項目)` |
| `参照項目API名` | その辺の参照項目 API 名 |

## 6. `列名の対応.csv` （ダウンローダー用）

ダウンローダー側は `(主オブジェクト, SOQL列名)` → 表示名 で `COLUMN_NAMES`
を組み立てる。 形式は **契約** で固定（ comken の
`comken.services.salesforce_downloader.contract` が正、 `load_sample()`
で見本を取得してバイト単位で比較 ） 。

| 列 | 中身 |
|---|---|
| `主オブジェクト` | record の `main_object` |
| `SOQL列名` | `column_map` の `対応フィールドAPI名` （解決できた列だけ） |
| `表示名` | 最多 （同数なら管理番号の小さいレポートのもの） 。 違う表示名が他にあれば 備考に「別の表示名あり:」 の形で並ぶ |
| `備考` | 別の表示名一覧 |
| `更新日` | 今回書いた日 （`YYYY-MM-DD`） |

- 1 行 = `(主オブジェクト, SOQL列名)` 。 管理番号の列は無い。
- **全レポート分を積み上げる**。 その回の実行で取得に成功した 管理番号 が
  解決した `(主オブジェクト, SOQL列名)` の行は今回の内容で入れ替わり、
  今回取らなかった / 失敗した 管理番号 由来の既存の行はそのまま残る。
  並べは `主オブジェクト → SOQL列名` 。
- 既存ファイルの見出しが想定と違うときは `CSVError` を上げ、 既存ファイル
  は変更しない。 「別名に退避してから再実行」 の対処が出る。

## 7. `data/項目定義.csv` の扱い

オブジェクト describe のキャッシュは `[FILES] DESCRIBE_CSV_PATH` （ 例:
`./data/項目定義.csv` ） に **UTF-8 BOM 付き + CRLF** の CSV で書かれる。
1 行 1 項目で、 1 オブジェクトの行は同じ取得日時。 組織の単位で区別される
ので、 本番と Sandbox が同じファイルに混ざっても取り違えない。

- **全部取り直したいとき**: ファイルを消す。 次の実行でまた API から取り直す
- **1 オブジェクトだけ取り直したいとき**: 該当 (組織 / オブジェクト) の行を消す
- **見出しが違う / 列数が壊れている** ときは、 ファイルを別名に退避してから
  再実行する。 退避せずもう一度実行すると `CSVError` で止まる

実行の終わりに INFO で `オブジェクトの describe: 保存データから N 件 /
Salesforce から N 件 / 取り直し N 件` のログが出る。

## 8. SOQL を組み立てる手順

このツールは **SOQL の下書き** を作ります（2026-10-15 復活、 安全策つき）。
状態は `作成済み` / `要確認` / `一部作れず` / `作れず` の 4 種。 `一部作れず`
のときは本文の 1 行目に `【未完成】…` の印が入り、 そのまま Salesforce に
投げると構文エラーになって実行できない。 必ず人が直すか、 印付きのものは
実行しないこと。 `作れず` は本文が空。

### そのまま使う場合

1. `実行.bat` を実行する
2. 出力先の `SOQL調査.xlsx` の **一覧** シートで状態を確認する
3. 状態が `作成済み` の SOQL はそのまま Salesforce で実行するか、 必要なら
   人が少し直す。 `要確認` は内容を見て直してから実行。 `一部作れず` /
   `作れず` は人が直すか、 このツールでは実行しない

### AI に Markdown を渡す場合

1. `実行.bat` を実行する
2. 出力先（`[FILES] OUTPUT_DIR` で指定したフォルダ） の `SOQL資料/` を開く
3. 該当 管理番号 の `.md` を AI に貼る
4. 受け取った SOQL を **人が確認してから実行する**。 条件を狭めるか分割実行を
   検討する、 必要なら手書きで直す

## 9. 限界

- レポート列の **表示名と、 項目の表示名が一致したもの** が `対応フィールドAPI名`
  に自動で埋まる。 それでも一致しないときは、 関連オブジェクトの項目ラベルとも
  突き合わせる。 それでもダメなら `(不明)` のまま残る
- 表示名が `タスク: 作業会社名` / `取引先: 取引先名` のように `オブジェクト:
  項目名` の形をしているときは、 コロンの前を **オブジェクトの表示名** として
  扱い、 一致するオブジェクト（describe の `label` を正規化して比較） の
  項目表示名を採る。 主オブジェクトなら項目名、 関連なら主からのリレーション名
  の鎖 + 項目名 （鎖が複数あれば浅いもの、 同じ深さで複数なら候補） 。
  コロンの前に一致するオブジェクトが無ければ、 後ろだけで従来どおりの照合。
  コロン無しの表示名は従来どおり
- 列キーが `<主オブジェクト>.<経路>.<項目>` の形（ 例 `Contact.Account.Name` /
  `Contact.Retention__c.Status__c` ） であれば、 列キーから主オブジェクトと
  各列の SOQL 列名（ `Account.Name` / `Retention__r.Status__c` のように
  参照項目 API 名を経路の `relationshipName` に置き換えた形 ） を自動で取る
- 列キーが `FK_<参照先>.<残りの経路>` の形（ 例 `FK_Contact.Email__c` /
  `FK_$Contact.Email__c` ） の列は、 主オブジェクトの参照項目から
  `<参照先>` への `relationshipName` を取り、 残りは上記の列キーたどりと
  同じ流れで解いて `<relationshipName>.<残りの SOQL>` にする。 候補が複数
  あれば備考に最大 5 件並べて表示名照合には進まない
- このツールは SOQL の `SELECT` / `WHERE` / `HAVING` / `ORDER BY` を
  自動では組み立てない。 集計（`SUMMARY` / `MATRIX`） やグルーピング
  つきのレポートは `SOQL資料/{管理番号}.md` を AI に貼って組み立てる
- **レポートの行データ**（値そのもの） は **メモリ上で件数を数えるだけ** で、
  CSV / ログ / 警告 / 例外メッセージには絶対に出さない。 2000 件チェックで
  `get` が呼ばれても、 戻り値の長さを取るだけで 中身は触らない

## 10. 個人情報の判定について

判定は **機械的な目安** で、 最終判断は人が行う。 CSV とこのドキュメントに
そう明記する。 判定が曖昧なものは `要確認` / `判定不可` に倒す。

判定ルール（列単位）:

- `あり`
  - 項目の型が `email` / `phone` / `address` / `location`
  - 表示名または API 名がキーワードに一致 かつ 所属オブジェクトが
    個人系（ `[PII] PERSON_OBJECTS` の値、 または `Account` で `IsPersonAccount`
    項目を持つ ）
- `要確認`
  - キーワードに一致するが所属オブジェクトが個人系でない
  - 対応表で対応フィールドが引けなかった列
- 空 … 上のどれでもない

キーワード一致のさせ方は **単純な部分一致ではなく、 3 段階** で見る:

- **1 文字の日本語キーワード** （`姓` / `名`）: 表示名がキーワードと
  **完全一致** するときだけ一致 （前後の空白は除く）。 API 名には
  適用しない。 `商談名` は `名` に **当たらない**
- **ASCII キーワード** （ `email` / `phone` / `city` / `state` / `zip` /
  `fax` / `birth` / `gender` / `mobile` / `street` / `postal` ）:
  API 名・表示名を **トークン** に分解 （ `_` / `__c` / 空白 /
  camelCase の切れ目 `BillingCity` → `Billing` `City` / 数字との切れ目 ）
  して、 いずれかのトークンがキーワードに **一致** するとき一致する。
- **上記以外の日本語キーワード** （2 文字以上）: 従来どおり
  **部分一致** （大文字小文字を無視）

`Account.Name` のように法人を表すオブジェクトの `Name` は キーワード
「氏名」 に一致しますが 個人系でないので `要確認` になる。 `Contact.Name`
は同じキーワード一致でも 個人系オブジェクトなので `あり` になる。

判定対象は レポートの **出力に出る列** だけ。 絞り込みにだけ使う列は
対象外（その列の値が出力されないので、 個人情報露出のリスクが低いため）。
