# 使い方

Salesforce のレポート describe を管理番号ごとにとってメモリに保持し、 人が
Excel で見る ``SOQL調査.xlsx`` と、 ダウンローダー用の ``列名の対応.csv``
を作るツールです。 JSON ファイルは作りません。

各レポートについて、 次の 4 つを機械的に判定して xlsx に出します（ **判定は
目安** で、 最終判断は人が行う。 曖昧なものは 「 要確認 」 / 「 判定不可 」 に
倒す ）：

1. 似たレポートをまとめられるか
2. 2000 件を超えているか
3. 個人情報を含むか
4. 取得できなかった項目は何か

**レポートの行データ**（ 個人情報を含みうる ） は **メモリ上で件数を数えるだけ** で、
CSV / ログ / 警告 / 例外メッセージには絶対に出さない。

**SOQL はこのツールでは組み立てない** （ 2026-10-14 撤去 ）。 代わりに
`OUTPUT_DIR/SOQL資料/{管理番号}.md` を AI に貼って組み立てる
（ もしくは `SOQL調査.xlsx` の `条件` `集計` `項目の対応` `項目一覧`
`関連` `一覧` シートを AI に渡す ）。 **必ず人が確認してから実行する** 。

カスタムレポートタイプのように `reportType.type` が主オブジェクトの API
名そのものではないとき、 列キーが `<主オブジェクト>.<経路>.<項目>` の
形（ 例 `Contact.Account.Name` / `Contact.Retention__c.Status__c` ）
であれば、 列キーから主オブジェクトと各列の SOQL 列名（ `Account.Name`
/ `Retention__r.Status__c` のように参照項目 API 名を経路の
`relationshipName` に置き換えた形 ） を自動で取る。 カスタムレポート
タイプのレポートタイプ自体の名前が分からなくても、 列キーの先頭を
集めて多い順に試して主オブジェクトを決める。 実物の列キーの形は未
確認のため、 結果の備考（ 「 列キーから 」 ） を見て人が確認する。

## 1. 初回準備

1. `config.ini.example` を `config.ini` にコピーする（実体の `config.ini` は
   `.gitignore` 済み）
2. `config.ini` の次のキーを必要に応じて書き換える。 `[FILES]` の 4 つの
   キーは **すべて必須** で、 どれか 1 つでも config.ini に無いと comken が
   `ConfigKeyNotFoundError` （ メッセージにキー名が出る ） で止まる

| セクション | キー | 意味 |
|---|---|---|
| `[FILES]` | `MASTER_XLSX_PATH` | レポート管理表（Excel）。**必須** |
| `[FILES]` | `OUTPUT_DIR` | 出力先。**必須**。 例: `./output` |
| `[FILES]` | `DESCRIBE_CSV_PATH` | オブジェクト describe を実行をまたいで貯める CSV。1 行 1 項目。組織 / オブジェクト / 項目 API 名 / 型 / 参照先 / リレーション名 / カスタム項目 / 絞り込み可 / 並べ替え可 / 選択肢 / 取得日時。レコードの値は入らない。**必須**。 例: `./data/項目定義.csv` |
| `[FILES]` | `COLUMN_MAP_CSV_PATH` | 人が Excel で開いて手で見比べる 列の対応表。 主オブジェクト / 列キー / 表示名 / SOQL列名 / メモ / 使っているレポート数 / 更新日 の 7 列。 自動の列対応で取れない列を人が直す。**必須**。 例: `./data/列の対応.csv` |

`[FILES]` の 4 つの**パスのみが** config.ini に書く値です。 次の 4 つの値は
**コードの定数** （ `src/` 配下の Python ファイル ） にあり、 config.ini に
書いても無視されます。 値を変えたいときはコードを直すか、 業務に合わせて
コミットで更新してください:

| 定数 | ファイル | 既定値 | 意味 |
|---|---|---|---|
| `RELATED_MAX` | `src/fetch.py` | `40` | 関連オブジェクト（参照先）の最大件数。**全段の合計**に対する上限 |
| `RELATED_DEPTH` | `src/fetch.py` | `3` | 関連オブジェクトを掘る最大の段数。 `1` なら参照先 1 段だけ （ 今までの挙動 ） |
| `ROW_LIMIT_ENABLED` | `src/fetch.py` | `True` | レポート 1 件ずつ実行して 2000 件超を判定するか。 `False` にすると 一覧 シートの `2000件超` 列が `未実施` になる |
| `DEFAULT_KEYWORDS` | `src/pii.py` | （ コード参照 ） | 個人情報判定に使うキーワード |
| `DEFAULT_PERSON_OBJECTS` | `src/pii.py` | `Contact, Lead, User, Individual, PersonAccount` | 個人系オブジェクト |
| `SIMILAR_COLUMN_SIMILARITY` | `src/run.py` | `0.8` | 似たレポート判定で 「 近い 」 とみなす Jaccard 類似度の下限。 0.0 〜 1.0 |

旧 config.ini に `[LIMITS]` / `[SF]` / `[CHECKS]` / `[PII]` / `[SIMILAR]` /
`[OBJECTS]` などのセクションが残っていても、 このツールは読まないので無視
されます （ そのまま残しておいて OK ）。

3. comken の親ディレクトリ（既定 `F:\dev`）を `PYTHONPATH` に含めるか、
   同梱の `実行.bat` を使う（ `実行.bat` は PYTHONPATH を代行してくれる）

## 2. 実行

### 動かす

```bat
実行.bat
```

または

```powershell
python main.py
```

**引数は受け付けない**。 付けるとエラーで終了コード `2` が返る （サブコマンドも
無い）。

### どのレポートが対象になるか

管理表の「有効」列が `○` のものすべて。 個別に取りたいときは、 その行だけ `○` にして、
ほかを `×` にする。 「○」が 1 件も無いときは「管理表に『有効』が `○ の行が
ありません」と表示して終了コード `2` で終わる。

実行すると次の順で動きます。

1. 管理表を読んで対象エントリを決める（ 「有効」列が `○` の全件）
2. ID ごとに Salesforce へつなぎ、 レポート describe・主オブジェクト
   describe・関連オブジェクト describe・（ `ROW_LIMIT_ENABLED` が `True` のとき ）レポート実行を
   取ってメモリ上の記録（`ReportRecord`）にする
3. `OUTPUT_DIR/` 配下へ **`SOQL調査.xlsx`** と **`列名の対応.csv`** と
   **`SOQL資料/{管理番号}.md`** を書く。 xlsx は 1 冊に 9 枚のシート、
   `SOQL資料/` は 1 レポート 1 Markdown
4. 失敗した ID は個別にスキップされ、 残りは続けて取得します。 Markdown
   も取れた record のぶんだけ上書きされ、 古い / 取れなかった分のファイルは
   消さない
5. 終了コードは「失敗が 1 件でもあれば `1`」、 全件成功なら `0`、
   引数エラーや設定・対象の不足は `2` です。

**SOQL は組み立てません。** `OUTPUT_DIR/SOQL資料/{管理番号}.md` を AI に
貼って組み立ててもらいます。

### RPA から呼ぶ例

社内 RPA 基盤から実行する場合は `実行.bat` を経由する。 終了コードは
`実行.bat` がそのまま返すので、 失敗があれば `1` で上がる。

```bat
実行.bat
```

**引数を付けるとエラー**（ 終了コード `2` ） になるので、 RPA から呼ぶときも
そのまま（ 引数なし ） で起動する。

### 単品で試す（ `trial/` ）

管理表を使わずにレポート 1 件だけ取りたいときは `trial/fetch_one_report.py`
の単品サンプルが使える。 出力は本体の `output/` ではなく `output/single/` に
隔離され、 本体 xlsx / csv にも混ざらない。

```
python -m trial.fetch_one_report <レポートのURL> [管理番号]
```

管理番号を省略すると既定 `sample`。 argparse が使い方（ usage ）を出して
`SystemExit(2)` するのは他の CLI と同じ。

1 件のサンプルでも `SOQL調査.xlsx` は作られる。

`trial/` は **名前空間パッケージ** で、 `__init__.py` を **持たない** 。
`comken` のように `pythonpath` で後ろから `sys.path` に入るライブラリが
あっても pytest は特に sys.path 書き換えをせずにそのまま動く。

## 3. `data/項目定義.csv` の扱い

オブジェクト describe のキャッシュは `[FILES] DESCRIBE_CSV_PATH` （ 例:
`./data/項目定義.csv` ） に **UTF-8 BOM 付き + CRLF** の CSV で書かれる。
1 行 1 項目で、 1 オブジェクトの行は同じ取得日時。 組織の単位 (プロジェクト
  の URL のネットロカ 小文字) で区別されるので、 本番と Sandbox が同じ
ファイルに混ざっても取り違えない。 列は `組織 / オブジェクト / オブジェクト
表示名 / カスタムオブジェクト / 項目 API 名 / 項目表示名 / 型 / 参照先 /
リレーション名 / カスタム項目 / 絞り込み可 / 並べ替え可 / 選択肢 / 取得日時`
の 14 列。 **レコードの値は入らない** （ describe 摘要を見ない ） 。

- **全部取り直したいとき**: ファイルを消す。 次の実行でまた API から取り直す
- **1 オブジェクトだけ取り直したいとき**: 該当 (組織 / オブジェクト) の行を消す
  （ 組織と他の API 名の組み合わせごとに、 ヘッダー込みで 1 オブジェクト分 ）。
  該当オブジェクトは次の実行で API から取り直される
- **見出しが違う / 列数が壊れている** ときは、 ファイルを別名に退避してから
  再実行する。 退避せずもう一度実行すると CSVError で止まる

実行の終わりに INFO で `オブジェクトの describe: 保存データから N 件 /
Salesforce から N 件 / 取り直し N 件` のログが出る。 取り直しは **CSV に
古い項目定義が残っていて列対応に `(不明)` が残り、 レポートで使ったオブジェクト
が CSV から読んだもののとき** に API で取り直して 1 度だけレポートを再計算する
動作。 同じ `(組織, オブジェクト)` は 1 回の実行で 1 度しか取り直さない。

## 4. `data/列の対応.csv` の使い方

`[FILES] COLUMN_MAP_CSV_PATH` （ 例: `./data/列の対応.csv` ） に **人が
Excel で開いて手で見比べる列の対応表** を書く。 自動の列対応
（ `mapping.build_column_map` ） では対応が取れない列や、 自動の対応が
間違っているときに使う。

列は次の 7 列（ この順 ）：

| 列 | 中身 |
|---|---|
| `主オブジェクト` | `record.main_object` |
| `列キー` | レポートの列キー（ `Opp.Name` / `Account.OwnerId` など ） |
| `表示名` | レポートの表示名 |
| `SOQL列名` | 自動が取れなかった列を人が直すセル。 空のままでも、 自動が取れるようになれば自動の結果で埋められる |
| `メモ` | 自動が取れなかった理由や、 人が手で入れた印 （ `手入力` ） 。 自動が取れたら空に戻る |
| `使っているレポート数` | 自動が毎回書き換える。 今回の実行で出たレポート数 |
| `更新日` | 自動が毎回書き換える。 `YYYY-MM-DD` |

**運用:**

1. `実行.bat` を 1 回動かす（ 手動で作った CSV が無いときは新規で作られる ）
2. 出力先の `data/列の対応.csv` を Excel で開く
3. **自動で取れなかった列** （ `SOQL列名` が空の行 ） を見て、 Salesforce の
   API 項目名に直す（ 例: `Account.Name` ）。 `メモ` も手作業で書いてよい。
   自動で取れた列は触らない （ 次の実行で自動の結果で上書きされる ）
4. CSV を保存して閉じる（ Excel で開いていると書き込めないので注意 ）
5. もう一度 `実行.bat` を実行する。 **手で入れるのは自動で取れなかった列
   だけ** 。 自動で取れるようになった列は自動の結果で上書きされ、 置き換え
   は WARNING としてログに出る

**人が書いた SOQL列名 （ 例: `Account.Owner.Name` ） の経路上に、 その
レポートで掘った範囲 （ コードの定数 `RELATED_DEPTH` / `RELATED_MAX` ） の
外にあるオブジェクト （ 例: `User` ） があっても、 そのレポートの接続と組織で
次に取りに行く。 経路は 5 段まで。 6 段以上なら WARNING （ 「 経路が長すぎ
ます」 ） で止める。 たどれないときは WARNING が 「 どこで切れたか 」 を出す
（ 例: `… — 「Ownr」が Account に見つかりません（リレーション名の候補: …）` ） ので、
候補を見て SOQL列名を直す。

**自動で取れた列は、 人の値より自動の結果が正しい** という方針。 前回の実行で
手で入れた値が残っていても、 次に自動で取れた時点で自動の結果で置き換わる。

**列キーが `<主オブジェクト>.<経路>.<項目>` の形** （ 例: `Contact.Account.Name` ）
**の列は、 表示名の一致を待たずに自動で SOQL 列名が決まる**。 列キーの先頭
から主オブジェクトの `fields` を 1 段ずつ `relationshipName` → `name` の順で
突き合わせ、 経路上のオブジェクトはレポートの接続と組織で次に取りに行く。
SOQL の経路は参照項目の `relationshipName` に置き換える （ 例:
`Contact.Retention__c.Status__c` → `Retention__r.Status__c` ）。 経路は
5 段まで、 6 段以上なら WARNING。 備考は「 列キーから 」 になる。 列キーが
`<主オブジェクト>.` で始まらない・たどれなかった列は、 既存の表示名照合に
任せる。 カスタムレポートタイプのように `reportType.type` の describe が
通らないときは、 列キーの先頭を多い順に最大 5 個試して主オブジェクトを
決める （ 2026-10-14 ） 。 実物の列キーの形は未確認。

**列キーが `FK_<参照先>.<残りの経路>` の形** （ 例: `FK_Contact.Email__c`
/ `FK_$Contact.Email__c` ） **の列は、 主オブジェクトの参照項目から
`<参照先>` への `relationshipName` を取り、 残りは上記の列キーたどりと
同じ流れで解いて `<relationshipName>.<残りの SOQL>` にする**。 備考は
「 FK_ から 」 。 参照項目が 2 件以上あり経路が解ける候補が複数あれば、
「 複数候補あり: Contact__r.Email__c（Contact__c） / Sub_Contact__r.Email__c（Sub_Contact__c） 」
の形で最大 5 件並べて表示名照合には進まない。 経路が解けない /
`<参照先>` への参照が主に無い / 対象の項目定義が取得できないときは
失敗理由を備考に持って表示名照合へフォールバック。 `FK_` で始まっても
残りに `.` を含まないもの （ 例: `FK_NAME` ） は対象外のままで、 既存の
表示名照合に任せる （ 2026-10-14 ） 。 主オブジェクトの代替候補を列キー
の接頭辞から集める段階では `FK_` 始まりのキーは対象外。

既存ファイルの見出しが違う （ 旧形式 `管理番号, 概要, SOQL列名, ...` を含む ）
ときは `CSVError` で止まり、 ファイルは変更されない。 「 別名に退避してから
再実行 」 の対処が出る。

## 5. 出力ファイルの読み方

`OUTPUT_DIR` には次の 3 種類が置かれる。 役割分担は次のとおり:
  - `SOQL資料/{管理番号}.md` … **AI に貼る** Markdown
  - `SOQL調査.xlsx` … 人が一覧で見る
  - `data/列の対応.csv` … 人が手で直して再実行に使う
  - `列名の対応.csv` … ダウンローダーが読む

### `SOQL資料/{管理番号}.md` の構成

1 レポート 1 Markdown。 AI が SOQL を組むために、 列定義・絞り込み・集計・
並び順・関連オブジェクトの経路を **Markdown 表** で出す。 UTF-8、 BOM なし、
改行 LF。

毎回、 今回取れたレポート分だけ上書きする。 失敗した ID や取れなかった
レポートの古いファイルは **消さない** （ パスが分かれば後から見られる ） 。

節（この順）:

| 節 | 中身 |
|---|---|
| `# {管理番号} {概要}` | タイトル |
| メタ 5 行 | レポートID / 主オブジェクト / レポート形式 / 2000件超 （ 件数付き ） / 個人情報 |
| `## 出力する列` | detailColumns の順、 4 列 （ 表示名 / SOQL列名 / 型 / 備考 ） の表。 解決できなかった列は SOQL列名が `(不明)` で 備考に理由や候補がそのまま入る |
| `## 絞り込み` | 組立式 （ `` `1 AND (2 OR 3)` `` のインライン ） 、 絞り込みの表 （ 番号 / 表示名 / SOQL列名 / 演算子 / 値 ） 、 日付 / 標準フィルタ / クロスフィルタ / 上位N の箇条書き。 無ければ 「 なし 」 |
| `## 並び順` | `sortBy` を 1 行ずつ |
| `## グループ・集計` | TABULAR は 「 なし 」、 SUMMARY / MATRIX は 「 SOQL では GROUP BY と集計関数で表すか、 明細を取って集計する 」 の 1 行 + グループ・集計の箇条書き |
| `## 関連オブジェクトの経路` | 主オブジェクトから使われている経路だけを `Contact → Account（Account）→ Owner（User）` の形で |
| `## SOQL を組むときの注意` | 取れなかった列 / 複数候補の列 / スコープが自分のレコード / 日時はタイムゾーンに注意 / 2000件超なので Bulk で取る / クロスフィルタはサブクエリ / 集計レポート のうち当てはまるものだけ |

### `SOQL調査.xlsx` の構成

**まず 一覧 シートを見る**。 1 行が 1 件のレポート。 「 2000件超 」 「 個人情報 」
「 似たレポート 」 「 統合の見込み 」 「 取得できなかった項目数 」 「 警告数 」
を機械判定した結果が出る。 そこから問題のあるレポートの 管理番号 を覚えて、
該当行を掘りに行く。

シートの並び （ この順 ） ：

1. 一覧
2. 取得できなかった項目
3. 項目の対応
4. 条件
5. 集計
6. 似たレポート
7. 警告
8. 項目一覧
9. 関連

ヘッダー行は太字で固定される。 シート名で意味の分かる日本語名になっていて、
番号は付いていない。

#### 一覧

1 行が 1 件のレポート。 「 **まずここを見る** 」 シート。

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `レポートID` | record の `report_id` |
| `レポートタイプ` | `record.report["reportMetadata"]["reportType"]["type"]` |
| `主オブジェクト` | record の `main_object` （ 取得失敗などで特定できなかったときは `(不明)` ） |
| `形式` | `record.report["reportMetadata"]["reportFormat"]` |
| `出力列数` | 出力に出る列の数 （ detailColumns + groupings + 集計対象 ） |
| `2000件超` | `row_check.status` （ `超えている` / `超えていない` / `判定不可` / `未実施` ） |
| `行数` | `row_check.rows` が非 `None` のときだけ実際の行数 |
| `2000件超の補足` | `row_check.reason` |
| `個人情報` | `pii.status` （ `あり` / `要確認` / `なし` ） |
| `個人情報の該当列` | `pii.matching_columns` を `表示名(根拠)` の `; ` 区切りで最大 10 件 |
| `類似グループ` | 該当のグループの番号、 `基準` なら `<番号> (<基準の管理番号> 基準)` |
| `統合の見込み` | グループ内の統合の見込み |
| `取得できなかった項目数` | 「 取得できなかった項目 」 シートで該当 管理番号 が含まれていた件数 |
| `警告数` | `record.warnings` のうち 「 取得できなかった項目 」 シートに行かなかった件数 （ = describe 失敗以外の警告 ） |

#### 取得できなかった項目

| 列 | 中身 |
|---|---|
| `種別` | `項目` または `オブジェクト` |
| `主オブジェクト` | record の `main_object` （ `項目` ） または オブジェクト名 （ `オブジェクト` ） |
| `列キー` | `項目` のときのレポート列キー （ `オブジェクト` のときは空 ） |
| `表示名` | `項目` のときのレポートの表示名 （ `オブジェクト` のときは空 ） |
| `理由` | `項目` のときの理由 （ 「 列キーから 」 / 「 FK_ から 」 / 「 表示名一致せず 」 / 「 関連オブジェクト経由 」 / 「 複数候補あり: Name（Opportunity 商談名） / Account.Name（Account 取引先名） 」 / 「 同じレポート内で表示名が重複 」 ） または `オブジェクト` のときの describe 失敗の理由 |
| `件数` | 何レポートで該当したか （ 同じ `(主オブジェクト, 列キー, 理由)` が複数レポートにあればここに積まれる ） |
| `管理番号` | 該当した 管理番号 を `|` 区切りで |

並びは 件数 ( 降順 ) → 種別 → 主オブジェクト → 列キー。

#### 項目の対応

`column_map` のうち、 `対応フィールドAPI名` が解決できた列を **全体で 1 行ずつ**
にまとめた表。 1 行 = `(主オブジェクト, SOQL列名)` で、 同じ `(主, SOQL列名)`
は 1 行に集約される。 「 取得できなかった項目 」 シート ( 解決できなかった列 )
はここには出ない。

| 列 | 中身 |
|---|---|
| `主オブジェクト` | record の `main_object` |
| `SOQL列名` | `column_map` の `対応フィールドAPI名` |
| `表示名` | 最多 （ 同数なら管理番号の小さいレポートのもの ） 。 異なる表示名があれば 備考に「 別の表示名あり: 」 の形で並ぶ |
| `型` | `column_map` の `型` |
| `参照先オブジェクト` | 参照項目のとき `referenceTo` を `|` 区切り |
| `個人情報` | 出力列について機械判定した PII 結果。 `あり` / `要確認` / 空 |
| `個人情報の根拠` | 判定理由。 `型 email` / `キーワード『電話』` 等 |
| `使っているレポート数` | 何レポートで該当したか |
| `管理番号` | 該当した 管理番号 を `|` 区切りで |
| `備考` | 別の表示名一覧 （ 「 別の表示名あり: 顧客名（1002）, 顧客氏名（1003）」 等 ） |

並びは 主オブジェクト → SOQL列名。

#### 条件

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `レポートID` | record の `report_id` |
| `種別` | `絞り込み` / `組立式` / `日付` / `標準フィルタ` / `クロス` / `上位N` |
| `番号` | 種別ごとの連番 （ `絞り込み` なら `1` から ） |
| `列キー` | 絞り込み列キー （ `絞り込み` ） または 日付列キー （ `日付` ） |
| `項目` | column_map で解決した SOQL 名 （ `絞り込み` のときに埋まる、 解決できなければ空 ） |
| `演算子` | 絞り込み演算子 |
| `値` | 絞り込み値、 組立式なら `1 AND (2 OR 3)` のまま、 日付なら `開始〜終了`、 クロスなら `primaryEntityField operator relatedEntity.relatedEntityJoinField (criteria)` |
| `備考` | 種別ごとの補足 （ 例: 日付の `durationValue` ） |

#### 集計

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `レポートID` | record の `report_id` |
| `種別` | `形式` / `グルーピング(行)` / `グルーピング(列)` / `集計` / `並び順` / `バケット` / `独自計算式` |
| `順` | 種別ごとの連番 |
| `名前` | 集計式やグルーピング名 |
| `内容` | 並び順やバケット値、 独自計算式のラベルなど |

#### 似たレポート

似たレポートを同じグループにまとめて、 1 ペア 1 行で 「 区分 」 と
「 基準との違い 」 を出したもの。 グループに入らなかったレポートは出ない。

| 列 | 中身 |
|---|---|
| `類似グループ` | グループ番号 |
| `管理番号` | この行のレポートの管理番号 |
| `概要` | この行のレポートの概要 |
| `レポートID` | この行のレポートの ID |
| `基準の管理番号` | グループの基準（ 最小の管理番号 ） のレポート |
| `区分` | `基準`（ 基準自身の行 ） / `同一` / `条件のみ違い` / `列のみ違い` / `近い` |
| `基準との違い` | 区分が `基準` 以外なら 人が読める 1 文。 例: `値: AMOUNT greater 100 → 200`、 `追加: STAGE equals Closed`、 `出力列の類似度 0.85` |
| `統合の見込み` | `1本にまとめられる` / `条件を引数にして1本にできそう` / `要確認` のいずれか。 区分 `基準` の行は空 |

該当グループが無ければ シートは見出しだけになる （ 0 件のデータ行 ）。

判定のロジック:

- **同一** … 構造 （ レポートタイプ・形式・出力列・グルーピング・集計・並び順 ）
  も同じで 条件（ 絞り込み・組立式・日付・標準フィルタ・クロス・上位 N・ scope ）
  も同じ。 ID 違いで 1 本にまとめられる
- **条件のみ違い** … 構造は同じで 条件が違う
  - 値だけ違う（ 同じ列キー・同じ演算子で値だけ ） / 日付の範囲だけ違う →
    `条件を引数にして1本にできそう`
  - その他 → `要確認`
- **列のみ違い** … 条件は同じで 出力列の集合が違う
  （ 片方がもう片方を含むときは 「 含む 」 と diff_text に書く ）
  → 統合の見込みは `要確認`
- **近い** … 上のどれにも当たらないが、 出力列の Jaccard 類似度が
  コードの定数 `SIMILAR_COLUMN_SIMILARITY` （ 既定 0.8 ） 以上
  → 統合の見込みは `要確認`

#### 警告

取得中に出た警告のうち、 **describe 失敗を除いた**もの。 describe 失敗は
「 取得できなかった項目 」 シートの `種別=オブジェクト` に行くので、 警告
シートには残らない。 2000 件チェックで `判定不可` だったときの理由もここに出る
（ 機微な情報は含めない ）。

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `レポートID` | record の `report_id` |
| `警告` | 1 警告 1 行 （ 例: 「 関連オブジェクトが 50 件あり上限 40 を超えたため、 次の 10 件は取得しません: … 」 ） |

#### 項目一覧

1 行が 1 つの項目。 AI に「どのフィールドが使えるか」を聞きたいときに。

| 列 | 中身 |
|---|---|
| `オブジェクト` | オブジェクトの API 名 |
| `段` | 主オブジェクトは `0`、 関連は record 内の `relations` の段 （ `1` / `2` / … ） |
| `オブジェクト表示名` | describe の `label` |
| `項目API名` | `name` |
| `項目表示名` | `label` |
| `型` | `type` |
| `参照先オブジェクト` | 参照項目なら `referenceTo` を `|` 区切り |
| `リレーション名` | `relationshipName` |
| `カスタム` | カスタム項目は `○` |
| `選択肢` | 選択肢のうち `active` のもの（30 件超なら末尾に `…`） |

並びは「 オブジェクト API 名の昇順 → describe の `fields` の並び順 」。

#### 関連

1 行が主＋関連の **取れた** オブジェクト同士の親→子の参照 1 本。

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `親オブジェクト` | 親オブジェクト API 名 |
| `参照項目API名` | 参照項目の API 名 |
| `リレーション名` | 参照項目の `relationshipName` |
| `子オブジェクト` | 子オブジェクト名 |
| `段` | **子の** 深さ （ 主 = 0 ） |

並びは **管理番号 → 段 → 親の出現順**。 上限で打ち切られた子・ describe 取得
に失敗した子はここにも出ない （ 項目一覧にも出ない ）。 ポリモーフィック参照は
`referenceTo` のエントリごとに 1 行ずつ。

### `列名の対応.csv` （ダウンローダー用）

ダウンローダー側は `COLUMN_NAMES = {"Amount": "金額", "Account.Name": "取引先名"}`
を各 SoqlReport に貼る （ キー = SOQL 結果の列名、 値 = 出力 CSV の見出し ）。
それを組み立てる材料。

| 列 | 中身 |
|---|---|
| `主オブジェクト` | record の `main_object` |
| `SOQL列名` | record の `column_map` の `対応フィールドAPI名` （ 解決できた列だけ ） |
| `表示名` | 最多 （ 同数なら管理番号の小さいレポートのもの ） 。 違う表示名が他にあれば 備考に「 別の表示名あり: 」 の形で並ぶ |
| `備考` | 別の表示名一覧 |
| `更新日` | 今回書いた日 （ `YYYY-MM-DD` ） |

- 1 行 = `(主オブジェクト, SOQL列名)` 。 管理番号の列は無い。
- **全レポート分を積み上げる**。 その回の実行で取得に成功した 管理番号 が
  解決した `(主オブジェクト, SOQL列名)` の行は今回の内容で入れ替わり、
  今回取らなかった／失敗した 管理番号 由来の既存の行はそのまま残る。
  並べは `主オブジェクト → SOQL列名` 。
- 既存ファイルの見出しが想定と違う （ 旧形式の `管理番号, 概要, SOQL列名,
  表示名, 備考` を含む ） ときは `CSVError` を上げ、 既存ファイルは変更
  しない。 「 別名に退避してから再実行 」 の対処が出る。
- `OUTPUT_DIR` は **ダウンローダーが読む場所** （ ダウンローダーの共有
  フォルダの `soql-collector` フォルダ ） にしておくと、 ダウンローダーは
  そのまま `列名の対応.csv` を `(主オブジェクト, SOQL列名)` で引いて使える。

## 6. SOQL を組み立てる手順

このツールは SOQL を組み立てません。 代わりに、 出力した
`OUTPUT_DIR/SOQL資料/{管理番号}.md` を AI に貼って組み立てる
（ もしくは `SOQL調査.xlsx` のシートを AI に渡す ）。 **必ず人が確認してから
実行する** 。

### AI に Markdown を渡す場合

1. `実行.bat` を実行する
2. 出力先（ `[FILES] OUTPUT_DIR` で指定したフォルダ ） の `SOQL資料/` を開く
3. 該当 管理番号 の `.md` を AI に貼る
4. 受け取った SOQL を **人が確認してから実行する**。 条件を狭めるか分割実行を
   検討する、 必要なら手書きで直す

`SOQL資料/{管理番号}.md` は次の節をこの順で含む:

- タイトル `# {管理番号} {概要}`
- メタ 5 行 （ レポートID / 主オブジェクト / レポート形式 / 2000件超 / 個人情報 ）
- `## 出力する列` 明細の列だけ。 detailColumns の順。 解決できなかった列は
  `SOQL列名` が `(不明)` で `備考` に理由がそのまま入る
- `## 絞り込み` 組立式 → 絞り込み表 → 日付 / 標準フィルタ / クロス / 上位N の
  箇条書き。 当てはまらなければ 「 なし 」
- `## 並び順` `sortBy` の列挙
- `## グループ・集計` TABULAR は 「 なし 」、 SUMMARY / MATRIX は
  GROUP BY のヒントと行 / 列グループ・集計の箇条書き
- `## 関連オブジェクトの経路` 主オブジェクトから使われている関連への
  `Contact → Account（Account）→ Owner（User）` 形式の表示
- `## SOQL を組むときの注意` 取れなかった列 / 複数候補 / scope / 日時 /
  2000件超 / クロスフィルタ / 集計レポート のうち当てはまるものだけ

### xlsx を AI に渡す場合 （ 旧手順 ）

1. `実行.bat` を実行する
2. 出力先（ `[FILES] OUTPUT_DIR` で指定したフォルダ ） の `SOQL調査.xlsx` を
   Excel で開く
3. まず `一覧` シートで対象 管理番号 を特定する
4. AI に次のシートをまとめて渡し、 SOQL を組み立ててもらう:
   `条件` / `集計` / `項目の対応` / `項目一覧` / `関連` / `一覧`
   （ `主オブジェクト` `列キー` `対応フィールドAPI名` などがそのまま使えます ）
5. 受け取った SOQL を **人が確認してから実行する**

## 7. 限界

- レポート列の **表示名と、 項目の表示名が一致したもの** が `対応フィールドAPI名`
  に自動で埋まる。 それでも一致しないときは、 関連オブジェクトの項目ラベルとも
  突き合わせる。 それでもダメなら `(不明)` のまま残る。 そのような record は
  「 取得できなかった項目 」 シートを見る
- このツールは SOQL の `SELECT` / `WHERE` / `HAVING` / `ORDER BY` を
  自動では組み立てない （ 2026-10-14 撤去 ）。 集計（ `SUMMARY` / `MATRIX` ）
  やグルーピングつきのレポートは `条件` `集計` シートを見ながら人が組み立てる
- `項目一覧` シートの `選択肢` は 30 件で切っている（ `…` で省略を表現 ）。
  30 を超えるリスト項目は `項目一覧` の `picklist` を確認すること （ active
  な値だけが **`picklist`** に入っており、 後ろに省略された件数は
  **`picklistTotal`** で分かる ）
- `関連` シートに出るのは **取れたオブジェクト同士の参照だけ** なので、 上限
  で打ち切られた子や、 describe の取得に失敗した子はここにも `項目一覧` にも
  出ない。 そのような経路は `警告` シートに名前が残る
- `SOQL資料/{管理番号}.md` は **AI に渡す用** の Markdown。 取れなかった
  レポート・失敗した ID の古いファイルはそのまま残る。 1 ページ、
  1 レポート。 役割は `SOQL調査.xlsx` と完全に重複する （ 両方とも AI に
  渡せるが、 Markdown の方が AI に読みやすい ）。 xlsx と Markdown を
  両方見比べる運用でも OK

## 8. 個人情報の判定について

判定は **機械的な目安** で、 最終判断は人が行う。 CSV とこのドキュメントに
そう明記する。 判定が曖昧なものは `要確認` / `判定不可` に倒す。

判定ルール（ 列単位 ）:

- `あり`
  - 項目の型が `email` / `phone` / `address` / `location`
  - 表示名または API 名がキーワードに一致 かつ 所属オブジェクトが
    個人系（ `Contact` / `Lead` / `User` / `Individual` / `PersonAccount` 、
    または `Account` で `IsPersonAccount` 項目を持つ ）
- `要確認`
  - キーワードに一致するが所属オブジェクトが個人系でない
  - 対応表で対応フィールドが引けなかった列
- 空 … 上のどれでもない

キーワード一致のさせ方は **単純な部分一致ではなく、 3 段階** で見る:

- **1 文字の日本語キーワード** （ `姓` / `名` ）: 表示名がキーワードと
  **完全一致** するときだけ一致 （ 前後の空白は除く ）。 API 名には
  適用しない。 `商談名` は `名` に **当たらない**
- **ASCII キーワード** （ `email` / `phone` / `city` / `state` / `zip` /
  `fax` / `birth` / `gender` / `mobile` / `street` / `postal` ）:
  API 名・表示名を **トークン** に分解 （ `_` / `__c` / 空白 /
  camelCase の切れ目 `BillingCity` → `Billing` `City` / 数字との切れ目 ）
  して、 いずれかのトークンがキーワードに **一致** するとき一致する。
  - 例: `BillingCity` ・ `City__c` ・ `Mailing State` は一致、
    `Capacity` ・ `Estate` ・ `Velocity` は **一致しない**
  - `birth` だけは **トークンの先頭一致** も許す （ `Birthdate` 、
    `BirthDate` 、 `Birth_Date` ）
- **上記以外の日本語キーワード** （ 2 文字以上 ）: 従来どおり
  **部分一致** （ 大文字小文字を無視 ）

`Account.Name` のように法人を表すオブジェクトの `Name` は キーワード
「 氏名 」 に一致しますが 個人系でないので `要確認` になる。 `Contact.Name`
は同じキーワード一致でも 個人系オブジェクトなので `あり` になる。

判定対象は レポートの **出力に出る列** だけ。 絞り込みにだけ使う列は
対象外（ その列の値が出力されないので、 個人情報露出のリスクが低いため ）。

既定のキーワードと個人系オブジェクトは コードの定数 `DEFAULT_KEYWORDS` /
`DEFAULT_PERSON_OBJECTS` （ `src/pii.py` ） にある。 変更したいときはコードを
直してコミットする。

`一覧` シートの `主オブジェクト` 列は、 `record.main_object` が **特定
できなかったとき** は `objects` dict の先頭キーで補完せず、 `(不明)` を入れる。

**レポートの行データ**（ 値そのもの ） は **メモリ上で件数を数えるだけ** で、
CSV / ログ / 警告 / 例外メッセージには絶対に出さない。 2000 件チェックで
`get` が呼ばれても、 戻り値の長さを取るだけで 中身は触らない。
