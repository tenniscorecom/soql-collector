# 使い方

Salesforce のレポート describe を管理番号ごとにとってメモリに保持し、 人が
Excel で見る ``SOQL調査.xlsx`` と、 ダウンローダー用の ``列名の対応.csv`` と
``SOQLレポート/{管理番号}.py`` 、 AI に貼る ``SOQL資料/{管理番号}.md`` を作る
ツールです。

完成形 （2026-10-15） ：

| ファイル | 役割 | 人がすること |
|---|---|---|
| `output/SOQL調査.xlsx` | 見る（3 シート: 一覧 / 列の対応 / 関係図） | 見るだけ（毎回作り直す） |
| `output/SOQL資料/{管理番号}.md` | AI に貼る資料 | これ 1 つを AI に貼る |
| `output/SOQLレポート/report_{管理番号}.py` | ダウンローダー用の SOQL レポート | 見るだけ（SOQL が作れなかったものは出ない） |
| `input/列の直し.xlsx` | 直す場所 | 直すのはここだけ |
| `output/列名の対応.csv` | ダウンローダー用 | 触らない（形式は今のまま。契約） |
| `input/子リレーション.csv` | 会社側で手入力する子リレーション | 必要なときだけ書く |
| `output/AIチャット用/` | AI チャットに渡すファイル | 資料と一緒に渡す |
| `data/元データ/` | Salesforce から取った原本 | 触らない |

## 典型的な流れ

1. ``実行.bat`` を実行 （引数なし。 取得のあと解析する）
2. ``output/SOQL調査.xlsx`` の **一覧** シートを開く（1 レポート 1 行）
3. 一覧の **要対応・要確認の列数** が 1 以上の行の **管理番号** を覚える
4. **列の対応** シートで該当の管理番号の **要対応**（薄い赤） / **要確認**
   （薄い黄） の行を確認する
5. ``input/列の直し.xlsx`` を開き、 **直したSOQL列名** 列に値を入れる
   （自動で取れた列を上書きしたいときもここを使う）
6. ``解析.bat`` を実行 （ Salesforce に接続せずに作り直す ）
7. ``output/SOQL資料/{管理番号}.md`` と、 冒頭に書いてある一緒に渡すファイルを
   AI チャットに渡して SOQL を組み立ててもらう（ 詳しくは「4-2. AI チャットに渡すファイル」 ）

途中で 「自動が取った列を上書きしたい」 ときも ``input/列の直し.xlsx``
の **直したSOQL列名** 列に値を入れれば、 次の実行で人の値が必ず優先される。
``直したSOQL列名`` と **メモ** のセルはツール側で絶対に上書きしない。

## 1. 初回準備

1. ``config.ini.example`` を ``config.ini`` にコピーする（ 実体の ``config.ini``
   は ``.gitignore`` 済み ）
2. ``config.ini`` のキーを必要に応じて書き換える。 ``[FILES]`` ``[SURVEY]``
   ``[PII]`` の **すべてのキーが必須** 。 キーが足りないと comken の
   ``ConfigError`` で止まる（既定値での補完はしない）。 値はあるけれど
   不正なときも ``ConfigError`` で止める
3. comken の親ディレクトリ（既定 ``F:\dev``） を ``PYTHONPATH`` に
   含めるか、 同梱の ``実行.bat`` を使う（ ``実行.bat`` は ``PYTHONPATH``
   を代行してくれる ）

### `[FILES]` のキー

| キー | 値の例 | 意味 |
|---|---|---|
| `MASTER_XLSX_PATH` | `./input/レポート管理表.xlsx` | レポート管理表（Excel）。 管理番号 / 概要 / Salesforce URL / 有効 |
| `OUTPUT_DIR` | `./output` | 出力先（`SOQL調査.xlsx` / `列名の対応.csv` / `SOQL資料/` / `関係図/` を置く） |
| `DESCRIBE_CSV_PATH` | `./data/項目定義.csv` | このパスの親フォルダの下の `元データ/` に原本を保存する。 ファイル自体は作らない |
| `COLUMN_FIX_XLSX_PATH` | `./input/列の直し.xlsx` | 人が直す xlsx。 詳細は「3. `input/列の直し.xlsx` の使い方」 |
| `XLSX_NAME` | `SOQL調査.xlsx` | `OUTPUT_DIR/` 配下に書く Excel ファイル名 |
| `MARKDOWN_DIR` | `SOQL資料` | `OUTPUT_DIR/` 配下に書く AI 向け Markdown のフォルダ名 |
| `DIAGRAM_DIR` | `関係図` | `OUTPUT_DIR/` 配下に書く Mermaid 関係図のフォルダ名 |

`列名の対応.csv` のファイル名は **ダウンローダーとの約束で固定** のため、
config からは外してある。 出力先は `OUTPUT_DIR/列名の対応.csv`。

### `[SURVEY]` のキー

| キー | 値の例 | 意味 |
|---|---|---|
| `RELATED_DEPTH` | `3` | 主オブジェクトから何段まで関連オブジェクトを掘るか。 `1` なら参照先 1 段だけ |
| `RELATED_MAX` | `40` | 関連オブジェクトの合計件数の上限。 超えた分は警告に名前が残る |
| `ROW_LIMIT_CHECK` | `○` | 1 レポートごとに 2000 件チェックを実行するか。 `×` だと 「2000件超」 列が 「未実施」 |
| `SIMILAR_COLUMN_THRESHOLD` | `0.8` | 似たレポート判定で 「近い」 とみなす Jaccard 類似度の下限。 0.0 〜 1.0 |

### `[PII]` のキー

| キー | 値の例 | 意味 |
|---|---|---|
| `KEYWORDS` | （`氏名, 名前, ...`） | 個人情報とみなすキーワード。 カンマ区切り |
| `PERSON_OBJECTS` | `Contact, Lead, User, Individual, PersonAccount` | 個人系オブジェクトの API 名。 カンマ区切り |

旧 config.ini に ``[LIMITS]`` / ``[SF]`` / ``[CHECKS]`` / ``[SIMILAR]`` /
``[OBJECTS]`` などのセクションが残っていても、 このツールは読まないので無視
される（そのまま残しておいて OK） 。

## 2. 実行

### 動かす

| 使うもの | 接続 | すること |
|---|---|---|
| `実行.bat` （`python main.py`） | する | 取得のあと解析。 ふだんはこれ |
| `取得.bat` （`python main.py --fetch`） | する | 保存に無いものだけ取る。 出力は作らない |
| `全部取り直し.bat` （`python main.py --fetch --force`） | する | 全部取り直して上書きする。 出力は作らない |
| `解析.bat` （`python main.py --analyze`） | しない | 保存データだけで出力を作る |

ほかの引数を付けるとエラーで終了コード `2` が返る。

**取り直すのは次のときだけでよい。**

- 新しいレポートを管理表に足した → `取得.bat` か `実行.bat` （足りないものだけ取る）
- Salesforce 側でレポートや項目を変えた → `全部取り直し.bat` のあと `解析.bat`
- `列の直し.xlsx` や `子リレーション.csv` を直した → `解析.bat` だけ

### 取得（`取得.bat` / `全部取り直し.bat`）

- レポートとオブジェクトの describe を **加工せず原本のまま** `data/元データ/` に保存する。
  解析で新しい項目が要るようになっても、 取り直さずに済む
- 保存にあるものは API を呼ばない。 実行の終わりに API の呼び出し回数がログに出る
- 取れなかったものは保存しないので、 次の取得でやり直す
- **レポートの行データは保存しない**（件数だけ `元データ/件数.csv` に残す）
- 今回調べないレポートの保存を消す

### 解析（`解析.bat`）

- **Salesforce には接続しない**。 `data/元データ/` からだけ作る
- 件数は `元データ/件数.csv` から読むので、 「2000件超」 列も同じ結果になる
- **レポートの原本が無いレポートは失敗になる**（ 終了コード `1` ）。 途中まで作った不完全な
  結果は出さない。 ログに 「保存データに無いので 取得.bat で取ってください（足りないもの: …）」
  と出る。 他のレポートは出る
- **オブジェクトの原本が無いときは、 レポートは失敗にせず警告が 1 行出る**。 警告は
  「オブジェクト {名前} は保存データに無い（取得.bat で取れることがあります）」 という文。
  そのオブジェクトの列は （不明） のままになる
- 組織は接続先の `DOMAIN_URL` から決めるので、 サンドボックスに差し替えているときは
  サンドボックスの保存データを使う
- 保存データは書き換えない。 今回調べないレポートの原本も消さない

### どのレポートが対象になるか

管理表の「有効」列が `○` のものすべて。 個別に取りたいときは、 その行だけ `○`
にして、 ほかを `×` にする。 「○」が 1 件も無いときは「管理表に『有効』が ○
の行がありません」と表示して終了コード `2` で終わる。

実行すると次の順で動きます。

1. 管理表を読んで対象エントリを決める（「有効」列が `○` の全件）
2. ID ごとに Salesforce へつなぎ、 レポート describe・主オブジェクト
   describe・関連オブジェクト describe・（`ROW_LIMIT_CHECK` が `○` のとき）
   レポート実行を取ってメモリ上の記録（`ReportRecord`） にする。 同時に
   **SOQL の下書き** を組み立て、 `一部作れず` のときは 1 行目に
   `【未完成】…` の印を入れる
3. `OUTPUT_DIR/` 配下へ
   - **`SOQL調査.xlsx`** （3 シート: 一覧 / 列の対応 / 関係図）
   - **`列名の対応.csv`** （ダウンローダー用）
   - **`SOQL資料/{管理番号}.md`** （1 レポート 1 Markdown）
   - **`関係図/{主オブジェクト}.md`** （主オブジェクト 1 つ 1 Markdown）
   - **`SOQLレポート/report_{管理番号}.py`** （1 レポート 1 Python。 SOQL が作れなかったレポートは作らない）
4. 失敗した ID は個別にスキップされ、 残りは続けて取得します。 Markdown
   も取れた record のぶんだけ上書きされ、 古い / 取れなかった分のファイルは
   消さない
5. 終了コードは「失敗が 1 件でもあれば `1`」、 全件成功なら `0`、 引数エラー
   や設定・対象の不足は `2`。 取れた record の xlsx / CSV を ``run_tables``
   で書き出すときに例外が出ても `1` を返す（出力の生成に失敗した）

### 単品で試す （`trial/`）

管理表を使わずにレポート 1 件だけ取りたいときは `trial/fetch_one_report.py`
の単品サンプルが使える。 出力は本体の `output/` ではなく `output/single/` に
隔離され、 本体 xlsx / csv にも混ざらない。

```
python -m trial.fetch_one_report <レポートのURL> [管理番号]
```

管理番号を省略すると既定 `sample`。 argparse が使い方（usage） を出して
`SystemExit(2)` するのは他の CLI と同じ。

`trial/` は **名前空間パッケージ** で、 `__init__.py` を **持たない** 。
`comken` のように `pythonpath` で後ろから `sys.path` に入るライブラリが
あっても pytest は特に sys.path 書き換えをせずにそのまま動く。

## 3. `input/列の直し.xlsx` の使い方

`[FILES] COLUMN_FIX_XLSX_PATH` （既定 `./input/列の直し.xlsx`） に **人が
Excel で開いて手で見比べる列の対応表** を書く。 自動の列対応
（`mapping.build_column_map`） では対応が取れない列や、 自動の対応が
間違っているときに使う。 **自動で取れた列を上書きしたいときも同じ** 。

- シート 1 枚、 Excel のテーブル 1 つ。 名前は ``ColumnFix``
- 列 （この順） ： 状態 / 主オブジェクト / 表示名 / 列キー / 自動のSOQL列名 /
  候補 / **直したSOQL列名** / メモ / 使っているレポート / 更新日
- 状態： `OK` （自動が取った・人が直した） / `要対応` （自動も人も取れず） /
  `要確認` （候補が複数、 人の値の型が引けない）
- 見栄え： 見出し行は 1 行目で固定、 列幅は全角=2・半角=1 で整え、 人が書く
  「直したSOQL列名」 と 「メモ」 の見出しセルは薄い緑、 状態=要対応の行は
  薄い赤、 状態=要確認の行は薄い黄で塗られる

**ルール**:

- 実行のたびに新しい列キーは行を追加、 既存行は `状態 / 表示名 / 自動のSOQL列名 /
  候補 / 使っているレポート / 更新日` を今回の値で書き換える
- **`直したSOQL列名` と `メモ` は絶対に書き換えない・消さない** （人の入力を尊重）
- **`直したSOQL列名` に値があれば、 自動で取れた列も人の値で上書きされる**
  （値が無い列も含めて、 人の値が `column_map` の `対応フィールドAPI名` に反映）
- 並び： 要対応 → 要確認 → OK、 その中は主オブジェクト → 列キー
- 書けない（PermissionError） ときは WARNING だけ出して他の出力は作る。
  読めない・見出し違いは ``ExcelError`` で止める （ファイルは変えない）
- 型を引けない値は状態=要確認、 値はそのまま使う

**移行**: 旧 `data/列の対応.csv` （メモ=手入力 かつ SOQL列名あり） がある
ときは、 「直したSOQL列名」に引き継ぐ。 旧ファイルは消さない。 件数をログに
出す。

**運用**:

1. ``実行.bat`` を 1 回動かす（``input/列の直し.xlsx`` が無いときは新規で作られる）
2. ``input/列の直し.xlsx`` を Excel で開く
3. **状態=要対応/要確認の行** を見て、 Salesforce の API 項目名に直す
   （例: `Account.Name`）。 自動で取れた列を上書きしたいときも、 `直したSOQL列名`
   に値を入れる
4. xlsx を保存して閉じる（Excel で開いていると書き込めないので注意）
5. ``解析.bat`` を実行する（ Salesforce に接続せずに出力だけ作り直す ）

## 3-2. `input/子リレーション.csv` の使い方

会社の中の情報は開発側に持ち出せないので、 **人が会社側で手入力する** ための
CSV を置ける。 場所は `[FILES] COLUMN_FIX_XLSX_PATH` と同じフォルダ
（既定 `./input/子リレーション.csv`） 。

- 親オブジェクト → 子オブジェクト の繋がり（ 子リレーション ） を書ける
- 実行のたびに **ファイルが無ければ見出しだけのファイルを作る** 。 既有の
  ファイルは上書きしない
- Excel で開いて編集・保存できる。 文字コードは cp932 でも UTF-8 （ BOM 付き ）
  でも読める
- 見出しが違うときは **エラーで止まる**（ `列の直し.xlsx` と同じ扱い。
  終了コード `2` ）

**列**:

| 親オブジェクト | リレーション名 | 子オブジェクト | 参照項目 | メモ |
|---|---|---|---|---|
| Account | Contacts | Contact | AccountId | 取引先の担当者一覧 |
| Account | Tasks | Task | WhatId | 取引先のタスク一覧 |

- `親オブジェクト` … `Account` のように主オブジェクト名
- `リレーション名` … `Contacts` のように Salesforce のリレーション名
- `子オブジェクト` … `Contact` のように子オブジェクト名
- `参照項目` … `AccountId` のように、 **親を参照する子の項目名**
- `メモ` … 自由欄。 SOQL には入らない

**書ける値の範囲**: `親オブジェクト` / `リレーション名` / `子オブジェクト` /
`参照項目` は `^[A-Za-z_][A-Za-z0-9_]*$` （ 英字・数字・`_` だけ ） に限る。
値は SOQL と生成 .py に入るので、 引用符や空白は入れられない。 条件に
合わない行は **使わずに警告が出る**。

**何に使うか**:

- Salesforce の describe が取れない環境 （ developers に無いオブジェクトなど ）
  でも、 クロスフィルタの副問い合わせの材料にする
- レポートの列が子の項目のとき、 SOQL の FROM を子に切り替える材料にする
  （ 「SOQL 資料」 の 「取り方」 にも出る ）

**出力への反映**:

- Markdown の 「子リレーション（サブクエリの材料）」 の表に 「出どころ」 列が
  出る（ `Salesforce` / `手入力` ）
- クロスフィルタの判定結果の `reason` と、 生成 .py のコメントに
  「手入力」 が出る

**保存データには書かない**: `data/元データ/` （ Salesforce から取ってきた原本 ） には
手入力の値を書き込まない。

## 4. `SOQL資料/{管理番号}.md` の構成

1 レポート 1 Markdown。 AI が SOQL を組むために、 次の節をこの順で含む:

| 節 | 中身 |
|---|---|
| `# {管理番号} {概要}` | タイトル |
| メタ 6 行 | レポートID / 主オブジェクト / レポート形式 / 集計形式（管理表） / 2000件超 （件数付き） / 個人情報 |
| 先頭案内 | 「このファイルを丸ごと AI に貼ってください。 SOQL の下書きを、 下の資料と照らして直すよう頼みます」 |
| `## SOQL の下書き` | 状態（`作成済み` / `要確認` / `一部作れず` / `作れず`） ・SOQL 本文（```sql フェンス） ・AI への補い方 ・作れなかった部分の箇条書き ・要確認の箇条書き。 `一部作れず` の SOQL は本文の 1 行目に `【未完成】…` の印が残る |
| `## 取り方` | `Bulk` か `REST` か。 REST のときは理由と、 REST の注意（ 値が文字列にならず数値・真偽値のまま / 0 件だと列が空 / 全行 null の参照項目は列が出ない ） を書く。 Bulk のときは 「SELECT の中の子サブクエリ・集計関数・GROUP BY・OFFSET・TYPEOF を使うように直したら USE_BULK を False にする」 を書く |
| `## クロスフィルタの繋がり` | クロスフィルタ 1 個ずつの判定の表（ 番号 / 判定 / 主側項目 / 子オブジェクト / 結合項目 / リレーション名 / SOQL（ `入れた` / `入れていない` ） / 理由 ）。 判定は `直接` / `直接でない` / `確認できず` の 3 種。 判定が 1 件も無いときは出ない |
| `## 子リレーション（サブクエリの材料）` | 主オブジェクトの子リレーションの表（ リレーション名 / 子オブジェクト / 参照項目 ）。 最大 100 行、 超えた分は 「ほか N 件」 。 例として `(SELECT Id FROM <リレーション名>)` と 「SELECT の中に書いたら USE_BULK を False にする」 を添える。 データが無いときは 「保存データに無い。実行.bat で取り直すと出る」 の 1 行 |
| `## 列の対応` | 表示名 → 使う SOQL 列名・どこから・候補の表 |
| `## 絞り込み` | 組立式・絞り込みの表・日付 / 標準フィルタ / クロスフィルタ / 上位 N の箇条書き |
| `## 並び順` | `sortBy` を 1 行ずつ |
| `## グループ・集計` | TABULAR は 「なし」、 SUMMARY / MATRIX は 「SOQL では GROUP BY と集計関数で表すか、 明細を取って集計する」 の 1 行 + グループ・集計の箇条書き |
| `## 関連オブジェクトの経路` | 主オブジェクトから使われている経路だけを `Contact → Account（Account）→ Owner（User）` の形で |
| 関係図リンクと字下げツリー | `../関係図/{主オブジェクト}.md` への相対リンクと、 字下げの罫線で組んだ同じ木 （``` フェンスの中に） 。 図が無いときは出ない |
| `## SOQL を組むときの注意` | 取れなかった列 / 複数候補の列 / スコープが自分のレコード / 日時はタイムゾーンに注意 / 2000件超なので Bulk で取る（ REST で取る場合は 「2000件超だが REST で取る（ページ送りで全件取れる。往復は増える）」 。 2000件超 の判定は 管理表の「2000件超」列が ○ のときにも出る ） / クロスフィルタ（ 副問い合わせにできたときは 「クロスフィルタは副問い合わせにした（REST で取る）」 、 できなかったときは 「クロスフィルタは副問い合わせにできていない（理由は「クロスフィルタの繋がり」）」 ） / 集計レポート （ ＋ 「GROUP BY と集計関数を使うなら USE_BULK を False にする」 ） のうち当てはまるものだけ |

毎回、 今回取れたレポート分だけ上書きする。 失敗した ID や取れなかった
レポートの古いファイルは **消さない** （パスが分かれば後から見られる） 。
UTF-8、 BOM なし、 改行 LF。

## 5. `SOQL調査.xlsx` の構成

**まず 一覧 シートを見る**。 1 行が 1 件のレポート。 そこから要対応の
あるレポートの 管理番号 を覚えて、 **列の対応** シートで掘りに行く。
**関係図** シートで主オブジェクト周りの構造を確認する。

**3 枚とも Excel のテーブル** （構造化） で、 列幅は全角=2・半角=1 で
計算して整え、 見出し行は固定される。 1 行目に案内文
（ 「 直すときは input/列の直し.xlsx の『直したSOQL列名』に書いて、
解析.bat を実行してください。 」 ） が出る。

### 一覧

1 行が 1 件のレポート。

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `主オブジェクト` | record の `main_object` |
| `SOQLの状態` | `作成済み` / `要確認` / `一部作れず` / `作れず` |
| `取り方` | `Bulk` / `REST（理由）` 。 理由は 通常 SOQL にした理由（ 副問い合わせ / 件数が 1000 件以下）。 下書きが無いレポートは空 |
| `クロスフィルタの繋がり` | クロスフィルタの判定の件数。 件数が 0 でない判定だけを `直接2・直接でない1・確認できず1` の形で並べる。 判定が無ければ空 |
| `要対応・要確認の列数` | 「列の対応」シートで該当 管理番号 が状態=要対応/要確認 だった件数 |
| `集計形式（管理表）` | 管理表の「集計形式」列の値（ `サマリー` / `マトリックス` / `無し` ）。 記入が無ければ `(未記入)` |
| `2000件超` | `row_check.status` （`超えている` / `超えていない` / `判定不可` / `未実施`） |
| `行数` | `row_check.rows` が非 `None` のときだけ実際の行数 |
| `個人情報` | `pii.status` （`あり` / `要確認` / `なし`） |
| `個人情報の該当列` | `pii.matching_columns` を `表示名(根拠)` の `; ` 区切りで |
| `似たレポート` | 例 「グループ2: 1001が基準・条件のみ違い・条件を引数にして1本にできそう」 |
| `似たSOQL` | 生成した SOQL が似ている相手。 例 「1002: WHERE以降が同じ（SELECT 追加: Amount）」。 相手は管理番号の昇順、 区切りは `; `。 比較するのは `作成済み` と `要確認` の SOQL だけで、 `作れず` と `一部作れず` は比べない |
| `警告` | 件数と最初の 1 件の要約 |
| `SOQL資料` | `SOQL資料/{管理番号}.md` への相対パス（ハイパーリンク） |

### 列の対応

1 行 = 1 レポートの 1 列。

| 列 | 中身 |
|---|---|
| `状態` | `OK` / `要対応` / `要確認` |

| `概要` | record の `summary` |
| `表示名` | レポートの表示名 |
| `列キー` | レポートの列キー |

| `自動の値` | 人が直して自動と違うときだけ、 自動で取れていた値 |

### 関係図

## 6. `列名の対応.csv` （ダウンローダー用）

ダウンローダー側は `(主オブジェクト, SOQL列名)` → 表示名 で `COLUMN_NAMES`
を組み立てる。 形式は **契約** で固定（ `tests/contract/列名の対応.contract.csv`
とバイト単位で一致 ） 。

| 列 | 中身 |
|---|---|
| `主オブジェクト` | record の `main_object` |
| `SOQL列名` | `column_map` の `対応フィールドAPI名` （解決できた列だけ） |
| `表示名` | 最多 （同数なら管理番号の小さいレポートのもの） 。 違う表示名が他にあれば 備考に「別の表示名あり:」 の形で並ぶ |
| `備考` | 別の表示名一覧 |
| `更新日` | 今回書いた日 （`YYYY-MM-DD`） |

## 8. SOQL を組み立てる手順

このツールは **SOQL の下書き** を作ります（2026-10-15 復活、 安全策つき）。
状態は `作成済み` / `要確認` / `一部作れず` / `作れず` の 4 種。 `一部作れず`
のときは本文の 1 行目に `【未完成】…` の印が入り、 そのまま Salesforce に
投げると構文エラーになって実行できない。 必ず人が直すか、 印付きのものは
実行しないこと。 `作れず` は本文が空。

### そのまま使う場合

1. `実行.bat` を実行する
2. 出力先の `SOQL調査.xlsx` の **一覧** シートで状態を確認する
3. 状態が `作成済み` の SOQL はそのまま Salesforce で実行するか、 必要なら
   人が少し直す。 `要確認` は内容を見て直してから実行。 `一部作れず` /
   `作れず` は人が直すか、 このツールでは実行しない

### AI に Markdown を渡す場合

1. `実行.bat` を実行する
2. 出力先（`[FILES] OUTPUT_DIR` で指定したフォルダ） の `SOQL資料/` を開く
3. 該当 管理番号 の `.md` を AI に貼る
4. 受け取った SOQL を **人が確認してから実行する**。 条件を狭めるか分割実行を
   検討する、 必要なら手書きで直す

### 相対日付の表記

レポートの条件（ `reportFilters` ） や日付フィルター（ `standardDateFilter` ） に
相対日付が書かれることがあります。 `LAST 60 DAYS` や `過去 60 日間` のような
表記は SOQL のリテラルに自動で直します（ `LAST_N_DAYS:60` ）。

- 直したときは `checks` に「相対日付を変換した: …」が 1 件入ります。 レポートの
  期間と SOQL の境界は違うことがあるので、 実行前に確認してください
- 「翌 N 日」 （ `NEXT_N_DAYS:60` ） はレポートでは当日を含めて 60 日
  （ 当日 〜 59 日後 ） ですが、 SOQL の `NEXT_N_DAYS:60` は翌日から 60 日
  なので、 `TODAY` を足した形
  （ `( CloseDate = TODAY OR CloseDate = NEXT_N_DAYS:59 )` ） になります。
  `checks` に「翌 60 日は当日を含めて 60 日なので TODAY と NEXT_N_DAYS:59
  にした: …」が入ります
- 「翌 1 日」 （ `NEXT_N_DAYS:1` ） は当日だけなので、 `CloseDate = TODAY`
  になります（ 括弧は付けません ）
- 数量が 1 未満（ `LAST 0 DAYS` ） や、 単位が分からない（ `過去 60 週日` ） ときは
  SOQL にできないので `missing` になります。 人が直す必要があります
- 文字列型の項目に `今日` のような値が入っているときは、 文字列のままです

### クロスフィルタの繋がり

レポートの クロスフィルタ（ `crossFilters` ） は、 **主オブジェクトと子オブジェクトが
直接つながるリレーションか** をプログラムの中で判定してから、 副問い合わせ
（ `IN (SELECT ...)` ） にします。 判定は 3 種です。

| 判定 | 意味 | SOQL |
|---|---|---|
| `直接` | 主オブジェクトの子リレーションが、 子オブジェクト名も参照項目も結合項目と一致する | 副問い合わせにする |
| `直接でない` | 情報はそろっているが直接つながっていない | 作りません（ 【未完成】 ） |
| `確認できず` | 情報が足りないので確認できない | 作りません（ 【未完成】 ） |

- `直接` の条件は 3 つ。 1) 主側の項目が主オブジェクトの項目に解決でき、 型が
  `id` 。 2) 主オブジェクトの子リレーションに、 子オブジェクト名が一致し
  **かつ** 参照項目が結合項目と一致する要素がある 。 3) 結合項目が子オブジェクトの
  項目に解決できる
- 同じ子オブジェクトへ参照が 2 本あるとき（ 例: `Contact.AccountId` と
  `Contact.ParentAccount__c` ） は、 結合項目に一致する方だけを使います
- `直接でない` / `確認できず` のときは、 従来どおり元の値の `repr` と
  理由を `missing` に入れて 【未完成】 にします
- **直接つながるものだけ副問い合わせにする** のは、 そうしないとレポートと
  意味の違う件数になるがあるためです
- 判定は 3 箇所に出ます。 `SOQL調査.xlsx` の 一覧 シートの
  「クロスフィルタの繋がり」 列（ `直接2・直接でない1・確認できず1` の形 ） 、
  Markdown の `## クロスフィルタの繋がり` の表、 生成した .py の
  `# 状態:` の直後のコメント（ `# クロスフィルタ 1: 直接（…）SOQL に入れた` ）

## 9. SOQL レポート Python ファイル

`OUTPUT_DIR/SOQLレポート/report_{管理番号}.py` に、 ダウンローダーの
`src/soql_reports/reports/` にそのまま置けるファイルを書いています。 中身は
`SoqlReport` のサブクラス 1 つだけです。

```python
"""<概要>（soql-collector が生成。管理番号 1001）。"""

from typing import ClassVar

from src.soql_reports.base import SoqlReport

# 状態: 要確認
# 要確認: ...
# 作れなかった部分: ...


class Report1001(SoqlReport):
    KEY = "1001"
    NAME = "売上レポート"
    REPORT_ID = "00O5g00000ABCDEfgh"
    USE_BULK = True  # False にすると通常の SOQL（REST の query()）で取る
    COLUMN_NAMES: ClassVar[dict[str, str]] = {
        "Owner.Name": "所有者",
    }

    def soql(self) -> str:
        return """SELECT Name,
  Owner.Name
FROM Case"""
```

- 1 レポート 1 ファイル。 **SOQL が作れなかったレポートは作りません**
  （ `作れず` の SOQL は本文が空なので、 書いても動かない）
- ファイル名の管理番号は英数字と `_` だけ残します（ 他の文字は `_` に
  置き換えます ）。 置換で同名になる管理番号は、 後の方に連番 `_2` を付けます
- `一部作れず` の SOQL は `【未完成】` の行をそのまま残します。 ダウンローダーは
  この行を見て実行前に止めます
- `NAME` にはレポート名を書きます。 レポート名が無いときは概要を使います。
  どちらも空なら `NAME` の行は書きません
- `REPORT_ID` にはレポート ID を書きます。 管理表の URL から取り出した値を
  そのまま書きます。 URL にレポート ID が無いときは `REPORT_ID` の行を書きません
  （ ファイルは作ります ）
- `REPORT_ID` は試験用リポジトリが、 管理表を通さず SOQL の件数とレポートの
  総件数を比べるのに使います。 ダウンローダーはこの行を読みません。 URL 全体
  （ 組織のドメイン ） は書きません。 管理表の URL は書き換えず、 正のままです
- `USE_BULK` には取り方（ `True` = Bulk API 2.0、 `False` = REST の `query()` ）
  を書きます。 取り方は **件数** で決まります。 1000 件を超えるレポートは Bulk で
  取り、 1000 件以下は通常 SOQL（ REST の `query()` ） で取ります。
  副問い合わせ（ クロスフィルタ ） を含む SOQL は、 件数に関係なく `False` に
  します（ Bulk API 2.0 で動作確認していないため、 確実に動かすため ）。
  理由（ `WHERE の副問い合わせを Bulk API 2.0 で動作確認していないため REST で取る`
  や `件数が 1000 件以下のため（根拠: …）` ） をコメントに付けます。
  集計関数（ `COUNT` / `SUM` 等）・ `GROUP BY` を使う SOQL も Bulk API で取れないので
  `False` にしてください（ これは自動で直しません。 人が直します ）
- `COLUMN_NAMES` には SELECT に入った列の「SOQL列名: 表示名」を書きます。
  同じ表示名が 2 列以上あるときはその列を入れず、 自動で引き直される方に
  任せます（ `# 見出しが重なるので自動の対応に任せた:` のコメントになります ）
- `CHECK_COUNT` は書きません（ 既定の `True` のままです ）

## 10. 限界

- レポート列の **表示名と、 項目の表示名が一致したもの** が `対応フィールドAPI名`
  に自動で埋まる。 それでも一致しないときは、 関連オブジェクトの項目ラベルとも
  突き合わせる。 それでもダメなら `(不明)` のまま残る
- **所有者 (`Owner`) は User とみなして解きます。** `Owner` はキュー (`Group`) を
  指せるので、 レポートの表示と合わせ_User として辿ります。 表示名の接頭辞が
  `所有者` / `ケース所有者` / `Opportunity Owner` のように所有者を指すときは、
  `Owner` 経由の User の項目だけを照合します（ 例: `所有者: 役職` → `Owner.Title` ）
- **表示名の接頭辞が参照項目を指すときは、 その参照経由の項目を照合します。**
  接頭辞（ 例: `作成者` `ケース作成者` `最終更新者` ） が主オブジェクトの参照項目
  （ `作成者ID` / `最終更新者ID` など ） を指すときは、 そのリレーション名経由で
  参照先の項目だけを照合します（ 例: `作成者: 役職` → `CreatedBy.Title` 、
  `最終更新者: 役職` → `LastModifiedBy.Title` ） 。 接頭辞が参照項目を指さない
  ときは従来どおりの照合に進みます
- `Owner.<項目>` のうち User だけの項目（ `Department` など ） は、 キューを
  指せるので SOQL が失敗する可能性があります。 そのときは注意書きが
  `checks` に入ります。 `Owner.Name` のように User の共通項目は対象外です
- 表示名が `タスク: 作業会社名` / `取引先: 取引先名` のように `オブジェクト:
  項目名` の形をしているときは、 コロンの前を **オブジェクトの表示名** として
  扱い、 一致するオブジェクト（describe の `label` を正規化して比較） の
  項目表示名を採る。 主オブジェクトなら項目名、 関連なら主からのリレーション名
  の鎖 + 項目名 （鎖が複数あれば浅いもの、 同じ深さで複数なら候補） 。
  コロンの前に一致するオブジェクトが無ければ、 後ろだけで従来どおりの照合。
  コロン無しの表示名は従来どおり
- 列キーが `<主オブジェクト>.<経路>.<項目>` の形（ 例 `Contact.Account.Name` /
  `Contact.Retention__c.Status__c` ） であれば、 列キーから主オブジェクトと
  各列の SOQL 列名（ `Account.Name` / `Retention__r.Status__c` のように
  参照項目 API 名を経路の `relationshipName` に置き換えた形 ） を自動で取る
- 列キーが `FK_<参照先>.<残りの経路>` の形（ 例 `FK_Contact.Email__c` /
  `FK_$Contact.Email__c` ） の列は、 主オブジェクトの参照項目から
  `<参照先>` への `relationshipName` を取り、 残りは上記の列キーたどりと
  同じ流れで解いて `<relationshipName>.<残りの SOQL>` にする。 候補が複数
  あれば備考に最大 5 件並べて表示名照合には進まない
- このツールは SOQL の `SELECT` / `WHERE` / `HAVING` / `ORDER BY` を
  自動では組み立てない。 集計（`SUMMARY` / `MATRIX`） やグルーピング
  つきのレポートは `SOQL資料/{管理番号}.md` を AI に貼って組み立てる
- **レポートの行データ**（値そのもの） は **メモリ上で件数を数えるだけ** で、
  CSV / ログ / 警告 / 例外メッセージには絶対に出さない。 2000 件チェックで
  `get` が呼ばれても、 戻り値の長さを取るだけで 中身は触らない

## 11. 個人情報の判定について

判定は **機械的な目安** で、 最終判断は人が行う。 CSV とこのドキュメントに
そう明記する。 判定が曖昧なものは `要確認` / `判定不可` に倒す。

判定ルール（列単位）:

- `あり`
  - 項目の型が `email` / `phone` / `address` / `location`
  - 表示名または API 名がキーワードに一致 かつ 所属オブジェクトが
    個人系（ `[PII] PERSON_OBJECTS` の値、 または `Account` で `IsPersonAccount`
    項目を持つ ）
- `要確認`
  - キーワードに一致するが所属オブジェクトが個人系でない
  - 対応表で対応フィールドが引けなかった列
- 空 … 上のどれでもない

キーワード一致のさせ方は **単純な部分一致ではなく、 3 段階** で見る:

- **1 文字の日本語キーワード** （`姓` / `名`）: 表示名がキーワードと
  **完全一致** するときだけ一致 （前後の空白は除く）。 API 名には
  適用しない。 `商談名` は `名` に **当たらない**
- **ASCII キーワード** （ `email` / `phone` / `city` / `state` / `zip` /
  `fax` / `birth` / `gender` / `mobile` / `street` / `postal` ）:
  API 名・表示名を **トークン** に分解 （ `_` / `__c` / 空白 /
  camelCase の切れ目 `BillingCity` → `Billing` `City` / 数字との切れ目 ）
  して、 いずれかのトークンがキーワードに **一致** するとき一致する。
- **上記以外の日本語キーワード** （2 文字以上）: 従来どおり
  **部分一致** （大文字小文字を無視）

`Account.Name` のように法人を表すオブジェクトの `Name` は キーワード
「氏名」 に一致しますが 個人系でないので `要確認` になる。 `Contact.Name`
は同じキーワード一致でも 個人系オブジェクトなので `あり` になる。

判定対象は レポートの **出力に出る列** だけ。 絞り込みにだけ使う列は
対象外（その列の値が出力されないので、 個人情報露出のリスクが低いため）。

## 調べる行を選ぶ（「調査」列）

管理表に **「調査」列を足すと**、「有効」の行のうち「調査」が `○` の行だけを今回調べます。
「有効」はダウンローダーの定期取得の対象を決める列なので、**「有効だが今回は調べない」行**を、
ダウンローダーに影響させずに外せます。

| 「有効」 | 「調査」 | 今回の調査 |
|---|---|---|
| ○ | ○ | 調べる |
| ○ | 空欄・× | 調べない |
| × | ○ | 調べない（「有効」が × の行は、 いつも対象外） |

- **「調査」列が無い管理表は、 今までどおり「有効」だけで決まります。** 列を足すかどうかは任意です。
- 列を足したら、 調べたい行に `○` を付けます。 **付いている行が 1 つも無いと、 終了コード 2 で止まります**。

### 調べない行の保存を消す

取得の最後に、 今回調べないレポート（管理表から消えた・「有効」が ×・「調査」が `○` でない）の
原本と件数を消します。 解析では消しません。

- **消すのは `元データ/レポート/` と `元データ/件数.csv` の中だけです。** 出力ファイルと
  オブジェクトの原本には触りません。
- 消したものは、 次に調べるときに Salesforce から取り直します（「調査」を付け外しして試すと、 そのたびに
  取り直しになります）。
- 消したくないときは、 `src/run.py` の `PRUNE_REPORT_STORE` を `False` にします。
- 対象が 0 件のときは、 何も消しません（管理表を読み違えたときに、 全部消えないようにするため）。


## 件数で取り方を決める（「2000件超」列）

管理表に **「2000件超」列を足すと**、 取り方（ Bulk / 通常 SOQL ）を
**本番の件数** で決められます。 この列は、 本番の件数を知っている人が `○` / `×` で
書きます（ ダウンローダーの管理表の同じ列と同じ意味です ）。

| 「2000件超」 | 本番の件数 | 取り方 |
|---|---|---|
| ○ | 2000 件超 | 1000 件を超えるので Bulk |
| × | 2000 件以下 | 1000 件以下なら通常 SOQL、 超えるなら Bulk |
| 不明 | 分からない | 空欄・列が無いと同じ。 1000 件以下だと分かったときだけ通常 SOQL、 以外は Bulk |
| 空欄・列が無い | 分からない | 1000 件以下だと分かったときだけ通常 SOQL、 以外は Bulk |

- **列は任意です。** 無い管理表でも動きます（そのときはサンドボックスの件数だけで
  判定します）。
- セルが空のときは「不明」として扱います（ `○` でも `×` でもありません）。
- セルに **「不明」と書いたときも、 空欄と同じ扱い** になります（ 分からない）。
  「×」は「2000 件以下だと分かっている」を表すので、 分からないことを表す別の語です。

### 判定の順序

1. 管理表が `○` なら 2000 件超
2. 管理表が `×` なら 2000 件以下。 サンドボックスの 2000 行チェックが
   「超えていない」で行数が取れていれば、 その行数が 1000 件を超えるかで
   1000 件超 / 1000 件以下を分けます
3. 管理表の列が無い（ 空欄・「不明」 ） なら サンドボックスの 2000 行チェックだけで
   決めます。「超えている」なら 2000 件超、 「超えていない」なら行数で分けます。
   判定できない（ 判定不可・未実施 ） ときは不明です

**管理表が分かっているときは、 サンドボックスの件数より管理表を採ります。**
サンドボックスで 2000 件以下でも本番では超えることがあるからです。

### 副問い合わせがあるとき

副問い合わせ（ クロスフィルタ ） がある SOQL は、 件数に関係なく通常 SOQL で取ります。
このとき、 2000 件超 または 不明 なら、 「本番の件数が 5000 件を超えるなら SOQL を
分ける」 という要確認が 1 件付きます（ `SOQL資料/{管理番号}.md` の「要確認」と、
生成した `.py` の `# 要確認:` の行に出ます）。

### 1000 件と 5000 件の由来

- **1000 件** … Bulk API 2.0 を使う境目。 超えたら Bulk で取ります
- **5000 件** … 副問い合わせがあるときに通常 SOQL で取れる上限。 超えるなら SOQL を
  分けます

どちらもコードの定数（ `src/row_size.py` の `BULK_MIN_ROWS` と
`REST_MAX_ROWS_WITH_SUBQUERY` ） で、 設定ファイルには出してません。


## 集計形式を確かめる（「集計形式」列）

管理表に **「集計形式」列を足すと**、 レポートの集計形式と 管理表で書いた値が
合っているかを確かめられます。 値は `サマリー` / `マトリックス` / `無し` の 3 つ。

| 管理表の「集計形式」 | レポートの形式（ `reportMetadata.reportFormat` ） |
|---|---|
| サマリー | `SUMMARY` |
| マトリックス | `MATRIX` |
| 無し | `TABULAR` |

- **列は任意です。** 無い管理表でも動きます（そのときは照合もしません）。
- セルが空のときは「記入なし」として扱います。
- 3 つ以外の値を書いた行は **集計形式なし** として扱い、 管理番号と値を出した
  WARNING が 1 件出ます（ 処理は止まりません ） 。
- 管理表の値とレポートの形式が **両方そろっていて違う** ときだけ、
  「管理表の集計形式は ○○ だが、レポートは ××」 という警告が 1 件出ます
  （ `SOQL調査.xlsx` の一覧シートの 「警告」 列と、`SOQL資料/{管理番号}.md` の
  「警告」 節に載ります ）。
- 管理表で書いた値は、 一覧シートの 「集計形式（管理表）」 列と
  `SOQL資料/{管理番号}.md` の 「集計形式（管理表）」 行に出ます。

**この列は確認用です。** 集計かどうかの判断（ GROUP BY と集計関数を使うか
など）は、 今までどおりレポートの定義（ `reportMetadata.reportFormat` ）で
行います。 管理表の値は 判断に使いません。


## 接続先（サンドボックスで調査する）

管理表の「Salesforce URL」は**本番の URL のまま**で構いません（1 レポート 1 行）。調査は、その本番の組織に
**対応するサンドボックス**へつないで行います。レポート ID は URL からそのまま使います。

- 接続先は、comken の `site_for(url, sandbox=True)` が決めます。本番とサンドボックスの対応は、comken の組織クラス
  （`Solution.SANDBOX_SITE`）に書いてあります。ブラウザのアドレスバーの URL（`○○.lightning.force.com`）を貼っても
  同じ組織として読みます。
- `src/fetch/flow.py` の `SURVEY_ON_SANDBOX`（既定 `True`）を `False` にすると、本番へつなぎます。
- **サンドボックスに同じ ID のレポートがあることが前提です。** サンドボックスの更新（リフレッシュ）より後に本番で
  作ったレポートは、警告「レポート describe に失敗（HTTP 404）」に説明が付いて、そのレポートだけ飛ばされます。
- 元データの保存（`data/元データ/`）は、
  **実際につないだ組織**で分けて持ちます。本番とサンドボックスの describe が混ざることはありません。
- **サンドボックスのデータは本番と違います。** 一覧シートの「2000件超」列は
  サンドボックスの件数で判定した値なので、 参考値です。 本番の件数で判断したい
  ときは、 管理表の「2000件超」列（ `○` / `×` ） を使ってください（ 管理表の列が
  あるときは、 サンドボックスの件数よりその列を優先します ）。
  `[SURVEY] ROW_LIMIT_CHECK = ×` でサンドボックスの 2000 行チェックを切れます。
