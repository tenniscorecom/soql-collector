# 使い方

Salesforce のレポート describe を管理番号ごとにとってメモリに保持し、 人が
Excel で見る ``SOQL調査.xlsx`` と、 ダウンローダー用の ``列名の対応.csv``
を作るツールです。 JSON ファイルは作りません。

各レポートについて、 次の 5 つを機械的に判定して xlsx に出します（ **判定は
目安** で、 最終判断は人が行う。 曖昧なものは 「 要確認 」 / 「 判定不可 」 /
「 確認できず 」 に倒す ）：

1. 似たレポートをまとめられるか
2. 2000 件を超えているか
3. 個人情報を含むか
4. SOQL を組み立てられるか
5. SOQL の件数とレポートの総件数が一致するか — 件数だけ突き合わせて
   条件の写し間違いを機械で見つける。 **不一致・確認できずのものだけ
   人が見る。 件数が一致しても列の中身までは保証しない。**

**レポートの行データ**（ 個人情報を含みうる ） は **メモリ上で件数を数えるだけ** で、
CSV / ログ / 警告 / 例外メッセージには絶対に出さない。

## 1. 初回準備

1. `config.ini.example` を `config.ini` にコピーする（実体の `config.ini` は
   `.gitignore` 済み）
2. `config.ini` の次のキーを必要に応じて書き換える

| セクション | キー | 意味 |
|---|---|---|
| `[FILES]` | `MASTER_XLSX_PATH` | レポート管理表（Excel）。**必須** |
| `[FILES]` | `OUTPUT_DIR` | 出力先。既定は `./output` |
| `[FILES]` | `DESCRIBE_CSV_PATH` | オブジェクト describe を実行をまたいで貯める CSV。1 行 1 項目。組織 / オブジェクト / 項目 API 名 / 型 / 参照先 / リレーション名 / カスタム項目 / 絞り込み可 / 並べ替え可 / 選択肢 / 取得日時。レコードの値は入らない。既定は `./data/項目定義.csv` |
| `[LIMITS]` | `RELATED_MAX` | 関連オブジェクト（参照先）の最大件数。**全段の合計**に対する上限。既定は `40` |
| `[LIMITS]` | `RELATED_DEPTH` | 関連オブジェクトを掘る最大の段数。 `1` なら参照先 1 段だけ （ 今までの挙動 ） 。 既定は `3` |
| `[SF]` | `CREDENTIAL_PREFIX` | comken の `comken cred` で登録した認証情報の先頭につける接頭辞 |
| `[CHECKS]` | `ROW_LIMIT` | レポート 1 件ずつ実行して 2000 件超を判定するか。 `○`（ 既定 ） / `×`。 `×` にすると 一覧 シートの `2000件超` 列が `未実施` になる |
| `[CHECKS]` | `SOQL_COUNT` | ツールが組み立てた SOQL の件数とレポートの総件数を突き合わせるか。 `○`（ 既定 ） / `×`。 `×` にすると 一覧 シートの `件数チェック` 列が `未実施` になる。 1 レポートあたり レポート実行 1 回 + COUNT() クエリ 1 回が増える |
| `[PII]` | `KEYWORDS` | 個人情報判定に使うキーワード。 カンマ区切り。 未設定 / 空なら既定 |
| `[PII]` | `OBJECTS` | 個人系オブジェクト名。 カンマ区切り。 未設定 / 空なら既定 |
| `[SIMILAR]` | `COLUMN_SIMILARITY` | 似たレポート判定で 「 近い 」 とみなす Jaccard 類似度の下限。 0.0 〜 1.0。 既定は `0.8` |

3. comken の親ディレクトリ（既定 `F:\dev`）を `PYTHONPATH` に含めるか、
   同梱の `実行.bat` を使う（ `実行.bat` は PYTHONPATH を代行してくれる）

## 2. 実行

### 動かす

```bat
実行.bat
```

または

```powershell
python main.py
```

**引数は受け付けない**。 付けるとエラーで終了コード `2` が返る （サブコマンドも
無い）。

### どのレポートが対象になるか

管理表の「有効」列が `○` のものすべて。 個別に取りたいときは、 その行だけ `○` にして、
ほかを `×` にする。 「○」が 1 件も無いときは「管理表に『有効』が `○ の行が
ありません」と表示して終了コード `2` で終わる。

実行すると次の順で動きます。

1. 管理表を読んで対象エントリを決める（ 「有効」列が `○` の全件）
2. ID ごとに Salesforce へつなぎ、 レポート describe・主オブジェクト
   describe・関連オブジェクト describe・（ `ROW_LIMIT=○` のとき ）レポート実行を
   取ってメモリ上の記録（`ReportRecord`）にする
3. `OUTPUT_DIR/` 配下へ **`SOQL調査.xlsx`** と **`列名の対応.csv`** を書く
   （ 1 冊の xlsx に 9 枚のシート ）
4. 失敗した ID は個別にスキップされ、 残りは続けて取得します。
5. 終了コードは「失敗が 1 件でもあれば `1`」、 全件成功なら `0`、
   引数エラーや設定・対象の不足は `2` です。

### RPA から呼ぶ例

社内 RPA 基盤から実行する場合は `実行.bat` を経由する。 終了コードは
`実行.bat` がそのまま返すので、 失敗があれば `1` で上がる。

```bat
実行.bat
```

**引数を付けるとエラー**（ 終了コード `2` ） になるので、 RPA から呼ぶときも
そのまま（ 引数なし ） で起動する。

### 単品で試す（ `trial/` ）

管理表を使わずにレポート 1 件だけ取りたいときは `trial/fetch_one_report.py`
の単品サンプルが使える。 出力は本体の `output/` ではなく `output/single/` に
隔離され、 本体 xlsx / csv にも混ざらない。

```
python -m trial.fetch_one_report <レポートのURL> [管理番号]
```

管理番号を省略すると既定 `sample`。 argparse が使い方（ usage ）を出して
`SystemExit(2)` するのは他の CLI と同じ。

1 件のサンプルでも `SOQL調査.xlsx` は作られる。

`trial/` は **名前空間パッケージ** で、 `__init__.py` を **持たない** 。
`comken` のように `pythonpath` で後ろから `sys.path` に入るライブラリが
あっても pytest は特に sys.path 書き換えをせずにそのまま動く。

## 3. `data/項目定義.csv` の扱い

オブジェクト describe のキャッシュは `[FILES] DESCRIBE_CSV_PATH` （ 既定
`./data/項目定義.csv` ） に **UTF-8 BOM 付き + CRLF** の CSV で書かれる。
1 行 1 項目で、 1 オブジェクトの行は同じ取得日時。 組織の単位 (プロジェクト
  の URL のネットロカ 小文字) で区別されるので、 本番と Sandbox が同じ
ファイルに混ざっても取り違えない。 列は `組織 / オブジェクト / オブジェクト
表示名 / カスタムオブジェクト / 項目 API 名 / 項目表示名 / 型 / 参照先 /
リレーション名 / カスタム項目 / 絞り込み可 / 並べ替え可 / 選択肢 / 取得日時`
の 14 列。 **レコードの値は入らない** （ describe 摘要を見ない ） 。

- **全部取り直したいとき**: ファイルを消す。 次の実行でまた API から取り直す
- **1 オブジェクトだけ取り直したいとき**: 該当 (組織 / オブジェクト) の行を消す
  （ 組織と他の API 名の組み合わせごとに、 ヘッダー込みで 1 オブジェクト分 ）。
  該当オブジェクトは次の実行で API から取り直される
- **見出しが違う / 列数が壊れている** ときは、 ファイルを別名に退避してから
  再実行する。 退避せずもう一度実行すると CSVError で止まる

実行の終わりに INFO で `オブジェクトの describe: 保存データから N 件 /
Salesforce から N 件 / 取り直し N 件` のログが出る。 取り直しは **CSV に
古い項目定義が残っていて列対応に `(不明)` が残り、 レポートで使ったオブジェクト
が CSV から読んだもののとき** に API で取り直して 1 度だけレポートを再計算する
動作。 同じ `(組織, オブジェクト)` は 1 回の実行で 1 度しか取り直さない。

## 4. 出力ファイルの読み方

### `SOQL調査.xlsx` の構成

**まず 一覧 シートを見る**。 1 行が 1 件のレポート。 「 2000件超 」 「 個人情報 」
「 似たレポート 」 「 統合の見込み 」 「 取得できなかった項目数 」 「 警告数 」 「 SOQL状態 」
を機械判定した結果が出る。 そこから問題のあるレポートの 管理番号 を覚えて、
該当行を掘りに行く。

シートの並び （ この順 ） ：

1. 一覧
2. SOQL
3. 取得できなかった項目
4. 項目の対応
5. 条件
6. 集計
7. 似たレポート
8. 警告
9. 項目一覧
10. 関連

ヘッダー行は太字で固定される。 シート名で意味の分かる日本語名になっていて、
番号は付いていない。

#### 一覧

1 行が 1 件のレポート。 「 **まずここを見る** 」 シート。

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `レポートID` | record の `report_id` |
| `レポートタイプ` | `record.report["reportMetadata"]["reportType"]["type"]` |
| `主オブジェクト` | record の `main_object` （ 取得失敗などで特定できなかったときは `(不明)` ） |
| `形式` | `record.report["reportMetadata"]["reportFormat"]` |
| `出力列数` | 出力に出る列の数 （ detailColumns + groupings + 集計対象 ） |
| `2000件超` | `row_check.status` （ `超えている` / `超えていない` / `判定不可` / `未実施` ） |
| `行数` | `row_check.rows` が非 `None` のときだけ実際の行数 |
| `2000件超の補足` | `row_check.reason` |
| `個人情報` | `pii.status` （ `あり` / `要確認` / `なし` ） |
| `個人情報の該当列` | `pii.matching_columns` を `表示名(根拠)` の `; ` 区切りで最大 10 件 |
| `類似グループ` | 該当のグループの番号、 `基準` なら `<番号> (<基準の管理番号> 基準)` |
| `統合の見込み` | グループ内の統合の見込み |
| `取得できなかった項目数` | 「 取得できなかった項目 」 シートで該当 管理番号 が含まれていた件数 |
| `警告数` | `record.warnings` のうち 「 取得できなかった項目 」 シートに行かなかった件数 （ = describe 失敗以外の警告 ） |
| `SOQL状態` | `src.soql_builder.build_soql()` の判定結果。 `作成済み` / `要確認` / `一部作れず` / `作れず` |
| `件数チェック` | ツールが組み立てた SOQL の件数とレポートの総件数の突き合わせ結果。 `一致` / `不一致` / `確認できず` / `未実施` 。 不一致は 「 不一致（ レポート=N 件・SOQL=M 件 ）」 のように件数が出る |

#### SOQL

ツールが自動で組み立てた SOQL を 1 レポート 1 行で出すシート。 「 まずここを
見る 」 の次に、 ツールが作った SOQL を見るときに使う。

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `主オブジェクト` | record の `main_object` （ 取得失敗などで特定できなかったときは `(不明)` ） |
| `状態` | `作成済み` / `要確認` / `一部作れず` / `作れず` のいずれか |
| `件数チェック` | SOQL 件数とレポート総件数の突き合わせ結果。 `一致` / `不一致` / `確認できず` / `未実施` 。 確認できずのときは理由も入る |
| `レポート件数` | レポートの総件数 （ 確認できずのとき `確認できず` ）。 `topRows.rowLimit` が有るときは SOQL 側を `min(totalSize, limit)` で比べる |
| `SOQL件数` | SOQL の `SELECT COUNT()` の `totalSize` （ 確認できずのとき `確認できず` ） |
| `SOQL` | ツールが組み立てた SOQL 。 `作れず` / `一部作れず` のときは SOQL が不完全 ( 詳細は `作れなかった部分` と `要確認` を見る ) |
| `作れなかった部分` | 省略した列・条件・グルーピングなどの 1 件 1 行 ( 改行区切り ) |
| `要確認` | ス コープ / 標準フィルタ / 日時置換など、 人が実行前に判断する事項の 1 件 1 行 ( 改行区切り ) |

**SOQL はツールが自動で組み立てる。 作れなかった部分と要確認を必ず見る。**
本番に使う前に人が確認する。

**状態の決まり:**

- `作れず` … 主オブジェクト不明、 または SELECT に入れられる列が無い
- `一部作れず` … 条件を省いた / 集計のため SOQL に入れなかった など 「 作れなかった部分 」 が 1 件以上ある
- `要確認` … SOQL は完全だが、 ス コープや日時置換など人が判断する事項が 1 件以上ある
- `作成済み` … `作れなかった部分` も `要確認` も無い

**件数チェックの決まり:**

- `一致` … レポートの総件数と SOQL の件数（ `topRows.rowLimit` 有るときは `min(totalSize, limit)` ） が一致
- `不一致` … 両方の件数が取れたが 一致しない
- `確認できず` … レポートの総件数が取れない、 SOQL がエラー、 SOQL が `作れず` 等。 理由は `件数チェック` のセルに 「 `確認できず（SalesforceError: INVALID_FIELD: ...）` 」 の形で出る
- `未実施` … `[CHECKS] SOQL_COUNT = ×` で実行しなかった

**「 不一致・確認できずのものだけ人が見る 」 。 一致しているレポートでも列の
中身までは保証しない （ 値の突合はあくまでこのツールの範囲外 ）。**

#### 取得できなかった項目

| 列 | 中身 |
|---|---|
| `種別` | `項目` または `オブジェクト` |
| `主オブジェクト` | record の `main_object` （ `項目` ） または オブジェクト名 （ `オブジェクト` ） |
| `列キー` | `項目` のときのレポート列キー （ `オブジェクト` のときは空 ） |
| `表示名` | `項目` のときのレポートの表示名 （ `オブジェクト` のときは空 ） |
| `理由` | `項目` のときの理由 （ 「 表示名一致せず 」 / 「 関連オブジェクト経由 」 / 「 複数候補あり: ... 」 / 「 同じレポート内で表示名が重複 」 ） または `オブジェクト` のときの describe 失敗の理由 |
| `件数` | 何レポートで該当したか （ 同じ `(主オブジェクト, 列キー, 理由)` が複数レポートにあればここに積まれる ） |
| `管理番号` | 該当した 管理番号 を `|` 区切りで |

並びは 件数 ( 降順 ) → 種別 → 主オブジェクト → 列キー。

#### 項目の対応

`column_map` のうち、 `対応フィールドAPI名` が解決できた列を **全体で 1 行ずつ**
にまとめた表。 1 行 = `(主オブジェクト, SOQL列名)` で、 同じ `(主, SOQL列名)`
は 1 行に集約される。 「 取得できなかった項目 」 シート ( 解決できなかった列 )
はここには出ない。

| 列 | 中身 |
|---|---|
| `主オブジェクト` | record の `main_object` |
| `SOQL列名` | `column_map` の `対応フィールドAPI名` |
| `表示名` | 最多 （ 同数なら管理番号の小さいレポートのもの ） 。 異なる表示名があれば 備考に「 別の表示名あり: 」 の形で並ぶ |
| `型` | `column_map` の `型` |
| `参照先オブジェクト` | 参照項目のとき `referenceTo` を `|` 区切り |
| `個人情報` | 出力列について機械判定した PII 結果。 `あり` / `要確認` / 空 |
| `個人情報の根拠` | 判定理由。 `型 email` / `キーワード『電話』` 等 |
| `使っているレポート数` | 何レポートで該当したか |
| `管理番号` | 該当した 管理番号 を `|` 区切りで |
| `備考` | 別の表示名一覧 （ 「 別の表示名あり: 顧客名（1002）, 顧客氏名（1003）」 等 ） |

並びは 主オブジェクト → SOQL列名。

#### 条件

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `レポートID` | record の `report_id` |
| `種別` | `絞り込み` / `組立式` / `日付` / `標準フィルタ` / `クロス` / `上位N` |
| `番号` | 種別ごとの連番 （ `絞り込み` なら `1` から ） |
| `列キー` | 絞り込み列キー （ `絞り込み` ） または 日付列キー （ `日付` ） |
| `項目` | column_map で解決した SOQL 名 （ `絞り込み` のときに埋まる、 解決できなければ空 ） |
| `演算子` | 絞り込み演算子 |
| `値` | 絞り込み値、 組立式なら `1 AND (2 OR 3)` のまま、 日付なら `開始〜終了`、 クロスなら `primaryEntityField operator relatedEntity.relatedEntityJoinField (criteria)` |
| `備考` | 種別ごとの補足 （ 例: 日付の `durationValue` ） |

#### 集計

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `レポートID` | record の `report_id` |
| `種別` | `形式` / `グルーピング(行)` / `グルーピング(列)` / `集計` / `並び順` / `バケット` / `独自計算式` |
| `順` | 種別ごとの連番 |
| `名前` | 集計式やグルーピング名 |
| `内容` | 並び順やバケット値、 独自計算式のラベルなど |

#### 似たレポート

似たレポートを同じグループにまとめて、 1 ペア 1 行で 「 区分 」 と
「 基準との違い 」 を出したもの。 グループに入らなかったレポートは出ない。

| 列 | 中身 |
|---|---|
| `類似グループ` | グループ番号 |
| `管理番号` | この行のレポートの管理番号 |
| `概要` | この行のレポートの概要 |
| `レポートID` | この行のレポートの ID |
| `基準の管理番号` | グループの基準（ 最小の管理番号 ） のレポート |
| `区分` | `基準`（ 基準自身の行 ） / `同一` / `条件のみ違い` / `列のみ違い` / `近い` |
| `基準との違い` | 区分が `基準` 以外なら 人が読める 1 文。 例: `値: AMOUNT greater 100 → 200`、 `追加: STAGE equals Closed`、 `出力列の類似度 0.85` |
| `統合の見込み` | `1本にまとめられる` / `条件を引数にして1本にできそう` / `要確認` のいずれか。 区分 `基準` の行は空 |

該当グループが無ければ シートは見出しだけになる （ 0 件のデータ行 ）。

判定のロジック:

- **同一** … 構造 （ レポートタイプ・形式・出力列・グルーピング・集計・並び順 ）
  も同じで 条件（ 絞り込み・組立式・日付・標準フィルタ・クロス・上位 N・ scope ）
  も同じ。 ID 違いで 1 本にまとめられる
- **条件のみ違い** … 構造は同じで 条件が違う
  - 値だけ違う（ 同じ列キー・同じ演算子で値だけ ） / 日付の範囲だけ違う →
    `条件を引数にして1本にできそう`
  - その他 → `要確認`
- **列のみ違い** … 条件は同じで 出力列の集合が違う
  （ 片方がもう片方を含むときは 「 含む 」 と diff_text に書く ）
  → 統合の見込みは `要確認`
- **近い** … 上のどれにも当たらないが、 出力列の Jaccard 類似度が
  `[SIMILAR] COLUMN_SIMILARITY`（ 既定 0.8 ） 以上
  → 統合の見込みは `要確認`

#### 警告

取得中に出た警告のうち、 **describe 失敗を除いた**もの。 describe 失敗は
「 取得できなかった項目 」 シートの `種別=オブジェクト` に行くので、 警告
シートには残らない。 2000 件チェックで `判定不可` だったときの理由もここに出る
（ 機微な情報は含めない ）。

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `レポートID` | record の `report_id` |
| `警告` | 1 警告 1 行 （ 例: 「 関連オブジェクトが 50 件あり上限 40 を超えたため、 次の 10 件は取得しません: … 」 ） |

#### 項目一覧

1 行が 1 つの項目。 AI に「どのフィールドが使えるか」を聞きたいときに。

| 列 | 中身 |
|---|---|
| `オブジェクト` | オブジェクトの API 名 |
| `段` | 主オブジェクトは `0`、 関連は record 内の `relations` の段 （ `1` / `2` / … ） |
| `オブジェクト表示名` | describe の `label` |
| `項目API名` | `name` |
| `項目表示名` | `label` |
| `型` | `type` |
| `参照先オブジェクト` | 参照項目なら `referenceTo` を `|` 区切り |
| `リレーション名` | `relationshipName` |
| `カスタム` | カスタム項目は `○` |
| `選択肢` | 選択肢のうち `active` のもの（30 件超なら末尾に `…`） |

並びは「 オブジェクト API 名の昇順 → describe の `fields` の並び順 」。

#### 関連

1 行が主＋関連の **取れた** オブジェクト同士の親→子の参照 1 本。

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `親オブジェクト` | 親オブジェクト API 名 |
| `参照項目API名` | 参照項目の API 名 |
| `リレーション名` | 参照項目の `relationshipName` |
| `子オブジェクト` | 子オブジェクト名 |
| `段` | **子の** 深さ （ 主 = 0 ） |

並びは **管理番号 → 段 → 親の出現順**。 上限で打ち切られた子・ describe 取得
に失敗した子はここにも出ない （ 項目一覧にも出ない ）。 ポリモーフィック参照は
`referenceTo` のエントリごとに 1 行ずつ。

### `列名の対応.csv` （ダウンローダー用）

ダウンローダー側は `COLUMN_NAMES = {"Amount": "金額", "Account.Name": "取引先名"}`
を各 SoqlReport に貼る （ キー = SOQL 結果の列名、 値 = 出力 CSV の見出し ）。
それを組み立てる材料。

| 列 | 中身 |
|---|---|
| `主オブジェクト` | record の `main_object` |
| `SOQL列名` | record の `column_map` の `対応フィールドAPI名` （ 解決できた列だけ ） |
| `表示名` | 最多 （ 同数なら管理番号の小さいレポートのもの ） 。 違う表示名が他にあれば 備考に「 別の表示名あり: 」 の形で並ぶ |
| `備考` | 別の表示名一覧 |
| `更新日` | 今回書いた日 （ `YYYY-MM-DD` ） |

- 1 行 = `(主オブジェクト, SOQL列名)` 。 管理番号の列は無い。
- **全レポート分を積み上げる**。 その回の実行で取得に成功した 管理番号 が
  解決した `(主オブジェクト, SOQL列名)` の行は今回の内容で入れ替わり、
  今回取らなかった／失敗した 管理番号 由来の既存の行はそのまま残る。
  並べは `主オブジェクト → SOQL列名` 。
- 既存ファイルの見出しが想定と違う （ 旧形式の `管理番号, 概要, SOQL列名,
  表示名, 備考` を含む ） ときは `CSVError` を上げ、 既存ファイルは変更
  しない。 「 別名に退避してから再実行 」 の対処が出る。
- `OUTPUT_DIR` は **ダウンローダーが読む場所** （ ダウンローダーの共有
  フォルダの `soql-collector` フォルダ ） にしておくと、 ダウンローダーは
  そのまま `列名の対応.csv` を `(主オブジェクト, SOQL列名)` で引いて使える。

## 5. ツールが作った SOQL を確認する手順

1. `実行.bat` を実行する
2. 出力先（ 既定 `./output` ） の `SOQL調査.xlsx` を Excel で開き、
   「 **一覧** 」 シートの `SOQL状態` 列で `作成済み` / `要確認` / `一部作れず`
   / `作れず` を確認する
3. `SOQL` シートで 該当 管理番号 の SOQL を見る。 `状態` が `作成済み` 以外
   のときは `作れなかった部分` / `要確認` も必ず見る
4. 「 一部作れず 」 / 「 作れず 」 のときは `条件` `集計` `取得できなかった項目`
   の各シートで、 `管理番号` 列でフィルタして詳細を確認する
5. `似たレポート` シートを見て、 似たレポートをまとめられそうなものを探す。
   統合の見込みが 「 1本にまとめられる 」 や 「 条件を引数にして1本に
   できそう 」 のレポートを優先する
6. ツールが作った SOQL は、 本番で実行する前に **必ず人が確認** する。
   `作成済み` でも `要確認` のチェック事項は適用される。
   `一部作れず` / `作れず` のときは AI や人が残りを補う（ SOQL を手書きで
   直す、or 条件を狭めるか分割実行を検討する ）

## 6. 限界

- レポート列の **表示名と、 項目の表示名が一致したもの** が `対応フィールドAPI名`
  に自動で埋まる。 それでも一致しないときは、 関連オブジェクトの項目ラベルとも
  突き合わせる。 それでもダメなら `(不明)` のまま残る。 そのような record は
  「 取得できなかった項目 」 シートを見る
- 集計（ `SUMMARY` / `MATRIX` ）やグルーピングつきのレポートは、 項目の対応
  だけでは SOQL の SELECT / HAVING を完全には再現できない。 その場合は
  `条件` `集計` シートを見ながら組み立てる
- `項目一覧` シートの `選択肢` は 30 件で切っている（ `…` で省略を表現 ）。
  30 を超えるリスト項目は `項目一覧` の `picklist` を確認すること （ active
  な値だけが **`picklist`** に入っており、 後ろに省略された件数は
  **`picklistTotal`** で分かる ）
- `関連` シートに出るのは **取れたオブジェクト同士の参照だけ** なので、 上限
  で打ち切られた子や、 describe の取得に失敗した子はここにも `項目一覧` にも
  出ない。 そのような経路は `警告` シートに名前が残る

## 6. 個人情報の判定について

判定は **機械的な目安** で、 最終判断は人が行う。 CSV とこのドキュメントに
そう明記する。 判定が曖昧なものは `要確認` / `判定不可` に倒す。

判定ルール（ 列単位 ）:

- `あり`
  - 項目の型が `email` / `phone` / `address` / `location`
  - 表示名または API 名がキーワードに一致 かつ 所属オブジェクトが
    個人系（ `Contact` / `Lead` / `User` / `Individual` / `PersonAccount` 、
    または `Account` で `IsPersonAccount` 項目を持つ ）
- `要確認`
  - キーワードに一致するが所属オブジェクトが個人系でない
  - 対応表で対応フィールドが引けなかった列
- 空 … 上のどれでもない

キーワード一致のさせ方は **単純な部分一致ではなく、 3 段階** で見る:

- **1 文字の日本語キーワード** （ `姓` / `名` ）: 表示名がキーワードと
  **完全一致** するときだけ一致 （ 前後の空白は除く ）。 API 名には
  適用しない。 `商談名` は `名` に **当たらない**
- **ASCII キーワード** （ `email` / `phone` / `city` / `state` / `zip` /
  `fax` / `birth` / `gender` / `mobile` / `street` / `postal` ）:
  API 名・表示名を **トークン** に分解 （ `_` / `__c` / 空白 /
  camelCase の切れ目 `BillingCity` → `Billing` `City` / 数字との切れ目 ）
  して、 いずれかのトークンがキーワードに **一致** するとき一致する。
  - 例: `BillingCity` ・ `City__c` ・ `Mailing State` は一致、
    `Capacity` ・ `Estate` ・ `Velocity` は **一致しない**
  - `birth` だけは **トークンの先頭一致** も許す （ `Birthdate` 、
    `BirthDate` 、 `Birth_Date` ）
- **上記以外の日本語キーワード** （ 2 文字以上 ）: 従来どおり
  **部分一致** （ 大文字小文字を無視 ）

`Account.Name` のように法人を表すオブジェクトの `Name` は キーワード
「 氏名 」 に一致しますが 個人系でないので `要確認` になる。 `Contact.Name`
は同じキーワード一致でも 個人系オブジェクトなので `あり` になる。

判定対象は レポートの **出力に出る列** だけ。 絞り込みにだけ使う列は
対象外（ その列の値が出力されないので、 個人情報露出のリスクが低いため ）。

`[PII] KEYWORDS` / `[PII] OBJECTS` で既定のキーワードと個人系オブジェクト
を置き換えられる。 未設定 / 空なら 既定値を使う。

`一覧` シートの `主オブジェクト` 列は、 `record.main_object` が **特定
できなかったとき** は `objects` dict の先頭キーで補完せず、 `(不明)` を入れる。

**レポートの行データ**（ 値そのもの ） は **メモリ上で件数を数えるだけ** で、
CSV / ログ / 警告 / 例外メッセージには絶対に出さない。 2000 件チェックで
`get` が呼ばれても、 戻り値の長さを取るだけで 中身は触らない。
