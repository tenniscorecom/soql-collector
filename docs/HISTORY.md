## 2026-11-06 … 保存データだけで作り直す入口を足す

- 以前の考え: ``input/列の直し.xlsx`` を直したら、 出力を作り直すには
  ``実行.bat`` をもう一度動かすしかなかった。 毎回 Salesforce にログインし
  （ レポート定義・項目定義を取り直す ） 、 2000 件チェックの API も呼ばれて
  いた
- いまの考え: ``python main.py --rebuild`` （ 同梱の ``直し反映.bat`` ） で
  **保存データだけで** 出力を作り直す。 レポート定義は ``data/レポート定義/``、
  項目定義は ``data/項目定義.csv`` から読み、 Salesforce には接続しない。
  件数チェックもしない。 **レポート定義** が保存データに無いレポートは、
  途中まで作った不完全な record を残さず失敗にする（ 実行.bat で取り直して
  ください ） 。 項目定義が無いオブジェクトは、 通常の実行で describe が 404
  などになったときと同じ扱い（ 警告を残して不明のまま ） 。 組織は通常の実行と
  同じく接続先クラスの ``DOMAIN_URL`` から決める。 保存データも書き換えない
- 理由: 列の直しのたびに Salesforce に接続していたため。 成功した describe は
  必ず保存されるので、 項目定義が無い ＝ 通常の実行でも取れなかったもの、
  とみなせる（ そこで失敗にすると、 通常の実行で出るレポートが作り直しでは
  毎回失敗する ）

## 2026-10-18 … レポートの describe を貯めて、 2 回目からは Salesforce に聞かない

- 以前の考え: オブジェクトの describe は ``data/項目定義.csv`` に貯めて再利用するが、 レポートの describe は
  毎回 Salesforce に聞く。 ``列の直し.xlsx`` を直してもう一度実行するたびに、 有効な全レポート分を取り直していた。
- いまの考え: SOQL 組立に要る部分だけに絞ったレポート定義と、 そのとき落としたキー名を、
  ``data/レポート定義/{組織}__{レポートID}.json`` に貯める（``src/report_store.py``）。 貯めてあれば
  ``describe`` を呼ばない。 行データは取らない（describe の応答に入っていない）。

  作り直したいときは ``レポート定義/`` フォルダ（または 1 ファイル）を消す。
- 壊れたファイル・書けない場所は、 警告を出して「貯めていない」扱いにする。 キャッシュは速くするためだけのもの。
- 案としては、 Report の ``LastModifiedDate`` を 1 回の SOQL で調べて、 更新があったものだけ取り直す方法がある
  （使う組織で ``Report`` を SOQL で引けるか未確認のため、 採っていない）。
- レポートの describe を飛ばしても、 Salesforce への接続（ログイン）は今までどおり行う
  （オブジェクトの describe や 2000 行チェックで、 接続が要ることがあるため）。

## 2026-10-18 … 管理表に「調査」列（任意）を足し、 調べない行の貯めたレポート定義を消す

- 以前の考え: 調べる行は、 管理表の「有効」列が ``○`` の行すべて。 個別に取りたいときは、 その行だけ ``○`` にして
  ほかを ``×`` にする。 ただし「有効」は、 ダウンローダーでは定期取得の対象を決める列でもある。
- いまの考え: 管理表に「調査」列（任意）を足すと、 「有効」のうち「調査」が ``○`` の行だけを調べる
  （``master.filter_survey_targets``）。 列が無い管理表は、 今までどおり「有効」だけで決まる。
  ``filter_enabled`` は、 これに置き換えて無くした。
- 調べない行（管理表から消えた・「有効」が ``×``・「調査」が ``○`` でない）の、 貯めたレポート定義
  （``data/レポート定義/``）を、 実行の最後に消す（``ReportStore.prune``、 ``run.PRUNE_REPORT_STORE``）。
- **消すのはレポート定義のキャッシュだけ。** ``列名の対応.csv`` は、 ダウンローダーとの契約で、 人が直した
  内容も含むので消さない。 ``SOQL資料/`` / ``関係図/`` は人が読むものなので、 古くなっても自動では消さない。
  ``項目定義.csv`` は、 組織全体で使い回すので消さない。
- 対象が 0 件のときは何も消さない（管理表を読み違えたときの保険）。
- 限界: 「調査」を付け外しして試すと、 外した間にキャッシュが消えて、 付け直したときに取り直しになる。
- 前提: ``ReportStore``（レポートの describe を貯める変更）が先に入っていること。


## 2026-10-18 … 調査はサンドボックスで取る（管理表は本番の URL のまま）

- 以前の考え: 管理表の URL のホスト名から接続先の組織が決まる。 サンドボックスで調べたいときは、
  collector 用に、サンドボックスの URL を載せた管理表を別に持つ。
- いまの考え: 管理表は本番の URL のまま 1 レポート 1 行。 collector は ``site_for(url, sandbox=True)`` で、
  本番の組織に対応するサンドボックスへつなぐ（``fetch.SURVEY_ON_SANDBOX``、 既定 ``True``）。
- 理由: 管理表を 2 つ持つと、 行が二重になり、 「有効」列の意味（調査する / 定期取得する）もぶつかる。
  組織を人が選ぶ列は作らない（URL と食い違うと、 別の組織へ問い合わせて「見つからない」になるため）。
- describe の保存の「組織」は、 管理表の URL ではなく、 実際につないだ組織で決める（``_org_of``）。
  ``org_from_url`` は comken の ``host_of`` に委ねる（``lightning.force.com`` と ``my.salesforce.com`` を同じ組織にする）。
- 限界: サンドボックスに同じ ID のレポートがある前提。 サンドボックスのデータは本番と違うので、
  件数に依存する判定（2000 件超）は参考値になる。
- comken の ``site_for(sandbox=...)`` と ``comken.toolbox.salesforce.hosts`` が前提（comken の同じ変更が先に必要）。

## 2026-11-02 … SOQL の構文を修正する

- いまの考え: 組立式と日付条件が並ぶときは組立式全体を ``( ... )`` で囲む。
  組立式は使える語と括弧の深さを検査し、 書けないときは WHERE 全体を出さない。
  日時の境界・``LIKE`` のエスケープ・演算子の表記ゆれ・型ごとの制約は
  ``src/soql_builder.py`` の定数と専用関数にまとめる
- 理由: 壊れた SOQL をそのまま出さないため。 実行時に失敗するかもしれないものは
  「missing」 ではなく「checks」 で知らせる（ Bulk API で使えない ``TYPEOF`` は
  生成しない ）

## 2026-11-02 … 表示名の接頭辞が参照項目を指すときの照合を一般化する

## 2026-11-06 … 生成する SOQL レポート Python ファイルに USE_BULK を出す

- いまの考え: 生成する ``.py`` のクラスに ``USE_BULK`` を 1 行加える。 値は常に
  ``True`` で、 レポートの内容からは決めない。 置く場所は ``REPORT_ID`` の行の
  直後（ ``REPORT_ID`` が無いときは ``NAME``、 どちらも無いときは ``KEY`` の
  直後） で、 ``COLUMN_NAMES`` より前
- 理由: 取り方（ Bulk API 2.0 か 通常の SOQL か ） をレポートごとに人が直せる
  ようにするため。 集計関数（ ``COUNT`` / ``SUM`` 等 ） や ``GROUP BY`` を使う
  SOQL は Bulk API で取れない
