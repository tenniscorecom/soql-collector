# 経緯のメモ

コード内のコメントから抜いた、 設計が変わった日付と理由を 1 項目ずつ並べたもの。
コードを読むときはここの存在を前提にしなくてよい （経緯は確認したい人だけ） 。
判断が変わったらここに追記する。

## 2026-10-16 … ``src.mapping`` をパッケージに分割

- 以前の考え: ``mapping.py`` を 1 ファイルで持っていた。 手順ごとのテストの
  分割がしづらかった
- いまの考え: ``src/mapping/`` パッケージに手順ごとのサブモジュールへ。
  公開 API は ``src.mapping`` から再エクスポートするので、 既存の
  ``from src.mapping import X`` はそのまま動く
- 理由: 1 関数あたりの複雑度を下げるため。 ``mccabe`` の実測最大が
  ``build_relation_chains`` の 14 で、 これからも手順で分割する方針

## 2026-10-16 … config.ini の既定値補完を廃止

- 以前の考え: 必須キーが無くても comken 側で既定値を補完していた
- いまの考え: 補完せず ``ConfigError`` （``ConfigKeyNotFoundError``） で止める
- 理由: 「触ってよい値」 と 「触ってはいけない値」 を混ぜないため

## 2026-10-15 … シート構成を 3 枚に集約

- 以前の考え: ``SOQL調査.xlsx`` に 9 枚のシートがあった
- いまの考え: 3 枚 （一覧 / 列の対応 / 関係図） に集約。 集計 / 条件 /
  グループ・並び順は 「列の対応」 シートで SOQL として表現し、
  ``SOQL資料/{管理番号}.md`` に集約
- 理由: 完成形を 1 か所にまとめ、 人が 「直す場所」 を 1 つに絞るため

## 2026-10-15 … SOQL の下書きを復活

- 以前の考え: SOQL は AI に Markdown を渡して組み立ててもらう方針だった
- いまの考え: 安全策つきで下書きを作る。 主が取れない / 組立式が解釈できない /
  履歴スナップショットがあるときは本文の 1 行目に ``【未完成】…`` の印を入れ、
  そのまま Salesforce に投げると構文エラーになるようにした
- 理由: AI だけに頼らず 1 次ソースを出せるようにし、 かつ危険なものを物理的に
  実行できないようにするため。 印は定数 ``INCOMPLETE_MARKER``
  （``src/soql_builder.py``） で、 ダウンローダー側が実行前に止める

## 2026-10-15 … ``coerce_str`` を ``src.text_utils`` に集約

- 以前の考え: ``_coerce_str`` が各モジュールに重複していた
- いまの考え: ``src.text_utils.coerce_str`` に集約。 境界
  （API / openpyxl / CSV） でだけ使う
- 理由: 重複定義の解消

## 2026-10-15 … 人が ``直したSOQL列名`` を入れた列を優先

- 以前の考え: 自動が取った列を上書きするには 「列の対応」 シートを直接触る
  必要があった
- いまの考え: 「直したSOQL列名」 に値があれば自動の結果より常に優先。 自動の
  値より人の値が尊重される。 「メモ」 も上書きしない
- 理由: 「直す場所」 を ``input/列の直し.xlsx`` 1 か所に絞る

## 2026-10-14 … 列キーからの主オブジェクト・SOQL 列名の解決

- 以前の考え: 主オブジェクトの API 名を知らないと SOQL 列名が引けなかった
- いまの考え: 列キー （ ``Contact.Account.Name`` / ``Contact.Retention__c.Status__c``
  のような形 ） から主オブジェクトと SOQL 列名を経路でたどって取る。 カスタム
  レポートタイプで人が主オブジェクトを知らなくても列名を引けるようにするため
- 理由: 人が主オブジェクトを事前入力しなくて済むようにするため

## 2026-10-14 … ``FK_`` 接頭辞の列も主からの経路として解決

- 以前の考え: ``FK_<参照先>.<残りの経路>`` の列は別経路として扱っていた
- いまの考え: 主オブジェクトの参照項目から ``<参照先>`` への
  ``relationshipName`` を取り、 残りは列キーたどりと同じ流れで解いて
  ``<relationshipName>.<残りの SOQL>`` にする。 候補が複数あれば備考に最大
  5 件並べて表示名照合には進まない
- 理由: ``FK_`` 付きの列も同じ扱いで一貫させるため

## 2026-10-14 … 列キー先頭のフォールバックで主オブジェクトを引く

- 以前の考え: ``reportType.type`` から主オブジェクトが取れなかったときは失敗に
  していた
- いまの考え: ``reportType.type`` の候補が全滅したとき、 列キー先頭
  （``.`` を含む列キーの最初の ``.`` より前） を代替候補として最大 5 個試す。
  ``FK_`` で始まる列キーの先頭は主オブジェクトではなく参照先なので候補から外す
- 理由: カスタムレポートタイプのレポートタイプ自体が主オブジェクトの API 名で
  ないケースに備える

## 2026-10-14 … レポート 1 本につき ``SOQL資料/{管理番号}.md`` を出力

- 以前の考え: AI に ``一覧`` / ``集計`` / ``条件`` / ``項目の対応`` / ``項目一覧``
  / ``関連`` シートを渡して SOQL を組み立ててもらう形だった
- いまの考え: レポート 1 本につき 1 つの Markdown を ``OUTPUT_DIR/SOQL資料/`` に
  書いて、 AI に貼る資料にする
- 理由: AI に渡すのに Markdown の方が読みやすいから

## 2026-10-14 … 末端 reference を ``nameField`` に置換

- 以前の考え: 関連オブジェクト末端の参照項目は素の API 名のまま使っていた
- いまの考え: 末端 reference を ``nameField`` に置換して表示名解決に使う
- 理由: 列キーから SOQL 列名を一意に引けるようにするため
## 2026-10-18 … ``_`` は「そのファイルの中だけで使う」印にそろえた

- 以前の考え: ``mapping/`` に分けたとき、別ファイルから使うクラス ``_ChainCandidate`` が ``_`` 付きのまま
  ``column_key.py`` / ``column_map.py`` / ``__init__.py`` から import されていた。
- いまの考え: ``_`` は定義したファイルの中だけで使う印。別ファイルから使う内部の関数・クラスには付けない
  （comken の ``docs/CONVENTIONS_PYTHON.md`` の命名規則と同じ）。``ChainCandidate`` にした。
- comken 側で ``_get_or_build_config`` / ``_default_config_path`` などが ``_`` なしになったので、
  ``tests/comken_state.py`` の参照も合わせた（comken のこの変更より前のタグでは動かない）。
- ``tests/test_private_naming.py`` が、別ファイルからの ``_`` 付きの使用を検出する。

## 2026-10-18 … レポートの describe を貯めて、 2 回目からは Salesforce に聞かない

- 以前の考え: オブジェクトの describe は ``data/項目定義.csv`` に貯めて再利用するが、 レポートの describe は
  毎回 Salesforce に聞く。 ``列の直し.xlsx`` を直してもう一度実行するたびに、 有効な全レポート分を取り直していた。
- いまの考え: SOQL 組立に要る部分だけに絞ったレポート定義と、 そのとき落としたキー名を、
  ``data/レポート定義/{組織}__{レポートID}.json`` に貯める（``src/report_store.py``）。 貯めてあれば
  ``describe`` を呼ばない。 行データは取らない（describe の応答に入っていない）。
- **期限は付けない。** 調査はサンドボックスで行い、 本番のレポートを直しながら回す使い方ではないため。
  作り直したいときは ``レポート定義/`` フォルダ（または 1 ファイル）を消す。
- 壊れたファイル・書けない場所は、 警告を出して「貯めていない」扱いにする。 キャッシュは速くするためだけのもの。
- 案としては、 Report の ``LastModifiedDate`` を 1 回の SOQL で調べて、 更新があったものだけ取り直す方法がある
  （使う組織で ``Report`` を SOQL で引けるか未確認のため、 採っていない）。
- レポートの describe を飛ばしても、 Salesforce への接続（ログイン）は今までどおり行う
  （オブジェクトの describe や 2000 行チェックで、 接続が要ることがあるため）。
