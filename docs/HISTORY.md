# 経緯のメモ

コード内のコメントから抜いた、 設計が変わった日付と理由を 1 項目ずつ並べたもの。
コードを読むときはここの存在を前提にしなくてよい （経緯は確認したい人だけ） 。
判断が変わったらここに追記する。

## 2026-11-13 … 日時の境界は日本時間（+09:00）にする

- いまの考え: `datetime` 項目に日付だけの値を入れるとき、 境界は
  `YYYY-MM-DDT00:00:00+09:00` / `YYYY-MM-DDT23:59:59+09:00` にする。
  `checks` にも 「日本時間の 0 時として扱った」 と書く
- 理由: レポートの絞り込みは日本時間なので、 UTC の 0 時だと 9 時間ずれて
  レポートと違う範囲を取る。 時差つきの表記なら SOQL 側で日本時間として
  解釈される

## 2026-11-13 … 「含まない」は (NOT f LIKE '%v%') にする

- いまの考え: `notContain` は `(NOT f LIKE '%v%')` の形にする。 複数値は
  NOT LIKE を 1 つずつ括弧で囲んで AND でつなぐ
  （ `((NOT f LIKE '%a%') AND (NOT f LIKE '%b%'))` ）
- 理由: `NOT (f LIKE '%v%')` は SOQL で通らない（ 実地で確認した ）。 NOT LIKE
  も 1 つずつ括弧で囲まないと SOQL が通らない（ 実地で確認した ）

## 2026-11-13 … 子の列は副問い合わせでも取れるようにする

- いまの考え: 子の列があるときは、 優先順位で形を決める。 **A** 人が
  「直したSOQL列名」に `<子リレーション名>.<子の項目>` と書いた列がある
  → **B** 人の指定が無くても 子の列と クロスフィルタがある
  → **C** それ以外 は 「子から取る」 形。 A・B は FROM を親のままにして
  SELECT の中に子リレーションの副問い合わせを 1 つ入れる
- 理由: 「子から取る」 形では、 クロスフィルタの副問い合わせが使えず
  （ 変換できないので missing になる ） 取り方を Bulk のままにできない。
  副問い合わせにすれば 両方を解決できて、 子の列の値も comken の
  `query()` と同じ `Contacts.LastName` の形で得られる

## 2026-11-11 … 管理番号 と件数を 数値で書く

## 2026-11-11 … 管理表の「RPA使用」列を 記録用として読む

- いまの考え: 管理表の任意列「RPA使用」（ `○` / `×` ）を 読み、

## 2026-11-11 … 管理表の「集計形式」列を 確認用として読む

- いまの考え: 管理表の任意列「集計形式」（ `サマリー` / `マトリックス` / `無し` ）を
  読み、 `ReportRecord.report_format` に入れて 一覧シートと Markdown に出す。
  管理表の値と レポートの `reportMetadata.reportFormat` が 両方そろっていて
  違うときだけ、 警告を 1 件出す
- 理由: 形式はレポート定義から分かるので、 管理表の値は **人の記入の確認用** に
  なる。 集計かどうかの判断は 今までどおり `reportFormat` で行う（ 管理表の値は
  判断に使わない ） 。 人が記入した値とレポートが食い違えば気づけるように、
  警告だけ出す
- ただし: 列は任意。 列が無い管理表・空欄は 記入なし（ `None` ） として扱い、
  照合もしない。 `サマリー` / `マトリックス` / `無し` 以外の値を書いた行は
  記入なしにして WARNING を 1 件出す（ 行は捨てない ）
- 対応表: 管理表の「集計形式」列の値 → レポートの `reportFormat` は
  サマリー=SUMMARY / マトリックス=MATRIX / 無し=TABULAR 。 読み取りの判定は
  `src/master.py` の 1 か所で行う
- 伴って: `ReportRecord` に `report_format` を足した。 取り方（ Bulk / 通常
  SOQL ）や状態は変えない

## 2026-11-11 … 管理表の「2000件超」列に「不明」を書けるようにする

- いまの考え: 管理表の「2000件超」列は ○ / × に加えて「不明」を書ける。
  「不明」は空欄と同じ扱い（ 件数が分からない） で、 列が無いときと同じ判定になる
- 理由: 「×」は「本番の件数が 2000 件以下だと分かっている」を表す。 分からない
  ときに × と読むと「2000 件以下」に取り違えるので、 分からないことを表す別の語
  （ 「不明」 ） を用意する
- ただし: 「不明」の判定は 管理表の読み取り 1 か所（ ``src/master.py`` ） で行う。
  件数の区分は 3 段判定の 3 段目（ 列が無い・空 と同じ ） に入る

## 2026-11-11 … 取り方（ Bulk / 通常 SOQL ） を件数で決める

- いまの考え: 取り方は、 副問い合わせの有無と件数で決める。 件数は管理表の
  「2000件超」列（ 本番の件数を知っている人が書く ） を 1 段目、 サンドボックスの
  2000 行チェックを 2 段目として、 3 段で判定する
- 理由: 1000 件を超えるレポートは Bulk で取る想定だから。 1000 件以下は通常 SOQL
  で取る。 サンドボックスの 2000 行チェックは本番の件数ではない（ サンドボックスで
  2000 件以下でも本番では超えることがある ） ので、 決め手にはしない
- 取り方: 副問い合わせなしなら 1000 件超（ 2000 件超 を含む ） で Bulk、 1000 件以下
  で通常 SOQL、 不明なら Bulk
- 副問い合わせあり: 常に通常 SOQL。 理由は 副問い合わせの SOQL を Bulk API 2.0 で
  動作確認していないため、 確実に動かせる REST を選ぶ
- ただし: 副問い合わせがあり、 2000 件超 または 不明 のときは、 「本番の件数が
  5000 件を超えるなら SOQL を分ける」 を要確認に 1 件足す
- ただし: 管理表の「2000件超」列は任意。 列が無い管理表では サンドボックスの
  2000 行チェックだけで判定する
- 閾値: 1000 件（ Bulk の境目 ） と 5000 件（ 副問い合わせがあるときの通常 SOQL の
  上限 ） は コードの定数（ ``src/row_size.py`` ）。 設定ファイルには出さない

## 2026-11-10 … 件数に関係なく全レポートの SOQL を作る

- いまの考え: 件数で SOQL を作るかどうかを分けない。 件数が少ない
  レポートにも SOQL を作る
- 理由: 件数が少ないレポートも SOQL で取りたいため。 ユーザー判断
  （ 2026-11-10 ）。 件数で飛ばすと、 列の直しの対象からも外れて
  後から SOQL が要ったときに一から確かめ直しになる
- ただし: 件数の判定 （ 2000 行チェック ） は残す。 一覧の 「2000件超」 列と
  件数比較に使うので、 SOQL を作れるか否かには使っていない

## 2026-11-09 … レポートの列が子の項目のときは、 SOQL を子から取る

- 以前の考え: レポートの主オブジェクト（ 親 ） を FROM にして、 子の列は
  サブクエリ （ ``SELECT (SELECT ... FROM Contacts) FROM Account`` ） で
  取っていた。 サブクエリは Bulk API 2.0 で取れるか確認していないので、
  取り方が REST  （ ``USE_BULK = False`` ） になっていた
- いまの考え: レポートの行が 1 行ずつ示すオブジェクト（ 子 ） を FROM にする。
  ``SELECT Account.Name, Name FROM Contact`` の形。 レポートと同じ 1 行 1 子の
  粒になり、 Bulk のまま取れて、 ダウンローダーの変更も要らない
- 理由: サブクエリは Bulk で取れるか分からず、 取り方を読む人が
  「REST にするしかない」 と思うと、 取り方を考える手間が増える。 レポートの
  粒が子なら、 最初から子から取ったほうがレポートと件数も合う
- ただし: レポートの列が指す子が 2 つ以上 （ あるいは同じ子への参照が複数 ）
  のときは切り替えられない。 推測で FROM を変えるとレポート以上の件数を取る
  ので、 そのまま `(不明)` のまま 【未完成】 にする
- 伴って: `ReportRecord` に `soql_from_object` を足した。 `main_object` は
  レポートの親のまま変えない（ 資料の「主オブジェクト」 は親のまま ） 。
  `列名の対応.csv` の主オブジェクト列だけは FROM の値にする
  （ ダウンローダーが「最初の FROM」 から主オブジェクトを引くため ）

## 2026-11-09 … 子リレーションは、手入力の CSV でも足せるようにする

- 以前の考え: 子リレーションは Salesforce の describe だけから得た
- いまの考え: `input/子リレーション.csv` に人が手入力した行も、 主オブジェクトの
  describe の `childRelationships` に足す
- 理由: 会社の中の情報は開発側に持ち出せない。 describe が取れない /
  持てないオブジェクトの繋がりを、 人が会社側で Excel を使って入力できるように
  した。 値は SOQL と .py に入るので、 識別子 （ 英字・数字・`_` だけ ） に限る
- 伴って: 手入力の要素は結合項目の describe 確認を省略してよい。 子の describe
  が無くても criteria が空なら副問い合わせにできる。 criteria が有ると列の型が
  分からないので 「確認できず」 にする

## 2026-11-09 … 同じ表示名の候補が複数あるときは、 最短経路の候補を自動採用する

- 以前の考え: 同じ表示名の候補が複数あると、 必ず 「複数候補あり」 で止まって
  人に選んでもらっていた
- いまの考え: 主オブジェクトに最も近い候補 （ 経路の段数が最少 ） が 1 つに
  決まるなら自動採用する。 同じ段数で並んだら従来どおり 「複数候補あり」 で
  止める
- 理由: 主オブジェクトの項目は、 関連オブジェクトの項目より事故が少ない。
  段数が最短なら「たぶん主の項目」で進める価値がある。 ただし断定はできない
  ので、 状態は **要確認** のままにして、 他の候補を 「候補」 列に出し、
  `列の直し.xlsx` で人能直せるようにする
- 伴って: 自動で確定した列は、 SOQL の `checks` に 1 件 1 行で出す。 件数比較
  では値の違いを検出できないため

## 2026-11-06 … 保存データだけで作り直す入口を足す

- 以前の考え: ``input/列の直し.xlsx`` を直したら、 出力を作り直すには
  ``実行.bat`` をもう一度動かすしかなかった。 毎回 Salesforce にログインし
  （ レポート定義・項目定義を取り直す ） 、 2000 件チェックの API も呼ばれて
  いた
- いまの考え: ``python main.py --rebuild`` （ 同梱の ``直し反映.bat`` ） で
  **保存データだけで** 出力を作り直す。 レポート定義は ``data/レポート定義/``、
  項目定義は ``data/項目定義.csv`` から読み、 Salesforce には接続しない。
  件数チェックもしない。 **レポート定義** が保存データに無いレポートは、
  途中まで作った不完全な record を残さず失敗にする（ 実行.bat で取り直して
  ください ） 。 項目定義が無いオブジェクトは、 通常の実行で describe が 404
  などになったときと同じ扱い（ 警告を残して不明のまま ） 。 組織は通常の実行と
  同じく接続先クラスの ``DOMAIN_URL`` から決める。 保存データも書き換えない
- 理由: 列の直しのたびに Salesforce に接続していたため。 成功した describe は
  必ず保存されるので、 項目定義が無い ＝ 通常の実行でも取れなかったもの、
  とみなせる（ そこで失敗にすると、 通常の実行で出るレポートが作り直しでは
  毎回失敗する ）

## 2026-10-14 … ``FK_`` 接頭辞の列も主からの経路として解決

- 以前の考え: ``FK_<参照先>.<残りの経路>`` の列は別経路として扱っていた
- いまの考え: 主オブジェクトの参照項目から ``<参照先>`` への

  5 件並べて表示名照合には進まない
- 理由: ``FK_`` 付きの列も同じ扱いで一貫させるため

## 2026-10-14 … 列キー先頭のフォールバックで主オブジェクトを引く

- 以前の考え: ``reportType.type`` から主オブジェクトが取れなかったときは失敗に
  していた
- いまの考え: ``reportType.type`` の候補が全滅したとき、 列キー先頭
  （``.`` を含む列キーの最初の ``.`` より前） を代替候補として最大 5 個試す。

## 2026-11-09 … クロスフィルタを副問い合わせにして、 取り方を自動判定する

- 以前の考え: ``crossFilters`` は SOQL に訳せず、 必ず「未完成」 にする。
  取り方（ ``USE_BULK`` ） も常に ``True`` で、 人が直すものだった
- いまの考え: ``crossFilters`` の要素（ 公式仕様の形。 実物では未確認 ） から
  ``<主側項目> IN (SELECT <結合項目> FROM <子オブジェクト> WHERE ...)`` を作る。

  副問い合わせは 1 文に 2 個まで。 REST にする理由は WHERE の副問い合わせを

- 理由: クロスフィルタを退化させるとレポート以上の件数を取る危険があるため、
  全部を自動にしない。 変換できたものだけ取り方を自動で決める。 子リレーションと

  従来どおり「未完成」 にする。 理由は「レポートと意味が変わるのを防ぐ」ため。

  あるので、 直接つながるものに限って変換する
- 追加: 子リレーションの「取得済み 0 件」と「未取得」を区別する。 子が 0 件の
