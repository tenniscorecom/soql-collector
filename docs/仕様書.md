# 仕様書

## 1. 目的

Salesforce のレポートごとに、 レポート describe と 主オブジェクト +
関連オブジェクトの describe を取って **メモリ上の記録 （``ReportRecord``）**
にし、 そこから人が Excel で見る ``SOQL調査.xlsx`` とダウンローダー用
``列名の対応.csv`` を生成する。 **SOQL の下書き** も組み立てる
（2026-10-15 復活、 安全策つき）。 主オブジェクトが取れないとき・組立式が
解釈できないとき・履歴スナップショットがあるときは SOQL は未完成になり、
本文の 1 行目に `INCOMPLETE_MARKER` （`【未完成】…`） を入れてそのまま
Salesforce に投げると構文エラーになるようにしている。

レポートごとに次の 4 つを機械判定し、 xlsx に出す。 判定は **目安** で、
最終判断は人が行う。 曖昧なものは 「要確認」 / 「判定不可」 に倒す。

1. **似たレポートをまとめられるか** … 同一 / 条件のみ違い / 列のみ違い / 近い
2. **2000 件を超えているか** … 超えている / 超えていない / 判定不可 / 未実施
3. **個人情報を含むか** … あり / 要確認 / なし
4. **取得できなかった項目** … 項目 / オブジェクト

**レポートの行データ**（値そのもの、 個人情報を含みうる） は **メモリ上で
件数を数えるだけ** で、 CSV / ログ / 警告 / 例外メッセージには絶対に出さない。
保存もしない。

## 2. 処理フロー

レポートとオブジェクトの describe を **加工せず原本のまま** 保存し、 出力は保存データだけから
作る。 取得（接続する）と解析（接続しない）を分ける。

| 入口 | 接続 | 内容 |
|---|---|---|
| `実行.bat` / `python main.py` | する | 取得の段のあと解析の段を通す |
| `取得.bat` / `python main.py --fetch` | する | 保存に無いものだけ取る。 出力は作らない |
| `全部取り直し.bat` / `python main.py --fetch --force` | する | 全部取り直して上書きする。 出力は作らない |
| `解析.bat` / `python main.py --analyze` | しない | 保存データだけで出力を作る |

それ以外の引数は終了コード 2 。

```
python main.py [引数]
   ├─ 引数が上の形でない -> エラー（終了コード 2）
   ├─ comken.runtime.is_dry_run() が真なら -> 接続も書き込みもせず、
   │   管理番号・レポートID・出力先をログに出すだけ （終了コード 0）
   ├─ 管理表 ( Excel ) を読む
   │   → 「有効」が ○ の行を全部対象にする
   │   → 0 件 -> 終了コード 2
   ├─ 列の直し.xlsx と 子リレーション.csv を読む （見出し違いで終了コード 2）
   ├─ 取得の段（--analyze 以外）
   │   ID ごとに、 解析と同じ経路を通して必要な原本を保存する
   │     主オブジェクト / 関連オブジェクト / 列キーのたどり / 列の直しの経路 /
   │     クロスフィルタの子 / 子から取る形の子
   │   保存にあるものは API を呼ばない。 件数も同じ
   │   今回調べないレポートの保存を消す （取得の段だけ）
   └─ 解析の段（--fetch 以外）
       接続しないクライアントで同じ経路を通し、 ReportRecord に詰める
       ReportRecord の一覧から、 OUTPUT_DIR に
         SOQL調査.xlsx / 列名の対応.csv / AIチャット用/ /
         SOQL資料/{管理番号}.md / 関係図/{主オブジェクト}.md /
         SOQLレポート/report_{管理番号}.py
       を書く
       列の直し.xlsx に今回の結果をマージして書く
       （空のセル・新しい行だけ埋める、 PermissionError は WARNING だけ）
```

`実行.bat` は取得の段と解析の段を順に実際に通す。 解析の結果が常に保存データだけから作られ、
`--fetch` のあとの `--analyze` と同じになる。 取得で失敗したレポートがあっても、 解析は
保存にある分で進み、 終了コードは失敗を反映する。

### 元データの保存

保存先は `[FILES] DESCRIBE_CSV_PATH` の親フォルダの下（キーの名前は既存の config.ini を
壊さないためそのまま。 そのファイル自体は作らない）。

| パス | 中身 |
|---|---|
| `元データ/レポート/{組織}__{レポートID}.json` | `client.report.describe` の返り値そのまま |
| `元データ/オブジェクト/{組織}__{オブジェクト名の小文字}.json` | `describe_object` の返り値そのまま |
| `元データ/件数.csv` | 組織 / レポートID / 判定 / 行数 / 理由 / 取得日時。 行データは保存しない |

JSON の形は `{"形式": 1, "組織": ..., "取得日時": ..., "原本": <API の返り値そのまま>}`。
一時ファイルに書いてから置き換えるので、 途中で止まっても半端なファイルは残らない。
壊れたファイルは警告を出して「無いもの」として扱う。

- **取得の段**: 保存にあるものは API を呼ばない。 `--force` は実行の最初に保存を見ないだけで、
  同じ実行の中で同じオブジェクトは 1 回だけ取る。 取り直しに失敗したものの保存は残る
- **API の失敗は保存しない**（次の取得でやり直す）。 同じ実行の中では 1 回だけ試す。
  401 / 403 はその ID の失敗。 件数の 「判定不可」 のうち、 形式のせいで判定できないもの
  （結合レポートなど）だけは何度取っても同じなので保存し、 通信エラーなどは保存しない
- **解析の段**: `site_for` は `DOMAIN_URL` を読むだけで、 サイトクラスを作らない（ログインしない）。
  原本を `make_slim_report` / `make_slim_object` で絞ってから今の処理に渡す。
  `collect_dropped_keys` も原本から作る。 件数は `件数.csv` から `RowCheck` に戻す
  （行が無ければ `row_check` なし）。 保存データは一切書き換えない
- レポートの原本が無いレポートは `OfflineApiError` で失敗にする（途中まで作った record は残さない。
  終了コード 1）。 メッセージは 「保存データに無いので 取得.bat で取ってください（足りないもの: …）」
- オブジェクトの原本が無いときは `OfflineDescribeMissing` を送り、 取得の段の describe 失敗
  （404 など）と同じ経路で処理する（失敗をメモリにだけ覚えて警告を 1 つ残し、 `None` を返す）。
  メッセージは 「オブジェクト {名前} は保存データに無い（取得.bat で取れることがあります）」
- 組織は **接続先クラスの `DOMAIN_URL`** から決める（保存データのファイル名から推測しない）
- 取得の段の終わりに API の呼び出し回数（レポート describe / 件数 / オブジェクト describe）をログに出す
- 古い保存データ（`data/項目定義.csv`、 `data/子リレーション.csv`、 `data/レポート定義/`）は
  読まず、 自動で消さない

### AI チャット用のファイル

解析の段で `OUTPUT_DIR/AIチャット用/` を書く（保存した原本から作り、 接続しない）。

| ファイル | 中身 |
|---|---|
| `はじめに.md` | 各ファイルの説明・読む順・頼み方の例・注意 |
| `一覧.csv` / `列の対応.csv` | `SOQL調査.xlsx` の同名シートと同じ |
| `子リレーション.csv` | 親 / リレーション名 / 子 / 参照項目 / 出どころ（Salesforce・手入力）。 主オブジェクトの分 |
| `項目定義/{オブジェクト}.csv` | 今回のレポートで使ったオブジェクト（主・関連・クロスフィルタの子・子から取る形の子）の全項目 |

- CSV は UTF-8 BOM、 Markdown は UTF-8
- **1 ファイル 100,000 バイトまで**（`AI_FILE_MAX_BYTES`）。 CSV は行の切れ目で `Account_1.csv` のように
  分け、 各ファイルに見出しを付ける。 `SOQL資料/{管理番号}.md` は `## ` の切れ目で
  `{管理番号}_2.md` 以降に分ける。 1 行で上限を超えるものは分けられないので警告を出す
- `SOQL資料/{管理番号}.md` の冒頭 「このレポートで一緒に渡すファイル」 に、 分割後のファイル名を載せる
- 分割の数が減ったときに古いファイルが残らないよう、 書く前に前回の分を消す

## 3. ReportRecord の形（メモリ上の記録）

### トップレベル

```python
@dataclass(frozen=True)
class ReportRecord:
    key: str            # 管理番号
    summary: str        # 概要
    report_id: str      # レポート ID
    url: str            # レポート URL
    main_object: str | None  # 主オブジェクト名（取得失敗なら None）
    report: dict[str, Any]   # レポート describe を slim した dict
    objects: dict[str, dict[str, Any]]  # 主＋関連オブジェクト describe を slim した dict
    relations: tuple[RelationRecord, ...]  # 主＋関連オブジェクト同士の参照
    column_map: list[dict[str, str]]  # 列対応表
    warnings: tuple[str, ...]  # 警告メッセージ
    row_check: RowCheck | None  # 2000 行チェック結果
    pii: pii.ReportPIIResult   # レポート単位の PII 評価結果
    soql_draft: SoqlDraft | None  # SOQL の下書き（無いときは None）
    cross_filter_objects: dict[str, dict[str, Any]]  # 副問い合わせに使う子オブジェクト describe
    soql_from_object: str | None  # SOQL の FROM に使うオブジェクト名（無ければ主オブジェクト）
    soql_from_relationship: str  # 子から取る形にしたときの、子から親へ戻るリレーション名
    exceeds_row_limit: bool | None  # 管理表の「2000件超」列（True / False / None=不明）
    report_format: str | None  # 管理表の「集計形式」列（サマリー / マトリックス / 無し / None=記入なし）
```

`cross_filter_objects` は クロスフィルタの副問い合わせに使う子オブジェクトの
describe を入れる。 キー = 子オブジェクト名。 **`objects` には入れない**
（ 関係図・関連表・対応表の出力を変えないため ） 。

`soql_from_object` は 「子の列を子から取る」 にしたときの FROM のオブジェクト名。
`None` のときは主オブジェクト。 **`main_object` は変えない** （ 資料の
「主オブジェクト」 はレポートの親のまま出す ） 。

`exceeds_row_limit` は 管理表の「2000件超」列の値。 `True` = 本番で 2000 件超、
`False` = 2000 件以下、 `None` = 列が無い・セルが空・「不明」と書いてある（ 不明 ） 。
取り方（ Bulk / 通常 SOQL ） の判定に使う（ 「取り方（ Bulk / REST ）」 節）。

`report_format` は 管理表の「集計形式」列の値。 `サマリー` / `マトリックス` /
`無し` のどれか。 `None` = 列が無い・セルが空・3 つ以外の値を書いた（ 記入なし ） 。
**集計かどうかの判断には使わない** （ 判断は `reportMetadata.reportFormat` で
する ） 。 管理表の値とレポートの形式が両方そろっていて違うときだけ、 警告を
1 件出す（ 警告表 = 一覧シートの 「警告」 列 ）。

### `row_check`

```python
@dataclass(frozen=True)
class RowCheck:
    status: str            # "超えている" / "超えていない" / "判定不可" / "未実施"
    rows: int | None       # "超えていない" のときだけ実際の行数
    reason: str | None     # "判定不可" の理由
```

`status` の遷移:

| 状況 | status | rows | reason |
|---|---|---|---|
| `client.report.get()` が `SalesforceReportTruncatedError` を上げた | `超えている` | `None` | `None` |
| 正常終了（`len(table)` を取れる） | `超えていない` | 行数 | `None` |
| `client.report.get()` が `SalesforceError`（取れない形式） | `判定不可` | `None` | `この形式のレポートは取得できないため判定できません（結合レポート・明細の列が無いレポートなど）` |
| `client.report.get()` が 401 / 403 由来 | （ID 全体が失敗） | | |
| その他の `SalesforceError` | `判定不可` | `None` | `<例外名>: <短い説明（200 字上限）>` |
| その他の例外（タイムアウト等） | `判定不可` | `None` | `<例外名>: <短い説明>` |
| `ROW_LIMIT_ENABLED = False` （コードの定数） | `None` | | |

行データ（値そのもの） はどこにも保存しない。 `get` の戻り値は `len()` だけ
取り、 中身は触らない。

**件数は `元データ/件数.csv` に保存する。** 取得の段は行があれば `report.get` を呼ばず、
解析の段はここから同じ判定を作る。 保存が無いときは `row_check` なし（ `None` ） のまま。

行データ（値そのもの） はどこにも保存しない。 `get` の戻り値は `len()` だけ
取り、 中身は触らない。

### `pii`

```python
@dataclass(frozen=True)
class ReportPIIResult:
    status: str                                  # "あり" / "要確認" / "なし"
    matching_columns: tuple[tuple[str, str], ...]  # (表示名, 根拠) 最大 10 件
```

### `pii`

判定は `pii.py` の純粋関数で、 レポートの **出力に出る列** （ `detailColumns`
/ `groupingsDown` / `groupingsAcross` / 集計対象 ） だけを対象にする。
絞り込みにだけ使う列は対象外。

### `report`

`client.report.describe(report_id)` の戻り値を **allowlist 方式** で絞った
もの。 次の **2 つのキーだけ** 含む:

| キー | 型 | 意味 |
|---|---|---|
| `reportMetadata` | dict | 元の `reportMetadata` のうち、 `REPORT_METADATA_KEYS` （機械判定に必要な SELECT / WHERE / 日付 / サブクエリ / GROUP BY / 集計 / ORDER BY / 独自グループ / 独自計算式に必要な 21 個） にあるキーだけを**そのまま**残した dict |
| `reportExtendedMetadata` | dict | `detailColumnInfo` / `groupingColumnInfo` / `aggregateColumnInfo` の 3 キーだけを**そのまま**残した dict |

許可リストで落としたキー名は **この dict には残さず**、 `warnings` に
「レポート定義の中で使わなかったキー: k1, k2, k3」 の形で 1 行入れる
（最初の本番実行で、 必要なものを間違って落としていないか確かめる用） 。

`reportMetadata` / `reportExtendedMetadata` が無い / dict でない / `None`
/ 文字列でも例外を上げない（そのキーは結果に出ない） 。

### `objects`

`describe_object` の戻り値を **allowlist 方式** で絞ったもの。 各オブジェクトは
次の 5 キーだけ:

| キー | 型 | 意味 |
|---|---|---|
| `name` | str | オブジェクト API 名 |
| `label` | str | オブジェクト表示名 |
| `custom` | bool | カスタムオブジェクトか |
| `fields` | list[dict] | 項目を **slim した** 形（下の ``fields`` セクション） |
| `childRelationships` | list[dict] | 子リレーション（ `childSObject` / `field` / `relationshipName` の 3 キー） 。 `relationshipName` が空の要素は落的とした |

`recordTypeInfos` / `urls` / `supportedScopes` / `layoutable` などの重いキーや
管理用キーは**最初から record に入らない**。

`childRelationships` は 副問い合わせ（ クロスフィルタ ） の材料として残す。
原本にそのまま入っているので、 取り直しは要らない。

### `fields` （各項目）

各項目は次の **8 キーだけ** （**この順**）:

| キー | 型 | 意味 |
|---|---|---|
| `name` | `str` | 項目 API 名 |
| `label` | `str` | 項目表示名 |
| `type` | `str` | 項目の型 |
| `custom` | `bool` | カスタム項目か |
| `referenceTo` | `list[str]` | 参照先のオブジェクト名（ポリモーフィックなら複数） |
| `relationshipName` | `str \| None` | リレーション名（SOQL で `Account.Name` のように辿る名前） |
| `picklist` | `list[str]` | 元の `picklistValues` のうち `active` が真の `value` を最大 30 件 |
| `picklistTotal` | `int` | `active` な選択肢の総数（`picklist` が 30 件に切られているとき、 後ろにどれだけ省略されたか） |

`picklistValues` / `inlineHelpText` / `length` などのキーや、 配列の項目詳細
（`controllerName` など）は record に出ない。 関連項目と名前を保存しない
ので、 関連オブジェクト収集は **slim 前** の `referenceTo` /
`relationshipName` で行う。

### `relations`

``RelationRecord`` の tuple （主＋関連オブジェクト同士の親→子参照） 。 各
要素は `parent` / `field` / `relationship_name` / `child` / `depth` を
持つ。 ポリモーフィックな参照は `referenceTo` のエントリごとに 1 本ずつ。

### `column_map` の各行

| キー | 型 | 意味 |
|---|---|---|
| `列キー` | `str` | レポートの列キー |
| `表示名` | `str` | 列の表示名 |
| `所属オブジェクト` | `str` | その項目を持つオブジェクト名 |
| `対応フィールドAPI名` | `str` | 解決できた SOQL 名（関連経由ならリレーション鎖つきドット記法） |
| `型` | `str` | 項目の型 |
| `参照先オブジェクト` | `str` | 所属オブジェクト側で `referenceTo` を `|` 区切り |
| `リレーション名` | `str` | 所属オブジェクト側で `relationshipName` |
| `備考` | `str` | 「関連オブジェクト経由」「列キーの接頭辞で絞り込み」「複数候補あり: ...」「対応フィールドなし」 等の注記 |

## 4. 関連オブジェクトの決め方

主オブジェクト describe の `fields` から次の条件に合う項目を抜き出し、
その `referenceTo` を **`RELATED_DEPTH` 段まで幅優先** で集める。

- `relationshipName` が空でない （SOQL で `Account.Name` のように辿る名前がある）
- `referenceTo` が空でないリスト
- 一般的な参照はリスト内の全エントリを採用

掘り方は **幅優先** :

- 0 段目 = 主オブジェクト自身。 1 段目は主オブジェクトの参照、
  k+1 段目は k 段目で取ったオブジェクトの参照を掘る
- 一度取った（または取ろうとした） オブジェクトは重複して取りにくい。
  主オブジェクト自身は最初から対象外 （`visited` に最初に入れておく）
- 循環参照（A→B→A など） は **既出なので掘らない** で止まる
- `RELATED_DEPTH` 段目まで掘る （`1` なら 1 段だけ、 今までの挙動）

件数は `RELATED_MAX` で **全段の合計** を打ち切り、 超えた名前は
`warnings` に残す。 近い段から優先的に取るので、 深い段のものは自動で諦める。
警告の形式:

```
関連オブジェクトが {全体} 件あり上限 {RELATED_MAX} を超えたため、
{スキップ数} 件は取得しません: {名前, ...}
```

`skipped` は **重複を除いた出現順**。 同じ名前が複数回候補になっても 1 回しか
数えない。

主オブジェクトの describe 自体が HTTP エラー（401 / 403 以外） で取れなかった
ときは `主オブジェクト: null` とし、 関連オブジェクトは取らない（警告は残る） 。

`relations` には **取れたオブジェクト同士の参照** だけが出る。 BFS で
「どのオブジェクトを取ったか」 を決めたあと、 別の処理で主＋関連オブジェクト
の `fields` を 主→関連（段順） の順でたどって組み立てる。 1 行が 1 本の
親→子の参照で、 次の形:

```
RelationRecord(
    parent=親オブジェクト API 名,
    field=参照項目の API 名,
    relationship_name=relationshipName （無ければ None）,
    child=子オブジェクト名,
    depth=子の段 （主 = 0）,
)
```

行の `段` は **子の段** （主 = 0）。 主＋関連の **取れた** オブジェクト
同士の参照を **全部** 載せる。 つまり、 主オブジェクト自身への参照
（例: `Account.TaskId → Task`） や自己参照 （ 例: `Account.ParentId →
Account`） も **出る** 。 並びは「 浅い方の親 （主→段順） → 同じ
親内では項目の出現順 」 。 一般的な参照は `referenceTo` の各エントリごとに
1 行ずつ。 同じ `（親, 項目, 子）` は 1 行。 上限で打ち切られた子、
describe 取得に失敗した子、 `RELATED_DEPTH` の外側は
**行に含まれない** （`warnings` か error log に名前だけ残る） — 親としても
子としても行に出ない。

### 手入力の子リレーション（ `input/子リレーション.csv` ）

会社の中の情報は開発側に持ち出せないので、 人が会社側で CSV に手入力して
使えるようにしている。 場所は **`[FILES] COLUMN_FIX_XLSX_PATH` と同じフォルダ**
（ 標準では `input/子リレーション.csv` ） 。

| 列 | 意味 |
|---|---|
| `親オブジェクト` | 主オブジェクト名 |
| `リレーション名` | 子リレーション名（ 例 `Contacts` ） |
| `子オブジェクト` | 子オブジェクト名（ 例 `Contact` ） |
| `参照項目` | 親を参照する子の項目名（ 例 `AccountId` ） |
| `メモ` | 自由欄。 SOQL には入らない |

- 取得の段でファイルが無ければ、 **見出しだけのファイルを作る** 。
  `--analyze` は作らない。 読むのは両方
- 文字コードは comken の CSV に任せる。 読み込みは cp932 と UTF-8 （ BOM 付き ）
  のどちらも読める。 新しく作るときは UTF-8 BOM つき
- 見出しが違うときは **例外で止める** （ `列の直し.xlsx` と同じ扱い。 `run()` は
  終了コード 2 ）

**使える行の制限。** 値は SOQL と生成 .py に入るので、 `親オブジェクト` /
`リレーション名` / `子オブジェクト` / `参照項目` は
`^[A-Za-z_][A-Za-z0-9_]*$` に限る。 どれかが空の行と、 _IDENTIFIER_ に
合わない行は **使わず、 警告を出す** 。

**主オブジェクトの describe へ合わせる。** 親が一致（大文字小文字無視）する行を、
`(子オブジェクト, 参照項目)` が同じ既存要素があれば置き換え、 無ければ足す。
足した要素・置き換えた要素には `"手入力": True` を付ける（ 出所として区別する
ため ） 。 この処理は 1 関数（ `src/child_relationship_csv.py` の
`merge_manual_child_relationships()` ） にまとめる。

- 手入力の値は **保存する原本（ `元データ/` ） には書かない**

**クロスフィルタの判定への反映。** 手入力の要素は、 結合項目の describe 確認を
省略してよい。

- 子の describe が有る場合は、 従来どおり確認する。 `reason` に
  「手入力の子リレーション（子の describe で確認した）」 が付く
- 子の describe が無い場合は、 `criteria` が空リスト `[]` のときだけ
  副問い合わせにできる（ 結合項目は手入力の値を使う ）。 `criteria` が有ると
  列の型が分からないので `確認できず` になる。 `reason` に 「手入力」 が付く
- 手入力で分かる子の describe も、 通常の取得部品（ ストアのキャッシュ → API ）
  で取りに行く（ `src/fetch/site_run.py` の `_collect_cross_filter_objects()` ）

**出力への反映。**

1. **Markdown の 「子リレーション（サブクエリの材料）」 の表** に
   「出どころ」 列を足す。 値は `Salesforce` / `手入力`
2. **Markdown の 「クロスフィルタの繋がり」 の表** の `reason` と、
   **生成 .py のコメント** に 「手入力」 が出る

### `SOQL調査.xlsx`

毎回その回の結果で丸ごと作り直す。 comken の `Excel` クラス
（`comken.toolbox.excel`） で書き、 ヘッダー行は太字で固定される。
シート名 （表示順） :

1. `一覧`
2. `取得できなかった項目`
3. `項目の対応`
4. `条件`
5. `集計`
6. `似たレポート`
7. `警告`
8. `項目一覧`
9. `関連`

（該当グループの無いサンプルデータは warn シートは見出しだけ 、 `似たレポート` シートも 0 件のときは見出しだけになる）

シート名の日本語は短い名で番号を付けない。

#### `一覧` シート

| 列 | 中身 |
|---|---|
| `管理番号` | record の `key` |
| `概要` | record の `summary` |
| `レポートID` | record の `report_id` |
| `レポートタイプ` | `record.report["reportMetadata"]["reportType"]["type"]` |
| `主オブジェクト` | record の `main_object` （取得失敗などで特定できなかったときは `(不明)` 。 `objects` dict の先頭キーで補完はしない） |
| `SOQLの状態` | `record.soql_draft.status` （ `作成済み` / `要確認` / `一部作れず` / `作れず` ）。 下書きが無いときは空 |
| `取り方` | `Bulk` / `REST（理由）` 。 理由は 通常 SOQL にした理由（ 副問い合わせ / 件数が 1000 件以下 ）。 下書きが無いときは空 |
| `クロスフィルタの繋がり` | クロスフィルタの判定の件数。 件数が 0 でない判定だけを `直接2・直接でない1・確認できず1` の形で並べる。 判定が無ければ空 |
| `形式` | `record.report["reportMetadata"]["reportFormat"]` |
| `出力列数` | 出力に出る列の数 （detailColumns + groupings + 集計対象） |
| `集計形式（管理表）` | 管理表の「集計形式」列の値（ `サマリー` / `マトリックス` / `無し` ）。 記入が無ければ `(未記入)` |
| `2000件超` | `row_check.status` |
| `2000件超の補足` | `row_check.reason` |
| `個人情報` | `pii.status` （`あり` / `要確認` / `なし`） |
| `個人情報の該当列` | `pii.matching_columns` を `表示名(根拠)` の `; ` 区切りで最大 10 件 |
| `類似グループ` | 該当のグループの番号、 `基準` なら `<番号> (<基準の管理番号> 基準)` |
| `統合の見込み` | グループ内の統合の見込み |
| `似たSOQL` | 生成した SOQL が似ている相手。 相手ごとに `<管理番号>: <区分>（<違い>）` を `; ` 区切りで並べる。 区分は `SOQL同一` / `WHERE以降が同じ` / `WHEREだけ違う` 。 比較するのは `作成済み` と `要確認` の SOQL だけで、 `作れず` と `一部作れず` は比べない（ 条件を一部省いた SOQL は似ていても当てにならない ）。 200 文字を超えたら 197 文字＋`…` に切る。 中身は `src/soql_similar.py` が判定する |
| `取得できなかった項目数` | 「取得できなかった項目」 シートに含まれた件数 （同一 管理番号 内、 重複は 1 件と数える） |
| `警告数` | `record.warnings` のうち describe 失敗以外 の数 |

一覧シートの実際の列と順番は `src/tables/constants.py` の `SURVEY_COLUMNS` が正。

#### `取得できなかった項目` シート

重複は (主オブジェクト, 列キー, 理由) (種 別が `項目` のとき) または
(主オブジェクト, 理由) (種別が `オブジェクト` のとき) の単位でまとめる。

- 種別 `項目`:
  - `column_map` の `対応フィールドAPI名` が `(不明)` の行。 理由は
    `column_map.備考` （ 例: 「表示名一致せず」 / 「関連オブジェクト経由」 /
    「複数候補あり: ...」 / 「対応フィールドなし」 )
  - 同じ record 内で同じ表示名が複数回現れている列。 理由は
    「同じレポート内で表示名が重複」 。 表示名がぶつかったものは
    「取得できなかった項目」 シートに行くが、 同じ (主, SOQL列名) は
    `項目の対応` シートにも 1 行出る
- 種別 `オブジェクト`:
  - describe に失敗したオブジェクト。 理由は 「 オブジェクト X の
    describe に失敗 」 の警告文から X と理由を抜き出したもの
  - 重複の単位は (主オブジェクト, 理由)

並びは 件数 (降順) → 種別 → 主オブジェクト → 列キー 。

#### `項目の対応` シート

`column_map` のうち、 `対応フィールドAPI名` が解決できた列を
``(主オブジェクト, SOQL列名)`` で集約した表。

| 列 | 中身 |
|---|---|
| `主オブジェクト` | record の `main_object` （無ければ `(不明)`） |
| `SOQL列名` | `column_map.対応フィールドAPI名` |
| `表示名` | 最多 （同数なら管理番号の小さいレポートのもの） |
| `型` | `column_map.型` （最小 管理番号 のレコードのもの） |
| `参照先オブジェクト` | `column_map.参照先オブジェクト` |
| `個人情報` | 出力列について機械判定した PII 結果。 `あり` / `要確認` / 空 |
| `個人情報の根拠` | 判定理由 |
| `使っているレポート数` | 何レポートで該当したか |
| `管理番号` | 該当した 管理番号 を `|` 区切り |
| `備考` | 別の表示名一覧 （ 「別の表示名あり: 顧客名（1002）, 顧客氏名（1003）」 ） |

並びは 主オブジェクト → SOQL列名 。 「取得できなかった項目」 シートに出た
(不明) 列や describe 失敗 はここには出ない。

#### `条件` / `集計` / `警告` シート

「取得できなかった」 調査シートの `列名の対応表` 、 `項目表` 、 `関連表` 、
`条件表` 、 `集計表` 、 `警告表` の各列を 1 シートずつに持つ。 列構成は同じ
だが、管理番号でフィルタしやすいよう `管理番号` 列は左側に置く。

- `条件` シート: 1 レポートを **複数行に分ける** （ `管理番号 → 種別ごと` に
  1 行 ）。
  - 種別: `絞り込み` / `組立式` / `日付` / `標準フィルタ` / `クロス` / `上位N`
  - 項目列: `column_map` で解決した SOQL 名 （`絞り込み` のときのみ）
- `集計` シート: `形式` / `グルーピング(行)` / `グルーピング(列)` / `集計`
  / `並び順` / `バケット` / `独自計算式`
- `警告` シート: `record.warnings` のうち `種別 = オブジェクト`
  （describe 失敗） を除いたもの。 describe 失敗は 「取得できなかった項目」 シートに行く

#### `似たレポート` シート

似たレポートを同じグループにまとめて、 1 ペア 1 行で 「区分」 と
「基準との違い」 を出したもの。 グループに入らなかったレポートは出ない。
`基準` 自身の行も出力される。 似たレポート判定の閾値は
`[SIMILAR] COLUMN_SIMILARITY` の閾値（既定 0.8） はコードの定数
`SIMILAR_COLUMN_SIMILARITY` （`src/run.py`） にある。

#### `項目一覧` / `関連` シート

- `項目一覧` シート: オブジェクト × 項目のフラット表。
  - 並びは 「record の `objects` のキー名の昇順 → describe の `fields` の並び順」 。
  - `段` は主オブジェクト `0`、 関連は `relations` の `段` 列の値
- `関連` シート: **主＋関連** の取れたオブジェクト同士の親→子の参照 1 本ごと。
  - 並びは **管理番号 → 段 → 親の出現順** 。
  - ポリモーフィック参照は `referenceTo` のエントリごとに 1 行ずつ。
  - 上限で打ち切られた子・ `describe` 取得に失敗した子はここにも `項目一覧`
    にも出ない

### `列名の対応.csv`

UTF-8 BOM + CRLF。 comken の `CSV` クラスで書き出す。

| 列 | 中身 |
|---|---|
| `主オブジェクト` | record の `main_object` |
| `SOQL列名` | `column_map.対応フィールドAPI名` （解決できた列だけ） |
| `表示名` | 最多 （同数なら管理番号の小さいレポートのもの） |
| `備考` | 別の表示名一覧 |
| `更新日` | `YYYY-MM-DD` |

- 1 行 = ``(主オブジェクト, SOQL列名)`` 。 管理番号の列は持たない。
- 解決できた列を 1 行ずつ出し、 表示名がレポートによって違うと 備考に
  「別の表示名あり:」 の形で並ぶ。
- **積み上げ** フィールド: 毎回 record が来た 管理番号 が解決した
  ``(主オブジェクト, SOQL列名)`` の行を今回の内容で入れ替え、 それ以外は
  そのまま残す。 並べは **主オブジェクト → SOQL列名** 。
- 既存ファイルが無いときは今回の結果だけを書く。
- 既存ファイルの見出しが想定と違ったり読めなかったりしたときは `CSVError` を上げ、
  既存ファイルは変更しない。
- 既存の record が何も取れなかった （`ok_keys` が空） ときは、 何も追加も
  上書きもせず、 既存ファイルをそのまま残す。

### 列名の対応.csv への 「別形式」 対応

古いプロジェクトでは `列名の対応.csv` が見出し違い （ 例: `管理番号, 概要,
SOQL列名, 表示名, 備考` ） の場合がある。 本実装ではその見出しを検知すると
``対処: ファイルを別名に退避してから再実行してください。`` のメッセージで
``CSVError`` を上げ、 既存ファイルは上書きしない。

### `列の対応.csv`

人が Excel で開いて手で見比べる列の対応表。 `[FILES] COLUMN_MAP_CSV_PATH`
（例: `./data/列の対応.csv`） に置かれる。 自動の列対応
（`mapping.build_column_map`） で対応が取れない列や、 自動の対応が間違って
いるときに使う。

列 （この順） :

1. `主オブジェクト`
2. `列キー`
3. `表示名`
4. `SOQL列名`
5. `メモ`
6. `使っているレポート数`
7. `更新日`

**運用ルール:**

- 手で入れるのは **自動で取れなかった（ `対応フィールドAPI名` が空か
  `(不明)` の ） 列だけ** 。 自動で取れた列は CSV の値を信用せず、 自動の
  結果を優先する。 人が入れていた値は自動の結果で置き換えられ、 WARNING
  としてログに出る
- 自動で取れなかった列は CSV の `SOQL列名` があれば使い、 `型` は
  `Account.Name` のようなドット記法を `record.objects` からたどって引く。
  引けないときは 「打ち間違い？」 WARNING を出して値はそのまま使う
- `表示名` は毎回レポートの表示名で上書きする
- `メモ` は自動が取れた行は空に、 取れず人の手で埋まった行は `手入力` に
  戻す。 取れずそのまま空のときは今回の取れなかった理由が入る
- `使っているレポート数` と `更新日` は今回用いた行で毎回書き換える。
  今回出てこなかった行は丸ごとそのまま残る
- 並びは `主オブジェクト` → `列キー` （大小比較無視）
- 見出し違いの既存ファイルは `CSVError` で止め、 既存ファイルは変更しない
- 書き込みが `PermissionError` のときは実行は止めず WARNING だけ出し、 他の
  出力 （`SOQL調査.xlsx` / `列名の対応.csv`） はそのまま作る

## 6. 書き方の制約

- xlsx は comken の `Excel` クラス （`comken.toolbox.excel`） で書き、
  ヘッダー行は太字で固定される。 列幅・交互の縞模様・オートフィルタは
  comken の API に無いため、 ここでは適用しない （ その代わり、 列ごとに
  そのまま読めるデータが出るように整形している ）。
- `列名の対応.csv` は UTF-8 BOM つき + CRLF。 comken の `CSV` クラスの
  既定で新規ファイルは BOM 付きで書かれる。
- 文字コードはこのプロジェクトの CSV が必ず UTF-8 BOM 付きで書かれることを
  前提にする。
- 失敗した record （`record is None`） の per-id CSV は作らない。
  全体 xlsx / csv は取れた record だけから組み立てる。 ただし `列名の対応.csv`
  の **積み上げ** のために 今回 record が来た 管理番号 集合は保持される
  （取れなかった 管理番号 の行はそのまま残る） 。

## 7. 失敗の扱い（ID ごと・終了コード）

| 失敗ケース | 振る舞い |
|---|---|
| 引数が決まった形でない | 終了コード `2`、 何も取らない |
| 管理表に「有効」が `○` の行が無い | 終了コード `2` |
| `report_id_from_url` が `SalesforceReportIDNotFoundError` を上げた | その ID だけ失敗（`status="failed"`）。 他の ID は続ける |
| `site_for(url)` が `ComkenError` （`SalesforceError` 含む） | その ID だけ失敗。 他の ID は続ける |
| レポート describe の `SalesforceRequestError` | 原本を保存せず警告を出す。 終了コード `1`。 解析の段では原本が無いので失敗になる |
| 主オブジェクト describe の **401 / 403** | その ID だけ失敗（record は作らない） |
| 関連オブジェクト describe の **401 / 403** | その ID だけ失敗 |
| 主オブジェクト / 関連オブジェクト describe の **401 / 403 以外の HTTP エラー** | 警告にして他のオブジェクトは続ける（record は作られる） |
| 2000 行チェックで `client.report.get()` が 401 / 403 由来の `SalesforceError` | ID 全体失敗（レポート API へのアクセス拒否） |
| 2000 行チェックで その他のエラー | `判定不可` に縮退し、 record は作られる。 `warnings` に理由が 1 行追加される |
| CSV / xlsx 書き出しの失敗 | `run_tables` が例外を投げるが、 `run` 側で握ってログに残す （record は取れているので、 全体は失敗扱いにしない） |
| `--analyze` で レポートの原本が保存データに無い | その ID だけ失敗（`status="failed"`）。 他の ID は続ける。 終了コード `1` |
| `--analyze` で オブジェクトの原本が保存データに無い | その ID は失敗にしない。 取得の段の describe 失敗と同じ扱い（ 警告を 1 つ残し、 そのオブジェクトは不明のまま。 record は作られる ） |

`run` の終了コードは、 失敗が **1 件でも** あれば `1`、 全件成功なら `0`、
引数エラー / 設定・対象の不足は `2` 。

## 8. ログに出すもの

- xlsx の書き出し: シートごとの行数 （一見として）
- `列名の対応.csv` の書き出し: ファイル名と行数
- Salesforce への接続エラー: HTTP ステータスコード + 詳細
- 2000 件チェックで 判定不可 理由: 例外名と短い説明（200 字以内）
describe の中身 （`fields` の `name` や `picklist` の値） はログに出さない
（機微な情報が漏れないように） 。 レポートの行データも **絶対に出さない** 。

```
main.py                      ← 薄い入口（src.run.run() を呼ぶだけ）
src/
  run.py                     ← 取得の段と解析の段 / 管理表 / fetch / tables を束ねる
  raw_store.py               ← 原本の JSON の読み書き
```

## 10. 所有者を User とみなす

Salesforce の `Owner` 項目はポリモーフィックで、 `referenceTo` に `Group`
（キュー） と `User` の両方が並ぶことがある。 レポートの表示は所有者を
User として見せるので、 **所有者系の項目は User として辿る** 。 判定は
`src/mapping/owner.py` の `is_owner_user_field()` 1 か所にまとめ、
列キー経路（`src/mapping/column_key.py`） と 「列の直し.xlsx」 経路
（`src/column_fix_xlsx.py`） の両方から使う。 他のポリモーフィック参照の
挙動は変えない。

| 対象 | 規則 |
|---|---|
| 参照先の候補 | 所有者項目では `User` を先に試す（引けなければ次の候補へ） |
| リレーション鎖 | 主オブジェクトから User への鎖が複数（ `CreatedBy` / `LastModifiedBy` / `Owner` ） あるときは `Owner` を採る。 項目の並びには依存しない |
| 表示名の接頭辞 | 「X: 項目名」 の X が主オブジェクトの参照項目を指すとき（ 参照項目の表示名から末尾の ` ID` / `ID` を除いたものと一致するか、 その表示名や `relationshipName` で終わるとき。 例: `所有者` `ケース所有者` `Opportunity Owner` `作成者` `ケース作成者` `最終更新者` ）、 その参照項目の `relationshipName` 経由（ 参照先は User など ） の項目だけを表示名で照合する。 解ければ `CreatedBy.Title` のようになる。 一致する参照項目が無いときは従来の照合に進む |
| 列キーの予備 | 既存の手順（列キー → `FK_` → 表示名） で `match` が取れなかったとき（失敗または複数候補）に限り、 大文字小文字を無視して次を試す。 `OWNER` / `OWNER_NAME` / `OWNER_FULL_NAME` / `CUST_OWNER_NAME` は `Owner.Name` に、 `OWNER.<項目>` / `OWNER_<項目>` は User に同じ名前の項目があれば `Owner.<実際の項目名>` にする。 備考は `所有者を User とみなして解決` |
| 末端項目の型 | 列キー経路の末端項目を主オブジェクトから名前で探すと別の項目に当たることがある（ `Case.Owner.Type` が `Case.Type` の型になる） 。 経路で引けた型を優先する |
| 注意書き | 主オブジェクト直下の `Owner` が 2 つ以上の `referenceTo` を持ち、 SOQL 列名が `Owner.<X>` で X が次の共通項目に無いとき、 備考に `OWNER_POLYMORPHIC_NOTE`（ `Owner はキュー等も指せるため User だけの項目は SOQL で失敗する場合あり` ） を足す。 `build_soql` はその備考を持つ列を SELECT・絞り込み・並び順で使っていれば `checks` に 1 列 1 件だけ積む |

共通項目: `Alias` `Email` `FirstName` `Id` `IsActive` `LastName`
`MiddleName` `Name` `Phone` `Profile` `ProfileId` `Suffix` `Title`
`Type` `Username` `UserRole` `UserRoleId`

`Owner` はキュー等も指せるため、 `TYPEOF` があれば安全だが、 Bulk API では
使えないので生成しない。 実行時に失敗する可能性があることを `checks` で
知らせる形にする。

## 11. SOQL 自動生成

`src/soql_builder.py` の `build_soql(record)` が SOQL の下書きを組み立てる。
`SoqlDraft` は `soql` / `status` / `missing` / `checks` / `count_soql` /
`limit` / `use_bulk` / `bulk_blockers` / `cross_filter_links` を持つ。
`status` は `作成済み` / `要確認` / `一部作れず` / `作れず` の 4 種で、
`一部作れず` のときは本文の 1 行目に `INCOMPLETE_MARKER` （ `【未完成】…` ） を
入れる（ そのまま Salesforce に投げると構文エラーになる ）。
`cross_filter_links` は クロスフィルタ 1 個ずつの繋がりの判定
（ `CrossFilterLink` のタプル ）。 下記の 「クロスフィルタ（副問い合わせ）」 節で
説明する 。

### 取り方（ Bulk / REST ）

- `use_bulk` は取り方（ `True` = Bulk API 2.0、 `False` = REST の `query()` ）。
  既定は `True`
- `bulk_blockers` は REST にした理由（ 1 件 1 要素）。 `use_bulk` が `True` の
  ときは空。 理由には件数の根拠（ 管理表かサンドボックスか ） を書く
- SOQL 文字列を後からパースして判定しない

**件数の区分** （ `src.row_size.decide_row_size()` ） は 3 段で決める。

| 段 | 管理表の「2000件超」列 | サンドボックスの 2000 行チェック | 結果 |
|---|---|---|---|
| 1 | `○` | 問わない | 2000 件超 |
| 2 | `×` | 「超えていない」で行数が取れる | 行数 > 1000 なら 1000 件超、 そうでなければ 1000 件以下 |
| 2 | `×` | 「超えている」 | 1000 件超（ 2000 件超 にはしない。 管理表を採る ） |
| 2 | `×` | 判定不可・未実施 | 1000 件超 かどうかは不明（ 2000 件以下だと分かっている ） |
| 3 | 列が無い・空・「不明」 | 「超えている」 | 2000 件超 |
| 3 | 列が無い・空・「不明」 | 「超えていない」で行数が取れる | 行数 > 1000 なら 1000 件超、 そうでなければ 1000 件以下 |
| 3 | 列が無い・空・「不明」 | 判定不可・未実施 | 不明 |

- 段 1 の管理表は、 段 2・3 のサンドボックスより **優先** する。 サンドボックスで
  2000 件以下でも本番では超えることがあるため
- 1000 件以下と分かるのは、 サンドボックスの行数が取れたときだけ

**取り方の決め方** （ `src.soql_builder._decide_use_bulk()` ）

| 条件 | 取り方 | `bulk_blockers` | 追加の `checks` |
|---|---|---|---|
| 副問い合わせなし・1000 件超（ 2000 件超 を含む ） | Bulk | 空 | なし |
| 副問い合わせなし・1000 件以下 | 通常 SOQL | 件数が 1000 件以下のため（根拠つき） | なし |
| 副問い合わせなし・不明 | Bulk | 空 | なし |
| 副問い合わせあり | 通常 SOQL | 副問い合わせの理由（ 件数も 1000 件以下なら足す ） | 2000 件超 または 不明のとき、 「本番の件数が 5000 件を超えるなら SOQL を分ける」 |

- 副問い合わせ（ クロスフィルタ ） があるときは、 件数に関係なく REST にする。
  理由は 「WHERE の副問い合わせを Bulk API 2.0 で動作確認していないため」 である。
  Bulk API 2.0 で取れないとは断定していない（ 確実に動かせる REST を
  選ぶ、という意味 ）
- 閾値はモジュール定数（ `src.row_size.BULK_MIN_ROWS` = 1000 、
  `src.row_size.REST_MAX_ROWS_WITH_SUBQUERY` = 5000 ）。 設定ファイルには出さない

### 値の組み立て

| 演算子 | 組み立て |
|---|---|
| `equals` / `notEqual` | 1 値は `=` / `!=` 、 複数値は `IN` / `NOT IN` 。 ただし `multipicklist` と `boolean` / `checkbox` は `IN` が使えないので `( f = a OR f = b )` / `( f != a AND f != b )` にする |
| `lessThan` / `greaterThan` / `lessOrEqual` / `greaterOrEqual` | `f < v` 形式。 ただし `boolean` `checkbox` `picklist` `multipicklist` `combobox` `textarea` では missing（ レポートの選択リスト順と SOQL は違うため ） |
| `contains` / `notContain` / `startsWith` | `LIKE` 系。 `id` / `reference` / `multipicklist` では missing |
| `includes` / `excludes` | `multipicklist` は `INCLUDES` / `EXCLUDES` のまま。 `picklist` は `IN` / `NOT IN`（ 1 値は `=` / `!=` ） |

- 演算子名は大小文字を無視して正規名へ寄せる（ `lessorequal` と
  `lessOrEqual` は同じ ） 。 対応表に無い演算子（ `within` など ） は missing
- `datetime` 項目 + 日付だけの値は、 演算子で境界を選ぶ。 `>=` と `<` は
  `dT00:00:00Z` 、 `<=` と `>` は `dT23:59:59Z` 。 `equals` は
  `( f >= dT00:00:00Z AND f <= dT23:59:59Z )` 、 `notEqual` は
  `( f < dT00:00:00Z OR f > dT23:59:59Z )` 。 複数値は `equals` なら OR 、
  `notEqual` なら AND でつなぐ
- `date` / `datetime` 項目 + 相対日付の `NEXT_N_DAYS:n` （ 「翌 N 日」 ） は、
  レポートでは当日を含めて n 日 （ 当日 〜 n-1 日後 ） だが、 SOQL の
  `NEXT_N_DAYS:n` は翌日から n 日なので、 `TODAY` を足す。 `n` が 2 以上の
  ときは `equals` が `( f = TODAY OR f = NEXT_N_DAYS:n-1 )` 、 `notEqual` が
  `( f != TODAY AND f != NEXT_N_DAYS:n-1 )` 。 `n` が 1 のときは当日だけなので
  `f = TODAY` （ 括弧なし ） にする。 他の値と組むときは OR / AND で並べる
- `LIKE` の値の中の `%` と `_` は、 ワイルドカードではなく文字として探す
  （ `\%` `\_` にエスケープする ） 。 先に `\` と `'` をエスケープしてから
  処理する
- 文字列リテラルの改行・復帰・タブは `\\n` `\\r` `\\t` にエスケープする
- `reportFilters` の値は `csv.reader` で分割する（ `"a,b",c` は 2 値 ） 。
  数値系の値は従来どおりカンマで切らない
- 日付リテラルは許可リスト （ `THIS_MONTH` / `LAST_N_DAYS:30` /
  `N_DAYS_AGO:30` / `30_DAYS_AGO` ほか ） だけを通す。 ほかは missing
- 相対日付は表記のゆれを吸収して SOQL のリテラルに直す。 前後の空白・全角空白・
  全角数字・英字の大文字小文字・空白と `_` のゆれは区別しない
  - 数量つきの相対日付

    | 入力の例 | 出力 |
    |---|---|
    | `LAST_N_DAYS:60` `LAST N DAYS:60` `LAST_60_DAYS` `LAST 60 DAYS` `過去 60 日間` `過去60日` `過去60日間` | `LAST_N_DAYS:60` |
    | `NEXT 30 DAYS` `NEXT_30_DAYS` `次の 30 日間` `今後 30 日間` `翌 30 日間` `翌30日` | `NEXT_N_DAYS:30` |
    | `60 DAYS AGO` `N_DAYS_AGO:60` `60 日前` | `N_DAYS_AGO:60` |
    | `LAST 3 WEEKS` `過去 3 週間` | `LAST_N_WEEKS:3` |
    | `NEXT 3 WEEKS` `次の 3 週間` | `NEXT_N_WEEKS:3` |
    | `3 週間前` | `N_WEEKS_AGO:3` |
    | `LAST 6 MONTHS` `過去 6 か月` `過去 6 ヶ月` `過去 6 カ月` | `LAST_N_MONTHS:6` |
    | `NEXT 6 MONTHS` `次の 6 か月` | `NEXT_N_MONTHS:6` |
    | `6 か月前` | `N_MONTHS_AGO:6` |
    | `LAST 2 YEARS` `過去 2 年間` `過去 2 年` | `LAST_N_YEARS:2` |
    | `NEXT 2 YEARS` `次の 2 年間` | `NEXT_N_YEARS:2` |
    | `2 年前` | `N_YEARS_AGO:2` |

  - 「翌 N 日」 （ `NEXT_N_DAYS:n` ） はレポートでは当日を含めて n 日
    （ 当日 〜 n-1 日後 ） だが、 SOQL の `NEXT_N_DAYS:n` は翌日から n 日なので、
    等号・不等号の条件では `TODAY` を足した形にする。 `n` が 2 以上のときは
    `equals` が `( f = TODAY OR f = NEXT_N_DAYS:n-1 )` 、 `notEqual` が
    `( f != TODAY AND f != NEXT_N_DAYS:n-1 )` 。 `n` が 1 のときは当日だけ
    なので `f = TODAY` （ 括弧なし ） にする。 他の値と組むときは OR / AND で
    並べる。 例: 「次の 30 日間」 は `NEXT_N_DAYS:30` に正規化されて、
    条件は `( f = TODAY OR f = NEXT_N_DAYS:29 )` になる。 変換するときは
    `checks` に「翌 n 日は当日を含めて n 日なので TODAY と NEXT_N_DAYS:n-1
    にした: <項目名>」を 1 件積む。 `n` が 1 のときは「翌 1 日は当日を含めて
    1 日なので TODAY だけにした: <項目名>」

  - 固定語

    | 入力の例 | 出力 |
    |---|---|
    | `TODAY` `今日` | `TODAY` |
    | `YESTERDAY` `昨日` | `YESTERDAY` |
    | `TOMORROW` `明日` | `TOMORROW` |
    | `THIS WEEK` `今週` / `LAST WEEK` `先週` / `NEXT WEEK` `来週` | `THIS_WEEK` / `LAST_WEEK` / `NEXT_WEEK` |
    | `THIS MONTH` `今月` / `LAST MONTH` `先月` / `NEXT MONTH` `来月` | `THIS_MONTH` / `LAST_MONTH` / `NEXT_MONTH` |
    | `THIS QUARTER` `今四半期` / `LAST QUARTER` `前四半期` / `NEXT QUARTER` `次四半期` | `THIS_QUARTER` / `LAST_QUARTER` / `NEXT_QUARTER` |
    | `THIS YEAR` `今年` / `LAST YEAR` `昨年` `去年` / `NEXT YEAR` `来年` | `THIS_YEAR` / `LAST_YEAR` / `NEXT_YEAR` |

  - 数量は 1 以上の整数。 `0` や小数は解釈できないので missing
  - 固定語 （ `LAST_90_DAYS` `THIS_FISCAL_YEAR` ほか ） はそのまま通す
  - 変換したときは `checks` に「相対日付を変換した: <元の値> → <リテラル>（境界はレポートと SOQL で異なる場合あり）」を 1 件積む。 入力が既に同じリテラルなら積まない
- 日付は `2024/1/5` のようにゼロ埋めが無くても `2024-01-05` にする

### 組立式（`reportBooleanFilter`）

- 使える語は 番号 / `AND` / `OR` / `NOT` / 括弧 だけ。 大文字小文字は
  無視し、 出力は大文字にそろえる
- 他の語 / 括弧の不一致 / 同じ括弧の深さで `AND` と `OR` が混在する
  とき（ `1 AND 2 OR 3` ） は、 WHERE 全体を出さない（ 「組立式の条件を
  作れない」 の missing に入れる ） 。 `1 AND NOT 2` は通す
- 日付条件があるときは組立式全体を `( ... )` で囲む。 囲まないと
  `( a ) OR ( b ) AND 日付` になり、 日付条件が 1 つの条件にだけかかる形に
  なる
- 副問い合わせ（ クロスフィルタ ） の行があるときも同じように組立式全体を
  `( ... )` で囲む。 日付条件が無くても囲む

### クロスフィルタ（副問い合わせ）

`reportMetadata.crossFilters` の要素は、 Analytics API の crossFilters の
形（ 公式仕様の記憶。 実物では未確認 ） :

```json
{
  "criteria": [{"column": "...", "operator": "...", "value": "..."}],
  "includesObject": true,
  "primaryEntityField": "...",
  "relatedEntity": "...",
  "relatedEntityJoinField": "..."
}
```

#### 繋がりの判定（ `SoqlDraft.cross_filter_links` ）

`crossFilters` の 1 個ごとに、 主オブジェクトと子オブジェクトが **直接つながる
リレーションか** を判定する。 判定結果は `SoqlDraft.cross_filter_links` に
`CrossFilterLink` のタプルとして持つ。

| フィールド | 型 | 意味 |
|---|---|---|
| `index` | int | `crossFilters` の中の順番（ 1 始まり ） |
| `status` | str | 判定。 `直接` / `直接でない` / `確認できず` のいずれか |
| `primary_field` | str | 主オブジェクト側の項目 API 名 |
| `child_object` | str | 子オブジェクト名 |
| `join_field` | str | 子オブジェクト側の結合項目 API 名 |
| `relationship_name` | str | 子リレーション名 |
| `converted` | bool | 副問い合わせとして SOQL に入れたか |
| `reason` | str | 判定の理由（ `直接` でも `converted` が `False` のときは 副問い合わせにできなかった理由 ） |

判定は 3 種:

- **`直接`** … 次の **すべて** を満たす
  1. `primaryEntityField` が主オブジェクトの項目に解決でき、 型が `id`
     （ 解決順は 「主オブジェクトの項目名と大文字小文字無視で一致」
     → 「`<主オブジェクト>.` を外して一致」 → 「列対応表の列キーと一致し、
     対応フィールドが主オブジェクトの項目」 ）
  2. 主オブジェクトの `childRelationships` に、 (`childSObject` または
     `relationshipName` が `relatedEntity` と一致) **かつ**
     (`field` が結合項目と一致) の要素がある。 比較は大文字小文字を無視する
  3. 結合項目が子オブジェクトの項目に解決できる
- **`直接でない`** … 情報はそろったが合っていない
  - 主側の項目が `id` 以外（ `reference` など ）
  - `relatedEntity` が `childRelationships` に無い
  - `relatedEntity` は一致するが 結合項目がそのリレーションの `field` でない
    （ reason に そのリレーションの実際の参照項目を並べる ）
- **`確認できず`** … 情報が足りない
  - `crossFilter` が dict でない
  - `primaryEntityField` が無い / 主オブジェクトの項目に解決できない
  - 主オブジェクトの `childRelationships` が空
  - `relatedEntity` / `relatedEntityJoinField` が無い
  - 子オブジェクトの describe が無い
  - 結合項目が子オブジェクトの項目に解決できない

同じ子オブジェクトへ参照が 2 本あるとき（ 例: `Contact.AccountId` と
`Contact.ParentAccount__c` ） は、 結合項目に一致するリレーションだけを
採用する。 別のリレーションを `直接` にしない。

#### 変換のルール

- **SOQL にするのは `直接` だけ。** `直接でない` と `確認できず` は
  `missing` に元の値の `repr` と理由を入れて、 従来どおり【未完成】にする
- `includesObject` / `criteria` / 副問い合わせの上限（ 1 文に 2 個まで ） で
  変換できないときは、 `status` は `直接` のまま `converted=False` にして
  `reason` に理由を入れる
- 3 個目以降も判定して `cross_filter_links` に載せる
- `作れず` （ SELECT に入る列が無い ） の早期 return でも、 主オブジェクトが
  分かっていれば `cross_filter_links` を入れる。 主オブジェクト不明なら空
- 組立式が壊れて WHERE 全体を出さないときは、 全リンクを `converted=False` に
  する

#### 変換できたとき

- 変換できるときは `<主側項目> IN (SELECT <結合項目> FROM <子オブジェクト> WHERE <条件> AND <条件>)` にする。 `includesObject` が `false` なら `NOT IN` 。 `criteria` が空リスト `[]` のときだけ内側の `WHERE` は出さない
- 次の **すべて** が確かめられないときは変換しない。 1 つでも欠けたら
  `missing` に元の値の `repr` と理由を入れて、 従来どおり【未完成】にする
  （ 推測で埋めない。 件数がレポートより増える事故を防ぐため ）
  - `includesObject` が `bool` （ `operator` キーは見ない ）
  - `criteria` の `column` が子オブジェクトの項目に解決でき、 値と演算子は
    既存の `_extract_filter_values` / `_build_filter_condition` で作れる
    （ 子の項目の型を渡す。 エスケープもそこに任せる ）
  - `criteria` がある（ キーが無い・ `None` は「criteria が無い」として
    変換しない。 絞り込みが消えるとレポートより多い件数になるため ）
- 副問い合わせは 1 文に 2 個まで（ `CROSS_FILTER_MAX_SUBQUERIES` ）。
  3 個目以降は `missing`
- 変換できたものは `checks` に
  「クロスフィルタを副問い合わせにした（公式仕様の形から作った。レポートと件数を実物で確かめる）: <条件式>」
  を入れる。 つまり最良でも状態は「要確認」
- 内側の条件の `checks` （ ロングテキストの注意 など ） は捨てずに、 全体の
  `checks` に入れる
- 件数用の `count_soql` と `where_items` にも同じ行が入る

#### 判定の出し先

1. **SOQL調査.xlsx の 「一覧」 シート**: 「取り方」 の直後の列
   「クロスフィルタの繋がり」 に、 件数が 0 でない判定だけを
   `直接2・直接でない1・確認できず1` の形で並べる。 クロスフィルタが
   無ければ空
2. **Markdown**: `## 取り方` の直後に `## クロスフィルタの繋がり` を出す
   （ 判定が 1 件でも無いときは出さない ）。 列は 番号 / 判定 / 主側項目 /
   子オブジェクト / 結合項目 / リレーション名 / SOQL（ `入れた` /
   `入れていない` ） / 理由
3. **生成 .py**: `# 状態:` の行の直後に 1 件 1 行で
   `# クロスフィルタ 1: 直接（Contacts: Contact.AccountId → Account.Id）SOQL に入れた`
   または `# クロスフィルタ 2: 直接でない（理由）SOQL に入れていない` 。
   値は `_flatten` で改行を空白に置き換える
4. **Markdown の 「SOQL を組むときの注意」**: 1 件でも `converted` なら
   「クロスフィルタは副問い合わせにした（REST で取る）」、 1 件も無ければ
   「クロスフィルタは副問い合わせにできていない（理由は「クロスフィルタの繋がり」）」

### 子の列を子から取る（ FROM の切り替え ）

レポートの列が子オブジェクトの項目のときは、 サブクエリ
（ `SELECT (SELECT ... FROM Contacts) FROM Account` ） ではなく、 **子から取る**
（ `SELECT Account.Name, Name FROM Contact` ） 形にする。 レポートと同じ
1 行 1 子の粒になり、 Bulk API 2.0 のまま取れて、 ダウンローダーの変更が
要らない。

`src/mapping/child_base.py` の `apply_child_base()` がやる。 **`site_run` の
列対応表ができたあと、 `列の直し` の上書きの前に** 適用する。

**発動条件。** 列キーの最初の `.` より前が、 主オブジェクトの
`childRelationships` の `childSObject` か `relationshipName` に大文字小文字
無視で一致し、 かつ主オブジェクト名と一致しない行が 1 つでもあるとき。
解決済みかどうかには依存しない。 子の列が表示名の照合で親の項目
（ 親の `Name` など ） に解決されると、 親の値を取り違えるため。

**切り替えられる条件。** レポートの列が指している直接の子オブジェクトが
**1 つだけ** のとき。 次のときは切り替えず、 列は `(不明)` にして理由を残す
（ `missing` に出て【未完成】になる ）。 対象にした列は親の値のままでは
別の値を取るため、 親の値は残さない。

| 場合 | 備考 |
|---|---|
| 子オブジェクトが複数 | `子オブジェクトが複数あるので 1 つの SOQL にできない: A, B` |
| 同じ子オブジェクトへの参照が複数 | `同じ子オブジェクトへの参照が複数あるので判別できません: ...` |
| 子の describe が取れない | `子オブジェクト X の項目定義が取れないため子から取れません` |
| 子の項目に親への参照項目が無い | `子オブジェクト X に参照項目 Y が無いため子から取れません` |

親へ戻るリレーション名を探すときの項目名の比較は、 大文字小文字を無視する
（ `childRelationships` の `field` には手入力の値もあるため ）。

**切り替え後の扱い。**

- 子の列は `resolve_column_key_to_soql(子, 列キー, 子describe, fetcher)` で
  解決し直す。 列キーの接頭辞がリレーション名のときは子オブジェクト名に
  置き換えてから渡す。 解決できない列は `(不明)` にして理由を書く
  （ 親の値は残さない ）
- 親の列（ 解決済みの行すべて ） は `対応フィールドAPI名` の前に
  `<リレーション名>.` を付ける。 合計の段数が `COLUMN_KEY_PATH_MAX_DEPTH`
  を超える列は `(不明)` にして理由を書く
  - **注意**: 別の関連オブジェクト経由で解決した列 （ 例 `What.Name` ） にも
    同じリレーション名が付く。 その経路が子の describe に無い場合は
    Salesforce が実行時にエラーになる。 実際に使うときは実物で確かめること
- 子を `state.objects` に入れる（ PII と列の直しのため ）。
  `列の直し` の上書きには主オブジェクトとして **子** を渡す
- `SELECT` / `WHERE` / `ORDER BY` は列対応表を読むので、 自動で追従する
- `ReportRecord.soql_from_object` に子オブジェクト名、
  `soql_from_relationship` に子から親へ戻るリレーション名（ 例 `Account` ） を
  入れる。 `main_object` は **変えない** （ 資料の「主オブジェクト」 は親のまま ）

**出力への反映。**

- `build_soql` の FROM は `record.soql_from_object or record.main_object`
- `列名の対応.csv` の主オブジェクト列は **FROM の値** にする
  （ ダウンローダーが「最初の FROM」 から主オブジェクトを引くため ）
- 状態は最良でも `要確認`。 `checks` に
  「子から取る形にした（親 Account、子 Contact、経路 Account）。子を持たない親の行は出ない。レポートと件数を確かめる」
  が入る
- `USE_BULK` は件数の判定に従う（ 1000 件以下なら通常 SOQL になる ）
- クロスフィルタがあるレポートで切り替えたときは、 副問い合わせの左辺が変わるので
  **変換しない** 。 判定はそのまま `converted=False` にして、 `reason` に
  「子から取るレポートのクロスフィルタは未対応」、 `missing` に入れる
- 集計レポートでの動作は変えない（ `aggregates` の missing はそのまま ）

### 列パスの自動確定

同じ表示名の候補が複数あるとき、 **主オブジェクトに最も近い候補** （ 経路の
段数が最少 ） が 1 つに決まれば自動で採用する。 同じ段数で並んだら従来どおり
「複数候補あり」 で止める。

- 段数は `soql_chain` の `.` 区切りの要素数（ 主オブジェクトの項目は 0 段 ）
- 実装は `src/mapping/column_map.py` の `_try_resolve_by_label()` と
  `_try_resolve_by_reference_prefix()` の 「複数候補」 の分岐
- FK 経路（ `_multi_from_fk` ） は同じ段数なので止めたまま
- 採用した行の備考は定数 `AUTO_PATH_NOTE` （
  `複数候補から自動で確定（経路が最短）` ） で始め、 続けて採用したものと
  他の候補を書く。 「他の候補」 には採用した候補を出さない

**判定と出力。**

- 状態の定数 `AUTO_PATH_NOTE` は `src/mapping/row_status.py` にある
- `column_status()` はこの行を **要確認** にする
- `column_candidates()` はこの行の「候補」 列に他の候補を出す
- `列の直し.xlsx` では **要確認** になる。 人の値が常に優先される
- `build_soql` は、 SELECT・絞り込み・並び順で使われる列にこの備考があれば
  `checks` に 1 列 1 件
  「列 <表示名> は候補から自動で確定した: <採用した列>（他の候補: ...）。値がレポートと同じか確かめる」
  を積む（ `_collect_owner_polymorphic_checks` と同じ作り ）。 件数比較では
  値の違いを検出できないため

## 12. SOQL レポート Python ファイル

`src/report_py.py` が `OUTPUT_DIR/SOQLレポート/report_<管理番号>.py` に
書く。 中身はダウンローダーの `SoqlReport` のサブクラスで、 そのまま
`src/soql_reports/reports/` に置ける。

- 1 レポート 1 ファイル。 SOQL が作れなかった（ `作れず` ） レポートは
  ファイルを作らない
- ファイル名の管理番号は英数字と `_` だけ残す（ 他の文字は `_` に置き換える ）。
  置換で同名になる管理番号は、 後の方に連番 `_2` を付ける
- `一部作れず` の SOQL は、 `【未完成】` の行をそのまま残す（ ダウンローダーが
  実行前に止める ）
- `NAME` はレポート名。 `reportMetadata.name` を書き、 それが無い・空・
  文字列でないときは概要（ `summary` ） を書く。 どちらも空なら `NAME` の行は
  書かない
- `REPORT_ID` はレポート ID。 管理表の URL（ `record.url` ） から
  `comken.toolbox.salesforce.report.report_id_from_url` で取り出す。 URL が空・
  レポート ID が無いときは `REPORT_ID` の行は書かない（ ファイルは作る ）。
  URL 全体（ 組織のドメイン ） は書かない
- `REPORT_ID` は試験用リポジトリが、 管理表を通さず SOQL の件数とレポートの
  総件数を比べるのに使う。 ダウンローダーはこの行を読まない。 管理表の URL は
  書き換えない（ 正のまま使う ）
- `USE_BULK` は取り方（ `True` = Bulk API 2.0、 `False` = REST の `query()` ）。
  `SoqlDraft.use_bulk` が `True` のときは `True` で書く。 `False` のときは
  `False` で、 理由をコメントに付ける（ `bulk_blockers` を `; ` でつないだ
  もの。 副問い合わせの理由と、 件数が 1000 件以下のときの原因。 改行と制御文字は
  空白に置き換える ）。 置く場所は `REPORT_ID` の
  行の直後（ `REPORT_ID` が無いときは `NAME`、 どちらも無いときは `KEY` の
  直後） で、 `COLUMN_NAMES` より前
- `COLUMN_NAMES` は SELECT に入った列の `SOQL列名: 表示名` 。 同じ表示名が
  2 列以上あるときはその列を入れず、 `# 見出しが重なるので自動の対応に任せた:`
  のコメントにする。 `CHECK_COUNT` は書かない（ 既定の `True` のまま ）
- **文字列の組み立ては必ず `repr()` を通す** 。 概要・レポート名・missing・
  checks の改行と制御文字は空白に置き換え、 docstring に入る `\` と `"""` は
  無害化する。 値に `\n__import__("os").system("x")` があってもコードに
  ならない
- **SOQL は 3 重引用符で、 改行をそのまま書く** 。 1 行ずつ `repr()` と同じ
  エスケープを通すので、 `\` は `\\` 、 `"` は `\"` になる。 `soql()` の返り値を
  元の SOQL と 1 文字も変えないため、 2 行目以降は字下げしない
